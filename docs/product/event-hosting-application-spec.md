# 赛事承办申请产品规格

状态：CAAU-027 待确认设计；本轮只交付规格、技术设计和计划，不代表业务功能已实现。

本文定义“赛事承办申请”作为正式赛事创建前的独立流程。已确认规则与待确认事项严格分开；文中的数据结构和页面名称是后续实现建议，不自动成为业务规则。

## 1. 目标与边界

### 1.1 已确认目标

1. 承办方自行填写赛事名称、时间、地点，提出新的办赛申请。
2. 总部审核通过后，系统自动创建正式赛事，并将申请机构登记为该赛事的承办方。
3. 未通过的申请不创建正式赛事。
4. 申请人是本次提交人，不默认限定为该赛事唯一经办人。
5. 原有办赛材料提交与审核完整保留，作为申请获批后的后续流程。

### 1.2 本流程不等于

- 申请不是正式赛事；申请处于待审、补充材料或驳回状态时均不得出现在正式赛事列表中。
- 申请机构是获批后的承办机构业务事实，不等于向某个人授予赛事访问权。
- 申请人是提交动作的实际人员，不自动成为唯一经办人、主经办人或材料任务经办人。
- 赛事承办申请资料不是现有办赛材料任务；获批不会在规则未确认前自动创建 `MaterialTask`。
- 本规格不处理赛事获批后的信息变更申请、报名、支付、俱乐部通知或外部报名系统同步。

## 2. 角色与数据范围

| 参与方 | 已确认能力 | 尚未确认 |
| --- | --- | --- |
| 承办方申请人 | 代表其所在申请机构填写并提交申请；提交记录保留实际申请人 | 哪些组织成员可新建、编辑、提交、查看同机构其他人的申请 |
| 总部审核方 | 对已提交版本执行通过、驳回或要求补充材料 | 具体角色、赛事范围、是否允许多人会签、是否允许申请创建人审核 |
| 申请机构 | 获批后登记为正式赛事的承办方 | 一个赛事是否允许多家承办/协办机构及关系类型 |
| 获批后经办人 | 不由“申请人”身份自动确定 | 如何指定、多少人、是否自动授权以及如何交接 |

所有读写必须由后端按当前会话、组织成员关系和审核权限判定；前端传入 organizationId、applicationId 或 eventId 不能作为授权依据。

## 3. 申请表与资料

### 3.1 已确认申请字段

首个申请版本至少保存以下业务值：

- 赛事名称；
- 赛事时间；
- 赛事地点。

“赛事时间”是单一时间点、起止区间还是多赛段，“赛事地点”是自由文本还是场馆/地址结构，均待确认。实现前不得以演示格式替代正式口径。

### 3.2 必交与选交资料的表达

本轮**不创建固定材料清单**。后续模型应支持由已确认来源产生的“申请资料要求版本”：

- 每个要求项有稳定 ID、名称、说明、`必交/选交`标记，以及经确认的格式、数量和大小限制；
- 必交项在提交时由后端校验已提供有效资料，选交项允许为空；
- 可选资料还可包含申请方主动补充的附件，但是否开放、数量上限待确认；
- 要求版本在申请提交时形成快照或引用不可变版本，防止清单后改写既有提交含义；
- 要求从哪里配置、由谁发布、何时对新申请生效，以及补充版本是否沿用原要求版本，均列为实施前确认项。

在资料清单未确认前，产品只能设计通用能力，不能自动生成“营业执照、场馆证明”等任何具体项。

### 3.3 草稿、提交版本与附件

建议采用“可变草稿 + 不可变提交版本”：

1. `Application` 是申请身份和当前状态；保存申请机构、草稿修订号及当前提交版本指针。
2. 草稿保存当前表单值、资料条目和已确认附件引用，使用 expected revision 防止覆盖。
3. 每次正式提交生成不可变 `ApplicationSubmission`（V1、V2……），冻结：申请表完整快照、资料要求版本/快照、每项资料元数据、附件关系、申请机构、实际提交人和服务器时间。
4. 附件使用私有对象存储；上传意图、字节校验、确认、草稿绑定、提交版本绑定分开。提交版本绑定后不得替换或删除；新版本需要形成新的附件关系，旧版本字节和摘要保留。
5. “要求补充材料”后的修改不覆盖 V1；再次提交生成 V2，并保留总部要求、版本差异、每次提交人与时间。
6. 审核动作必须指向明确 submissionId；总部看到和裁决的是某一不可变版本，而不是仍可变化的草稿。

申请人字段记录每次提交的实际 actor。不同版本是否允许由同机构其他有权人员提交，尚未确认；模型不得把首次申请人固化为唯一办理人。

## 4. 状态和操作语义

建议状态集合如下，最终中文名称可在页面实现前确认：

| 状态 | 含义 | 允许的审核操作 | 是否创建赛事 |
| --- | --- | --- | --- |
| 草稿 `DRAFT` | 尚未正式提交，或正在准备首次版本 | 无 | 否 |
| 待审核 `PENDING_REVIEW` | 当前不可变版本已提交，等待总部处理 | 通过、驳回、要求补充材料 | 否 |
| 待补充 `NEEDS_SUPPLEMENT` | 总部未作通过结论，要求申请方按意见补充 | 申请方编辑并形成下一提交版本；具体操作权限待确认 | 否 |
| 已驳回 `REJECTED` | 总部明确不通过当前申请 | 当前申请不创建赛事 | 否 |
| 已通过 `APPROVED` | 总部通过指定提交版本，正式赛事及承办关系已原子创建 | 不再对同一申请重复裁决 | 是，且只能一个 |

三种审核动作必须区分：

- **通过**：对当前提交版本形成通过结论；同一事务创建正式赛事、登记申请机构的承办关系、保存来源追溯并更新申请状态。不得只改状态后异步补建赛事。
- **驳回**：形成明确不通过结论和原因，不创建赛事。驳回后能否在原申请继续补正，或只能新建申请，尚未确认。
- **要求补充材料**：不是驳回，也不创建赛事；保存具体补充要求，将当前版本封存为已处理历史。申请方后续提交必须形成新版本，不能修改被要求补充的版本。

是否需要“审核中/领取”、申请方撤回、总部撤销错误操作、处理时限和通知均未确认，不加入首期状态。

## 5. 获批结果与追溯

获批事务完成后应能回答：

- 该正式赛事由哪个申请产生；
- 总部批准的是 V1、V2 中的哪一个提交版本；
- 当时获批的赛事名称、时间、地点和资料要求/附件是什么；
- 申请机构为何成为该赛事的承办机构；
- 谁提交、谁审核、何时发生、审核意见是什么。

正式赛事保存稳定的申请来源关系，获批申请版本保存完整快照。后续即使赛事信息通过另一个已批准的变更流程更新，也不得改写最初获批版本。现有总部直接创建或历史赛事不伪造申请来源。

## 6. 承办关系与访问授权

获批时登记的是赛事与申请机构之间的业务关系，建议称 `EventOrganizerAppointment`。它与以下对象分开：

- `EventGrant`：某组织成员能否访问赛事的安全授权；继续只表示授权，不表示承办事实；
- `EventOrganizerAgent`：获批后代表承办机构处理赛事的人员关系，人数和职责待确认；
- `TaskScope`：某一个办赛材料任务当前由哪个机构/人员办理；
- 申请提交人：某一版本的实际提交 actor。

获批事务不得因为申请人存在就默认创建“唯一经办人”。是否给申请人或其他人员创建 `EventGrant`、授予什么能力、由谁确认，必须在实施前明确。业务承办关系即使暂未配置人员授权也应保持为事实记录，不能用 grant 的有无反推承办关系。

## 7. 页面和入口调整

### 7.1 总部 Web

建议新增独立“赛事承办申请”入口，与现有“赛事管理”和“资料审核”分开：

- 申请列表：按状态、申请机构、提交时间查询；权限和可见范围由后端限定；
- 申请详情：显示申请表、资料要求完成情况、不可变 V1/V2、附件、提交人/时间及审核历史；
- 审核区：对当前版本分别提供“通过”“驳回”“要求补充材料”，展示各自动作后果并二次确认；
- 通过成功后展示唯一正式赛事链接和承办机构关系，不重复提供创建按钮；
- 赛事详情新增“来源”区域：有申请来源时链接到获批版本；历史/总部直接创建赛事明确显示无申请来源，不伪造数据；
- 承办机构关系和人员访问授权分区展示，禁止把 `ORGANIZER EventGrant` 标成“承办方”。

### 7.2 承办方小程序

“赛事承办申请”是赛事创建前流程，不依赖当前赛事选择器：

- 在主页业务板块提供独立入口；未拥有任何赛事的合格申请人仍应能进入（具体资格待确认）；
- 页面包括申请列表、创建/编辑草稿、申请表、资料上传、提交确认、状态详情、补充要求与版本历史；
- 待审核只读；待补充时在权限确认后从已处理版本形成新草稿；已驳回展示原因但是否出现“重新申请”入口待确认；
- 已通过展示正式赛事结果。是否可立即进入赛事及材料页面取决于后续经办授权和材料任务规则，不能仅凭申请人身份放行。

现有主页赛事上下文、材料提交、审核进度和私有附件流程保持不变；新入口不得把未获批申请注入赛事选择列表。

## 8. 兼容与数据保留

1. 后续只允许追加模型和迁移，不修改已执行历史迁移。
2. 现有 `Event`、`EventScope`、`EventGrant`、`MaterialTask`、`TaskScope`、材料、附件、提交版本、审核动作和审计记录原样保留。
3. 不从现有任务指派或 `ORGANIZER EventGrant` 反推、批量回填赛事承办关系。
4. 现有赛事不补造申请、提交人或批准版本；来源保持“历史/总部直接创建”或空来源的兼容表达。
5. 新申请附件与现有办赛材料附件分属不同业务归属，不能复用附件 ID 绕过授权；底层私有存储能力可复用。
6. 申请获批不改写既有赛事或任务；创建的是一个新正式赛事。未通过、补充中和事务失败均不得留下孤立 Event/EventScope/承办关系。
7. 后续数据库验收必须对迁移前后旧表摘要、历史迁移 checksum、私有文件 hash 和旧流程权限做保留验证。

## 9. 验收口径（后续实现阶段）

- V1 提交后不可变；要求补充后 V2 保留 V1、附件摘要、提交人和审核意见。
- 通过请求重复点击、响应丢失重试和并发审核时至多创建一个 Event、一条来源关系和一条有效承办关系；事务失败时全部不创建。
- 驳回和要求补充均不创建 Event，且历史中动作语义不同。
- 正式赛事可追溯到唯一获批申请版本；历史/直接创建赛事仍可正常访问且不伪造来源。
- `EventOrganizerAppointment` 与 `EventGrant` 分开验证：有承办关系不等于已有人员授权，有 grant 不等于承办机构。
- 现有材料任务、附件、不可变版本和审核历史在升级、重启及新页面接入后保持可读和原权限行为。
- Web 与小程序分别验证空态、加载、失败、无权、重复操作和版本历史；小程序构建、开发者工具和真机证据分别记录。

## 10. 实施前必须确认的规则

1. **驳回后能否重新申请**：允许恢复同一申请、必须新建申请，还是按条件决定；重复赛事名称/时间是否拦截。
2. **申请审核权限**：由赛事管理员、审核员或新角色处理；可见范围、是否允许创建/提交相关人员审核、是否会签。
3. **申请资格与机构内权限**：哪些承办机构和成员可创建、查看、编辑、提交；同机构能否交接草稿或由他人提交 V2。
4. **获批后的经办授权**：经办人数、指定人、角色、何时创建/撤销 `EventGrant`，申请人是否仅作为候选而非默认经办人。
5. **何时创建办赛材料任务**：获批事务内、总部后续手工创建，还是满足其他条件后创建；任务名称、截止、经办人、要求来源均未确认。确认前获批事务不创建任务。
6. **申请资料清单**：具体必交/选交项、配置者、版本生效规则、格式/大小/数量、申请方能否自由追加资料。
7. **时间和地点结构**：时区、起止、多赛段、场馆和地址字段及校验规则。
8. **补充材料规则**：是否只补附件还是可改名称/时间/地点；总部补充要求是否必填；补充次数和截止时间。
9. **驳回/补充意见**：是否必填、最小内容、附件或结构化问题项要求。
10. **申请方撤回与作废**：提交后能否撤回，获批前谁可作废，错误批准如何处理。
11. **并发审核方式**：共享处理、显式开始审核、领取或多人会签；当前仅确认存在总部审核动作。
12. **赛事承办基数**：一个赛事是否只能有一家承办机构，是否存在主办/承办/协办类型和有效期。
13. **获批后赛事生命周期**：正式赛事初始状态、发布时间、是否立即对其他角色可见。
14. **后续信息变更**：获批申请快照如何与未来赛事信息变更申请衔接，不在本流程内提前决定。
15. **通知**：提交、补充、驳回、通过是否需要站内/微信通知，收件人和失败重试规则。
