# 赛事承办申请产品规格

状态：CAAU-027 待确认设计；本轮只交付规格、技术设计和计划，不代表业务功能已实现。

本文定义“赛事承办申请”作为正式赛事创建前的独立流程。已确认规则与待确认事项严格分开；文中的数据结构和页面名称是后续实现建议，不自动成为业务规则。

## 1. 目标与边界

### 1.1 已确认目标

1. 承办方自行填写赛事名称、时间、地点，提出新的办赛申请。
2. 总部审核通过后，系统自动创建正式赛事，并将申请机构登记为该赛事的承办方。
3. 未通过的申请不创建正式赛事。
4. 申请人是本次提交人，不默认限定为该赛事唯一经办人。
5. 原有办赛材料提交与审核完整保留，作为申请获批后的后续流程。
6. 申请资料要求为：必交“营业执照”“简介（办赛经验）”“现场照片”，选交“其他文档”。
7. 申请审核必须包含“审核中”状态；有权审核员明确点击“开始审核”后进入，打开详情不触发状态变化。
8. 要求补充材料后，承办方可在同一原申请中修改并重交，形成新的不可变提交版本，旧版本及审核历史完整保留。
9. 驳回是当前申请的终止状态；该申请不得恢复编辑或重交。承办方可以另建新申请，原申请及审核历史完整保留。
10. 申请审核使用独立权限，不依赖正式赛事 `EventGrant`；有权总部审核员共享查看和处理申请。
11. 审核员必须明确点击“开始审核”进入审核中，该动作不产生独占领取；其他有权审核员可以接续处理。
12. 每个审核状态变更记录实际操作人、服务器时间和目标提交版本；禁止审核本人提交过任一版本的申请，同一版本的冲突审核只能一个成功且不能覆盖既有结果。
13. 同一申请机构内，具有申请办理权限的有效经办人可共同查看、编辑、提交申请及补充版本，不限定创建人；每次操作保留实际操作人和历史，使用并发控制防止多人编辑覆盖，禁止跨机构访问，已提交版本不可修改。

### 1.2 本流程不等于

- 申请不是正式赛事；申请处于待审、补充材料或驳回状态时均不得出现在正式赛事列表中。
- 申请机构是获批后的承办机构业务事实，不等于向某个人授予赛事访问权。
- 申请人是提交动作的实际人员，不自动成为唯一经办人、主经办人或材料任务经办人。
- 赛事承办申请资料不是现有办赛材料任务；获批不会在规则未确认前自动创建 `MaterialTask`。
- 本规格不处理赛事获批后的信息变更申请、报名、支付、俱乐部通知或外部报名系统同步。

## 2. 角色与数据范围

| 参与方 | 已确认能力 | 尚未确认 |
| --- | --- | --- |
| 承办方申请经办人 | 同一申请机构内具有申请办理权限且当前有效的经办人，共享查看、编辑、提交申请及补充版本；每步记录实际人员，不限定创建人 | 办理权限由谁授予/撤销及成员停用管理流程 |
| 总部审核方 | 通过独立承办申请审核权限共享查看和处理申请；显式开始但不独占，其他有权审核员可接续；禁止审核本人提交过任一版本的申请 | 独立权限由谁授予/撤销及停用管理流程 |
| 申请机构 | 获批后登记为正式赛事的承办方 | 一个赛事是否允许多家承办/协办机构及关系类型 |
| 获批后经办人 | 不由“申请人”身份自动确定 | 如何指定、多少人、是否自动授权以及如何交接 |

所有读写必须由后端按当前会话、组织成员关系和权限判定；前端传入 organizationId、applicationId 或 eventId 不能作为授权依据。申请方必须同时满足 active user、active 同机构成员和有效申请办理权限；创建人不获得绕过停用/撤权的永久权限，同机构无办理权限者及任何跨机构成员均不得列表、查看、编辑、上传、提交或下载。承办申请审核权限独立于正式赛事授权：有 `EventGrant` 但没有申请审核权限者不得查看/处理申请；有申请审核权限者无需等待申请获批或取得 `EventGrant` 即可进入共享申请队列。

## 3. 申请表与资料

### 3.1 已确认申请字段

首个申请版本至少保存以下业务值：

- 赛事名称；
- 赛事时间；
- 赛事地点。

“赛事时间”是单一时间点、起止区间还是多赛段，“赛事地点”是自由文本还是场馆/地址结构，均待确认。实现前不得以演示格式替代正式口径。

### 3.2 必交与选交资料的表达

已提出的申请资料要求如下，不再把整个清单标记为未确认：

| 属性 | 资料项 |
| --- | --- |
| 必交 | 营业执照 |
| 必交 | 简介（办赛经验） |
| 必交 | 现场照片 |
| 选交 | 其他文档 |

后续模型应将上述清单保存为可追溯的“申请资料要求版本”：

- 每个要求项有稳定 ID、名称、说明和`必交/选交`标记；不得擅自增加“场馆证明”等未提出项目；
- 三项必交资料在提交时由后端校验已提供有效资料，“其他文档”允许为空；
- 要求版本在申请提交时形成快照或引用不可变版本，防止后续规则变化改写既有提交含义；
- **仍待确认的只是细化口径**：各项允许格式、单文件/总大小、文件数量，以及证照暂缺、现场尚未布置、多场地等特殊情况如何处理；
- 清单由谁配置/发布、何时对新申请生效，以及补充版本是否沿用原要求版本，也需在实施前确认，但不影响上述四项及其必交/选交属性已被提出。

### 3.3 草稿、提交版本与附件

建议采用“可变草稿 + 不可变提交版本”：

1. `Application` 是申请身份和当前状态；保存申请机构、草稿修订号及当前提交版本指针。
2. 草稿保存当前表单值、资料条目和已确认附件引用。所有有权同机构经办人按同一权威 draft revision 协作：保存、附件绑定/移除和提交必须携带 expected revision；过期 revision 返回冲突和最新 revision，不自动合并或覆盖另一人的成功修改。
3. 每次正式提交生成不可变 `ApplicationSubmission`（V1、V2……），冻结：申请表完整快照、资料要求版本/快照、每项资料元数据、附件关系、申请机构、实际提交人和服务器时间。
4. 附件使用私有对象存储；上传意图、字节校验、确认、草稿绑定、提交版本绑定分开。提交版本绑定后不得替换或删除；新版本需要形成新的附件关系，旧版本字节和摘要保留。
5. “要求补充材料”后，系统在同一 applicationId 下允许编辑原申请并重交；修改不覆盖 V1，再次提交生成 V2，并保留总部补充要求、版本差异、每次提交人与时间。
6. 草稿创建、保存、附件操作、首次提交和补充重交都记录实际 actorId、服务器时间、前后 revision/目标版本及必要的不可变操作历史；不能把创建人回填为他人的操作人。
7. 审核动作必须指向明确 submissionId；总部看到和裁决的是某一不可变版本，而不是仍可变化的草稿。

申请的 createdBy 只记录创建动作，不是办理权限或唯一责任人。每次提交版本分别记录实际 submittedBy；同机构其他有权有效经办人可以提交 V1 或补充版本。提交形成版本后，任何申请方成员都不能修改该版本快照、附件关系、提交人或时间，只能在允许编辑的当前草稿中形成下一版本。

## 4. 状态和操作语义

状态集合必须包含“审核中”；英文枚举是技术设计名称，中文文案可在页面实现前确认：

| 状态 | 含义 | 允许的下一步 | 是否创建赛事 |
| --- | --- | --- | --- |
| 草稿 `DRAFT` | 尚未正式提交，或正在准备首次版本 | 提交 | 否 |
| 待审核 `PENDING_REVIEW` | 当前不可变版本已提交，等待总部开始处理 | 有权审核员明确点击“开始审核”进入审核中 | 否 |
| 审核中 `IN_REVIEW` | 总部已开始处理当前提交版本，但尚未形成结论 | 通过、驳回、要求补充材料 | 否 |
| 待补充 `NEEDS_SUPPLEMENT` | 总部未作通过结论，要求申请方在原申请中修改 | 编辑同一申请并重交，形成 Vn+1 后回到待审核 | 否 |
| 已驳回 `REJECTED` | 总部明确终止当前申请 | 只读保留；不得恢复编辑或重交，可另建新申请 | 否 |
| 已通过 `APPROVED` | 总部通过指定提交版本，正式赛事及承办关系已原子创建 | 不再对同一申请重复裁决 | 是，且只能一个 |

“审核中”及其进入方式均已确认：有权审核员必须明确点击“开始审核”才从待审核进入审核中。打开申请详情仅为只读查看，绝不自动进入审核中，也不生成开始审核动作。“开始审核”只记录实际开始人、服务器时间和目标提交版本，不产生 owner、领取锁或排他权；其他有权总部审核员可接续执行通过、驳回或要求补充材料，结论人可以与开始人不同。

每个开始审核和审核结论动作都必须指向明确 submissionId，并记录实际 actorId、服务器时间和版本。当前操作人若是该申请任一提交版本的 submittedBy，后端必须拒绝开始审核及任何审核结论，不能仅由前端隐藏按钮。同一版本上的开始/结论状态变更使用 revision/CAS、幂等键和唯一结果约束；并发冲突只能一个成功，失败方得到冲突响应并重新读取权威结果，不得后写覆盖先写。

三种审核结论动作必须区分：

- **通过**：对审核中的当前提交版本形成通过结论；同一事务创建正式赛事、登记申请机构的承办关系、保存来源追溯并更新申请状态。不得只改状态后异步补建赛事。
- **驳回**：对审核中的当前提交版本形成明确不通过结论和原因，不创建赛事，并终止当前申请。驳回后该 applicationId 永久只读，不得保存草稿、恢复编辑或重交；承办方可另建具有新 applicationId、从 V1 开始的新申请。两份申请各自保留完整表单、附件、版本和审核历史，不覆盖或删除原申请。
- **要求补充材料**：对审核中的当前提交版本保存具体补充要求；这不是驳回，也不创建赛事。承办方可在同一 applicationId 中修改原申请并重交，形成 Vn+1；被要求补充的版本保持不可变，补充要求及新旧版本历史完整保留。

申请方撤回、总部撤销错误操作、处理时限和通知仍未确认，不加入首期状态。

## 5. 获批结果与追溯

获批事务完成后应能回答：

- 该正式赛事由哪个申请产生；
- 总部批准的是 V1、V2 中的哪一个提交版本；
- 当时获批的赛事名称、时间、地点和资料要求/附件是什么；
- 申请机构为何成为该赛事的承办机构；
- 谁提交、谁审核、何时发生、审核意见是什么。

正式赛事保存稳定的申请来源关系，获批申请版本保存完整快照。后续即使赛事信息通过另一个已批准的变更流程更新，也不得改写最初获批版本。现有总部直接创建或历史赛事不伪造申请来源。

## 6. 承办关系与访问授权

获批时登记的是赛事与申请机构之间的业务关系，建议称 `EventOrganizerAppointment`。它与以下对象分开：

- `EventGrant`：某组织成员能否访问赛事的安全授权；继续只表示授权，不表示承办事实；
- `EventOrganizerAgent`：获批后代表承办机构处理赛事的人员关系，人数和职责待确认；
- `TaskScope`：某一个办赛材料任务当前由哪个机构/人员办理；
- 申请提交人：某一版本的实际提交 actor。

获批事务不得因为申请人存在就默认创建“唯一经办人”。是否给申请人或其他人员创建 `EventGrant`、授予什么能力、由谁确认，必须在实施前明确。业务承办关系即使暂未配置人员授权也应保持为事实记录，不能用 grant 的有无反推承办关系。

## 7. 页面和入口调整

### 7.1 总部 Web

建议新增独立“赛事承办申请”入口，与现有“赛事管理”和“资料审核”分开：

- 申请列表：按状态、申请机构、提交时间查询；权限和可见范围由后端限定；
- 申请详情：显示申请表、资料要求完成情况、不可变 V1/V2、附件、提交人/时间及审核历史；
- 审核区：展示待审核/审核中；提供明确“开始审核”操作，再对审核中的当前版本提供“通过”“驳回”“要求补充材料”，展示各自动作后果并二次确认；开始不独占，页面显示每步实际操作人/时间/版本；打开详情本身不改变状态；
- 通过成功后展示唯一正式赛事链接和承办机构关系，不重复提供创建按钮；
- 赛事详情新增“来源”区域：有申请来源时链接到获批版本；历史/总部直接创建赛事明确显示无申请来源，不伪造数据；
- 承办机构关系和人员访问授权分区展示，禁止把 `ORGANIZER EventGrant` 标成“承办方”。

### 7.2 承办方小程序

“赛事承办申请”是赛事创建前流程，不依赖当前赛事选择器：

- 在主页业务板块提供独立入口；未拥有任何赛事的合格申请人仍应能进入（具体资格待确认）；
- 页面包括同机构共享申请列表、创建/编辑草稿、申请表、资料上传、提交确认、状态详情、补充要求与版本历史；不按创建人过滤，有办理权限的有效经办人可接续；
- 待审核只读；待补充时在同一原申请中从已处理版本形成可编辑草稿，重交生成下一版本；已驳回申请只读且不提供恢复编辑/重交，允许从申请列表另建新申请；
- 已通过展示正式赛事结果。是否可立即进入赛事及材料页面取决于后续经办授权和材料任务规则，不能仅凭申请人身份放行。

现有主页赛事上下文、材料提交、审核进度和私有附件流程保持不变；新入口不得把未获批申请注入赛事选择列表。

## 8. 兼容与数据保留

1. 后续只允许追加模型和迁移，不修改已执行历史迁移。
2. 现有 `Event`、`EventScope`、`EventGrant`、`MaterialTask`、`TaskScope`、材料、附件、提交版本、审核动作和审计记录原样保留。
3. 不从现有任务指派或 `ORGANIZER EventGrant` 反推、批量回填赛事承办关系。
4. 现有赛事不补造申请、提交人或批准版本；来源保持“历史/总部直接创建”或空来源的兼容表达。
5. 新申请附件与现有办赛材料附件分属不同业务归属，不能复用附件 ID 绕过授权；底层私有存储能力可复用。
6. 申请获批不改写既有赛事或任务；创建的是一个新正式赛事。未通过、补充中和事务失败均不得留下孤立 Event/EventScope/承办关系。
7. 后续数据库验收必须对迁移前后旧表摘要、历史迁移 checksum、私有文件 hash 和旧流程权限做保留验证。

## 9. 验收口径（后续实现阶段）

- 同机构两名有申请办理权限的有效经办人均可查看同一申请：甲创建/保存后乙可继续编辑并作为实际提交人提交 V1；要求补充后甲或乙可提交 V2。每个创建、保存、附件和提交动作显示其实际人/时间/revision，不能统一显示创建人。
- 两人基于同一 draft revision 并发保存时只能一个成功，另一方收到冲突且其本地输入不被成功方静默覆盖；刷新权威草稿后才可显式重试。跨机构列表/深链/文件/写操作均拒绝，同机构无办理权限或已停用/撤权者同样拒绝。
- V1 提交必须校验营业执照、简介（办赛经验）和现场照片均已提供；其他文档允许为空。提交后版本及附件关系不可修改；要求补充后只编辑当前补充草稿并在同一 applicationId 提交 V2，完整保留 V1、附件摘要、实际提交人、补充要求和审核意见。
- 待审核申请进入详情后仍为待审核；有权审核员明确执行“开始审核”才进入审核中并记录实际人员、服务器时间和目标版本，重复/并发开始受幂等和冲突保护；开始人不获得独占权，另一有权审核员可以接续形成结论并记录自己的身份。
- 两名有权审核员对同一版本并发执行通过/驳回/要求补充等冲突动作时只能一个成功，最终状态和结果不得被覆盖；通过请求重复点击或响应丢失重试时至多创建一个 Event、一条来源关系和一条有效承办关系，事务失败时全部不创建。
- 独立权限矩阵验证：申请审核权限不依赖 `EventGrant`；仅有赛事 grant 者不能审核申请，有申请审核权限但无赛事 grant 者可共享查看/处理；提交过该申请任一版本的本人即使具有申请审核权限也不能开始或形成结论。
- 驳回和要求补充均不创建 Event，且历史中动作语义不同：待补充可在原申请生成 Vn+1；驳回后原申请所有编辑/重交命令均被后端拒绝，但可新建独立申请，原申请及审核历史仍可按权限只读查询。
- 正式赛事可追溯到唯一获批申请版本；历史/直接创建赛事仍可正常访问且不伪造来源。
- `EventOrganizerAppointment` 与 `EventGrant` 分开验证：有承办关系不等于已有人员授权，有 grant 不等于承办机构。
- 现有材料任务、附件、不可变版本和审核历史在升级、重启及新页面接入后保持可读和原权限行为。
- Web 与小程序分别验证空态、加载、失败、无权、重复操作和版本历史；小程序构建、开发者工具和真机证据分别记录。

## 10. 实施前必须确认的规则

1. **申请审核权限管理**：审核使用独立权限且有权总部审核员共享接续已确定；仍需确认由谁授予/撤销该权限，以及总部人员停用时的管理流程。
2. **申请办理权限管理**：同机构有办理权限的有效经办人共享查看/编辑/提交及补充版本已确定；仍需确认由谁授予/撤销办理权限，以及成员停用时的管理操作。
3. **获批后的经办授权**：经办人数、指定人、角色、何时创建/撤销 `EventGrant`，申请人是否仅作为候选而非默认经办人。
4. **何时创建办赛材料任务**：获批事务内、总部后续手工创建，还是满足其他条件后创建；任务名称、截止、经办人、要求来源均未确认。确认前获批事务不创建任务。
5. **申请资料细化口径**：营业执照、简介（办赛经验）、现场照片已确定为必交，其他文档已确定为选交；仍需确认各项格式、大小、数量、特殊情况处理、配置者和版本生效规则。
6. **时间和地点结构**：时区、起止、多赛段、场馆和地址字段及校验规则。
7. **补充材料细化规则**：已确定在同一原申请修改并重交形成新版本；仍需确认可修改字段范围、总部补充要求是否必填、补充次数和截止时间。
8. **驳回/补充意见**：是否必填、最小内容、附件或结构化问题项要求。
9. **申请方撤回与作废**：提交后能否撤回，获批前谁可作废，错误批准如何处理。
10. **多人会签**：显式开始审核、不独占领取、其他有权审核员可接续及同版本冲突只能一个成功已确定；是否另需多人会签/复核属于尚未提出的扩展，不纳入首期默认流程。打开详情不得自动开始审核。
11. **赛事承办基数**：一个赛事是否只能有一家承办机构，是否存在主办/承办/协办类型和有效期。
12. **获批后赛事生命周期**：正式赛事初始状态、发布时间、是否立即对其他角色可见。
13. **后续信息变更**：获批申请快照如何与未来赛事信息变更申请衔接，不在本流程内提前决定。
14. **通知**：提交、补充、驳回、通过是否需要站内/微信通知，收件人和失败重试规则。
