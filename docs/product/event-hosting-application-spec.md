# 赛事承办申请产品规格

状态：CAAU-027 待确认设计；本轮只交付规格、技术设计和计划，不代表业务功能已实现。

本文定义“赛事承办申请”作为正式赛事创建前的独立流程。已确认规则与待确认事项严格分开；文中的数据结构和页面名称是后续实现建议，不自动成为业务规则。

## 1. 目标与边界

### 1.1 已确认目标

1. 承办方自行填写赛事名称、开始日期、结束日期、赛事地点，提出新的办赛申请。
2. 总部审核通过后，系统自动创建正式赛事，并将申请机构登记为该赛事的承办方。
3. 未通过的申请不创建正式赛事。
4. 申请人是本次提交人，不默认限定为该赛事唯一经办人。
5. 原有办赛材料提交与审核完整保留，作为申请获批后的后续流程。
6. 申请资料要求为：必交“营业执照”“简介（办赛经验）”“现场照片”，选交“其他文档”。
7. 申请审核必须包含“审核中”状态；有权审核员明确点击“开始审核”后进入，打开详情不触发状态变化。
8. 要求补充材料后，承办方可在同一原申请中修改并重交，形成新的不可变提交版本，旧版本及审核历史完整保留。
9. 驳回是当前申请的终止状态；该申请不得恢复编辑或重交。承办方可以另建新申请，原申请及审核历史完整保留。
10. 申请审核使用独立权限，不依赖正式赛事 `EventGrant`；有权总部审核员共享查看和处理申请。
11. 审核员必须明确点击“开始审核”进入审核中，该动作不产生独占领取；其他有权审核员可以接续处理。
12. 每个审核状态变更记录实际操作人、服务器时间和目标提交版本；禁止审核本人提交过任一版本的申请，同一版本的冲突审核只能一个成功且不能覆盖既有结果。
13. 同一申请机构内，具有申请办理权限的有效经办人可共同查看、编辑、提交申请及补充版本，不限定创建人；每次操作保留实际操作人和历史，使用并发控制防止多人编辑覆盖，禁止跨机构访问，已提交版本不可修改。
14. 申请通过时，申请机构内当时具有申请办理权限且有效的经办人，自动获得新赛事基本信息查看权限。
15. 自动查看权限不包含赛事修改、申请/赛事审核或任何材料任务办理能力；不得复用会附带这些能力的宽泛角色或授权。
16. 机构承办关系与人员查看授权分别记录；前者是赛事与机构的业务事实，后者是具体人员的最小访问能力。
17. 获批时不自动创建材料任务；总部后续按现有任务流程创建任务、指定办理人并沿用现有任务权限规则。
18. 首版申请表固定为赛事名称、开始日期、结束日期和赛事地点；地点必须保留“省市区、详细地址、场馆名称”三个部分，不能简化为一个自由文本框。正式提交时上述字段、地点各部分及办赛经验简介均必填，结束日期不得早于开始日期；草稿可暂时不完整。
19. `NEEDS_SUPPLEMENT` 下，有权经办人可修改赛事名称、开始/结束日期、地点三个部分、办赛经验简介及附件；申请机构不可变。保存仍是可变草稿，重交生成 Vn+1 并重新校验全部必交字段和资料。
20. 旧提交版本、附件关系、总部补充意见及操作历史不可变保留；总部可查看相邻提交版本的字段变化和按资料项归类的附件新增、移除、替换情况。
21. 新增独立“总部超级管理员”：可管理账号、机构、权限、全部赛事及任务，并查看/审核全部承办申请、附件和历史及指派人员；仍受禁止自审、不可变历史和业务状态机约束，所有操作留痕。普通 `SYSTEM_ADMIN` 不自动获得业务权限；首个超级管理员仅由受控本地初始化准备，HTTP 接口不得创建该角色，生产初始化另行处理。
22. 批准时至少存在一名有效申请经办人。新增有效经办人同步取得本机构既有获批赛事基本信息查看权；撤销办理权时撤销该来源查看权，恢复有效办理资格时恢复；用户或成员停用由逐请求 active 校验立即拒绝，恢复后恢复该来源访问，其他独立授权不受影响。
23. 获批赛事创建为内部“筹备中”，不自动公开发布；普通总部赛事管理员必须取得明确赛事授权后才能接管。申请审核权不派生赛事管理权，获批不自动创建资料任务。

### 1.2 本流程不等于

- 申请不是正式赛事；申请处于待审、补充材料或驳回状态时均不得出现在正式赛事列表中。
- 申请机构是获批后的承办机构业务事实，不等于向某个人授予赛事访问权。
- 申请人是提交动作的实际人员，不自动成为唯一经办人、主经办人或材料任务经办人。
- 赛事承办申请资料不是现有办赛材料任务；获批明确不自动创建 `MaterialTask`，也不授予任何任务办理能力。
- 本规格不处理赛事获批后的信息变更申请、报名、支付、俱乐部通知或外部报名系统同步。

## 2. 角色与数据范围

| 参与方 | 已确认能力 | 尚未确认 |
| --- | --- | --- |
| 承办方申请经办人 | 同一申请机构内具有申请办理权限且当前有效的经办人，共享查看、编辑、提交申请及补充版本；每步记录实际人员，不限定创建人 | 办理权限由谁授予/撤销及成员停用管理流程 |
| 总部审核方 | 通过独立承办申请审核权限共享查看和处理申请；显式开始但不独占，其他有权审核员可接续；禁止审核本人提交过任一版本的申请 | 无 |
| 总部超级管理员 | 管理账号、机构、权限、全部赛事/任务；查看和处理全部申请/附件/历史并指派人员；所有动作审计 | 生产首个账号初始化不在本阶段 |
| 普通 `SYSTEM_ADMIN` | 继续管理现有系统账号/机构能力 | 不自动获得申请、赛事或任务业务权限 |
| 申请机构 | 获批后登记为正式赛事的承办方 | 一个赛事是否允许多家承办/协办机构及关系类型 |
| 获批时有效申请经办人 | 自动取得新赛事基本信息查看权；不能修改赛事、审核或办理材料任务 | 后续新增、撤权、停用时是否自动联动见第 6.1 节建议，尚未确认为业务规则 |

所有读写必须由后端按当前会话、组织成员关系和权限判定；前端传入 organizationId、applicationId 或 eventId 不能作为授权依据。申请方必须同时满足 active user、active 同机构成员和有效申请办理权限；创建人不获得绕过停用/撤权的永久权限，同机构无办理权限者及任何跨机构成员均不得列表、查看、编辑、上传、提交或下载。承办申请审核权限独立于正式赛事授权：有 `EventGrant` 但没有申请审核权限者不得查看/处理申请；有申请审核权限者无需等待申请获批或取得 `EventGrant` 即可进入共享申请队列。

## 3. 申请表与资料

### 3.1 已确认申请字段

首版申请表及不可变提交快照固定保存以下业务字段，不增加联系人、联系电话、预算、规模等未确认字段：

| 字段 | 首版表达 | 提交规则 |
| --- | --- | --- |
| 赛事名称 | `eventName` 文本 | 必填 |
| 开始日期 | `startDate`，ISO 8601 日历日期 `YYYY-MM-DD` | 必填且必须是真实日期 |
| 结束日期 | `endDate`，ISO 8601 日历日期 `YYYY-MM-DD` | 必填且必须是真实日期；不得早于开始日期，等于开始日期表示单日赛事 |
| 赛事地点 | `location` 对象，包含 `administrativeArea`（省、市、区县）、`detailedAddress`（详细地址）、`venueName`（场馆名称） | 省、市、详细地址、场馆名称必填；按实际层级允许区县为空，不能折叠成单一自由文本；一份申请填写一个主要场地 |
| 办赛经验简介 | `eventExperienceIntroduction` 文本，作为必交“简介（办赛经验）”资料项的内容 | 必填；不额外要求上传简介文件 |

草稿保存允许字段或地点子字段暂时为空，以支持逐步填写；只要开始、结束日期同时存在，就必须校验 `endDate >= startDate`。正式提交时由后端再次校验赛事名称、开始/结束日期、省/市、详细地址、场馆名称、办赛经验简介及日期顺序；区县按实际行政层级可空。一份申请只填写一个主要场地。首版不开放港澳台及海外，不包含时分、时区、多赛段、经纬度或其它地址字段。

### 3.2 必交与选交资料的表达

已提出的申请资料要求如下，不再把整个清单标记为未确认：

| 属性 | 资料项 |
| --- | --- |
| 必交 | 营业执照 |
| 必交 | 简介（办赛经验） |
| 必交 | 现场照片 |
| 选交 | 其他文档 |

后续模型应将上述清单保存为可追溯的“申请资料要求版本”：

- 每个要求项有稳定 ID、名称、说明和`必交/选交`标记；不得擅自增加“场馆证明”等未提出项目；
- 三项必交资料在提交时由后端重新校验：营业执照和现场照片必须各有有效附件，简介（办赛经验）必须有非空文本内容；“其他文档”允许为空。不得把简介擅自改为必须上传文件；
- 要求版本在申请提交时形成快照或引用不可变版本，防止后续规则变化改写既有提交含义；
- 营业执照必须恰好 1 个 PDF/JPG/PNG；现场照片必须 1～10 张 JPG/PNG，可提交场地现状照片；其他文档选交且最多 5 个 PDF/JPG/PNG；每个文件不超过 10 MB；
- 缺少任何必交字段或资料只能保存草稿，不能提交；一份申请只表达一个主要场地；
- 首版使用固定、可追溯的 requirement snapshot，补充版本重新按当前已确认清单全量校验；未来由谁配置/发布新要求版本及生效策略排除出第一批，不改变首版四项及其必交/选交属性。

#### 首版文件规则

| 资料项 | 正式格式 | 正式数量 | 单文件上限 |
| --- | --- | --- | --- |
| 营业执照（必交） | PDF、PNG、JPG/JPEG | 恰好 1 个 | 10 MB |
| 现场照片（必交） | PNG、JPG/JPEG | 1～10 个 | 10 MB |
| 其他文档（选交） | PDF、PNG、JPG/JPEG | 0～5 个 | 10 MB |

上传继续校验真实字节、格式特征、大小和 SHA-256；办赛经验简介是必填文本，不要求文件。场地尚未正式布置时可提交场地现状照片；营业执照和现场照片不能以“稍后补充”为由绕过提交校验。首版不支持 TXT、Office、压缩包、病毒扫描或生产对象存储，这些技术边界不新增业务资料项。

### 3.3 草稿、提交版本与附件

建议采用“可变草稿 + 不可变提交版本”：

1. `Application` 是申请身份和当前状态；保存申请机构、草稿修订号及当前提交版本指针。
2. 草稿保存当前表单值、资料条目和已确认附件引用。所有有权同机构经办人按同一权威 draft revision 协作：保存、附件绑定/移除和提交必须携带 expected revision；过期 revision 返回冲突和最新 revision，不自动合并或覆盖另一人的成功修改。
3. 每次正式提交生成不可变 `ApplicationSubmission`（V1、V2……），冻结：申请表完整快照、资料要求版本/快照、每项资料元数据、附件关系、申请机构、实际提交人和服务器时间。
4. 附件使用私有对象存储；上传意图、字节校验、确认、草稿绑定、提交版本绑定分开。提交版本绑定后不得替换或删除；新版本需要形成新的附件关系，旧版本字节和摘要保留。
5. “要求补充材料”后，系统在同一 applicationId 下从最近提交版本形成补充草稿；任一当前有权同机构经办人可修改赛事名称、开始/结束日期、地点三个部分、办赛经验简介，以及绑定/移除/替换草稿附件。申请机构、applicationId、既有 submission 及其附件关系不可修改。
6. 补充修改先按 revision/CAS 保存为可变草稿；重交时重新校验全部必交字段、地点子字段、日期顺序和三项必交资料，而不是只校验本次变化。成功后生成 Vn+1、回到 `PENDING_REVIEW`，不覆盖 Vn。
7. Vn+1 保留总部对 Vn 的补充意见及全部旧版本、附件和动作。总部详情可比较 Vn 与 Vn+1：字段逐项显示旧值/新值，附件按资料项显示新增、移除和替换；差异来自不可变快照，不能由客户端提交差异结果。
8. 草稿创建、保存、附件操作、首次提交和补充重交都记录实际 actorId、服务器时间、前后 revision/目标版本及必要的不可变操作历史；不能把创建人回填为他人的操作人。
9. 审核动作必须指向明确 submissionId；总部看到和裁决的是某一不可变版本，而不是仍可变化的草稿。

申请的 createdBy 只记录创建动作，不是办理权限或唯一责任人。每次提交版本分别记录实际 submittedBy；同机构其他有权有效经办人可以提交 V1 或补充版本。提交形成版本后，任何申请方成员都不能修改该版本快照、附件关系、提交人或时间，只能在允许编辑的当前草稿中形成下一版本。

## 4. 状态和操作语义

状态集合必须包含“审核中”；英文枚举是技术设计名称，中文文案可在页面实现前确认：

| 状态 | 含义 | 允许的下一步 | 是否创建赛事 |
| --- | --- | --- | --- |
| 草稿 `DRAFT` | 尚未正式提交，或正在准备首次版本 | 提交 | 否 |
| 待审核 `PENDING_REVIEW` | 当前不可变版本已提交，等待总部开始处理 | 有权审核员明确点击“开始审核”进入审核中 | 否 |
| 审核中 `IN_REVIEW` | 总部已开始处理当前提交版本，但尚未形成结论 | 通过、驳回、要求补充材料 | 否 |
| 待补充 `NEEDS_SUPPLEMENT` | 总部未作通过结论，要求申请方在原申请中修改 | 编辑同一申请并重交，形成 Vn+1 后回到待审核 | 否 |
| 已驳回 `REJECTED` | 总部明确终止当前申请 | 只读保留；不得恢复编辑或重交，可另建新申请 | 否 |
| 已通过 `APPROVED` | 总部通过指定提交版本，正式赛事及承办关系已原子创建 | 不再对同一申请重复裁决 | 是，且只能一个 |

“审核中”及其进入方式均已确认：有权审核员必须明确点击“开始审核”才从待审核进入审核中。打开申请详情仅为只读查看，绝不自动进入审核中，也不生成开始审核动作。“开始审核”只记录实际开始人、服务器时间和目标提交版本，不产生 owner、领取锁或排他权；其他有权总部审核员可接续执行通过、驳回或要求补充材料，结论人可以与开始人不同。

每个开始审核和审核结论动作都必须指向明确 submissionId，并记录实际 actorId、服务器时间和版本。当前操作人若是该申请任一提交版本的 submittedBy，后端必须拒绝开始审核及任何审核结论，不能仅由前端隐藏按钮。同一版本上的开始/结论状态变更使用 revision/CAS、幂等键和唯一结果约束；并发冲突只能一个成功，失败方得到冲突响应并重新读取权威结果，不得后写覆盖先写。

三种审核结论动作必须区分：

- **通过**：对审核中的当前提交版本形成通过结论；同一事务创建正式赛事、登记申请机构的承办关系、保存来源追溯并更新申请状态。不得只改状态后异步补建赛事。
- **驳回**：对审核中的当前提交版本形成明确不通过结论和原因，不创建赛事，并终止当前申请。驳回后该 applicationId 永久只读，不得保存草稿、恢复编辑或重交；承办方可另建具有新 applicationId、从 V1 开始的新申请。两份申请各自保留完整表单、附件、版本和审核历史，不覆盖或删除原申请。
- **要求补充材料**：对审核中的当前提交版本保存具体补充要求；这不是驳回，也不创建赛事。承办方可在同一 applicationId 中修改已确认范围并保存草稿，重交形成 Vn+1、回到待审核；申请机构不可变，全部必交字段和资料重新校验。被要求补充的版本、附件、补充意见及操作历史完整保留。

申请方撤回、总部撤销错误操作、处理时限和通知仍未确认，不加入首期状态。

## 5. 获批结果与追溯

获批事务完成后应能回答：

- 该正式赛事由哪个申请产生；
- 总部批准的是 V1、V2 中的哪一个提交版本；
- 当时获批的赛事名称、开始日期、结束日期、赛事地点和资料要求/附件是什么；
- 申请机构为何成为该赛事的承办机构；
- 谁提交、谁审核、何时发生、审核意见是什么。

正式赛事保存稳定的申请来源关系，获批申请版本保存完整快照。后续即使赛事信息通过另一个已批准的变更流程更新，也不得改写最初获批版本。现有总部直接创建或历史赛事不伪造申请来源。

## 6. 承办关系与访问授权

获批时登记的是赛事与申请机构之间的业务关系，建议称 `EventOrganizerAppointment`。它与以下对象分开：

- `EventInformationAccessGrant(EVENT_BASIC_INFO_VIEW)`：获批时逐人创建的最小赛事基本信息只读授权，不包含修改、审核或材料任务能力；
- `EventGrant`：现有赛事授权；可能与成员角色共同带来更宽能力，不用于本次自动基本信息查看，也不表示承办事实；
- `EventOrganizerAgent`：获批后代表承办机构处理赛事的人员关系，人数和职责待确认；
- `TaskScope`：某一个办赛材料任务当前由哪个机构/人员办理；
- 申请提交人：某一版本的实际提交 actor。

获批事务按申请机构在批准事务中的权威成员/办理权限状态，为所有“有效成员 + 有效申请办理权限”的经办人创建独立、细粒度的赛事基本信息查看授权，建议能力码为 `EVENT_BASIC_INFO_VIEW`。该授权只允许读取赛事 ID、名称、开始日期、结束日期、地点等正式基本信息及必要来源标识；不得用于赛事修改、申请/赛事审核、材料任务列表/详情、附件下载或任务写操作。

当前 `EventGrant` 与成员角色参与既有赛事/任务策略，可能携带超出“只看基本信息”的能力，因此自动查看权不得通过赋予 `ORGANIZER`、`EVENT_MANAGER`、`REVIEWER` 等宽泛角色或复用宽泛 `EventGrant` 实现。后续模型应使用独立的人员访问授权，例如 `EventInformationAccessGrant(capability=EVENT_BASIC_INFO_VIEW)`，并保存 memberId、eventId、来源 handler grant/申请/提交版本、授予时间和状态。

`EventOrganizerAppointment` 继续独立记录“申请机构是赛事承办方”的业务事实；人员查看授权逐人记录。撤销某个人员访问、成员停用或人员变化不能删除/改写机构承办关系。反过来，存在机构承办关系也不能绕过人员授权直接放行。

获批事务不创建 `MaterialTask`、`TaskScope` 或任务办理授权。总部后续通过现有任务创建流程选择任务办理机构/人员，沿用现有任务权限、截止、历史和附件规则；拥有 `EVENT_BASIC_INFO_VIEW` 的人员若未被任务明确指派，不能看到或办理该任务。

### 6.1 人员变化规则

- **新增或恢复申请经办权限**：自动补齐/恢复该机构全部已获批赛事由此 handler grant 派生的基本信息查看权；
- **撤销申请办理权限**：同一事务停用由该 handler grant 派生的查看权，只处理该来源，不撤销 EventGrant 或其它独立来源；
- **用户或机构成员停用/恢复**：访问策略逐请求检查 active，停用立即失权；恢复且 handler grant 仍有效时，该来源查看权恢复；
- **机构承办关系与任务**：人员变化不修改 `EventOrganizerAppointment`，不创建、转移或关闭任何任务。

上述动作均由总部超级管理员管理并完整审计。

## 7. 页面和入口调整

### 7.1 总部 Web

建议新增独立“赛事承办申请”入口，与现有“赛事管理”和“资料审核”分开：

- 申请列表：按状态、申请机构、提交时间查询；权限和可见范围由后端限定；
- 申请详情：显示申请表、资料要求完成情况、不可变 V1/V2、附件、提交人/时间及审核历史；对相邻提交版本展示字段旧值/新值及按资料项归类的附件新增、移除、替换；
- 审核区：展示待审核/审核中；提供明确“开始审核”操作，再对审核中的当前版本提供“通过”“驳回”“要求补充材料”，展示各自动作后果并二次确认；开始不独占，页面显示每步实际操作人/时间/版本；打开详情本身不改变状态；
- 通过成功后展示唯一正式赛事链接和承办机构关系，不重复提供创建按钮；
- 赛事详情新增“来源”区域：有申请来源时链接到获批版本；历史/总部直接创建赛事明确显示无申请来源，不伪造数据；
- 承办机构关系和人员基本信息查看授权分区展示，禁止把宽泛 `EventGrant` 标成“承办方”或用其代替最小查看权。

### 7.2 承办方小程序

“赛事承办申请”是赛事创建前流程，不依赖当前赛事选择器：

- 在主页业务板块提供独立入口；未拥有任何赛事的合格申请人仍应能进入（具体资格待确认）；
- 页面包括同机构共享申请列表、创建/编辑草稿、申请表、资料上传、提交确认、状态详情、补充要求与版本历史；不按创建人过滤，有办理权限的有效经办人可接续；
- 待审核只读；待补充时在同一原申请中从已处理版本形成可编辑草稿，只开放赛事名称、开始/结束日期、地点三个部分、办赛经验简介及附件，申请机构只读；重交生成下一版本并重新校验全部必交内容；已驳回申请只读且不提供恢复编辑/重交，允许从申请列表另建新申请；
- 已通过后，当时有效且有申请办理权限的同机构经办人可进入正式赛事基本信息只读页；页面不显示赛事编辑、审核或材料任务办理入口。后续只有总部创建材料任务并明确指派后，相关人员才按现有任务权限进入材料流程。

现有主页赛事上下文、材料提交、审核进度和私有附件流程保持不变；新入口不得把未获批申请注入赛事选择列表。

## 8. 兼容与数据保留

1. 后续只允许追加模型和迁移，不修改已执行历史迁移。
2. 现有 `Event`、`EventScope`、`EventGrant`、`MaterialTask`、`TaskScope`、材料、附件、提交版本、审核动作和审计记录原样保留。
3. 不从现有任务指派或 `ORGANIZER EventGrant` 反推、批量回填赛事承办关系。
4. 现有赛事不补造申请、提交人或批准版本；来源保持“历史/总部直接创建”或空来源的兼容表达。
5. 新申请附件与现有办赛材料附件分属不同业务归属，不能复用附件 ID 绕过授权；底层私有存储能力可复用。
6. 申请获批不改写既有赛事或任务；创建的是一个新正式赛事。未通过、补充中和事务失败均不得留下孤立 Event/EventScope/承办关系。
7. 后续数据库验收必须对迁移前后旧表摘要、历史迁移 checksum、私有文件 hash 和旧流程权限做保留验证。

## 9. 验收口径（后续实现阶段）

- 同机构两名有申请办理权限的有效经办人均可查看同一申请：甲创建/保存后乙可继续编辑并作为实际提交人提交 V1；要求补充后甲或乙可提交 V2。每个创建、保存、附件和提交动作显示其实际人/时间/revision，不能统一显示创建人。
- 两人基于同一 draft revision 并发保存时只能一个成功，另一方收到冲突且其本地输入不被成功方静默覆盖；刷新权威草稿后才可显式重试。跨机构列表/深链/文件/写操作均拒绝，同机构无办理权限或已停用/撤权者同样拒绝。
- 草稿允许已确认字段暂时未填完整；日期逆序必须拒绝。V1/V2 提交必须校验赛事名称、日期、省/市、详细地址、场馆名称及办赛经验简介；区县允许为空，且只保存一个主要场地。首版省份必须属于中国大陆范围，港澳台及海外拒绝。
- V1/V2 必须校验营业执照恰好 1 个、现场照片 1～10 个、其他文档不超过 5 个，格式和 10 MB 上限符合规则；其他文档允许为空。提交后版本及附件关系不可修改；补充重交重新校验全部必交内容并完整保留历史。
- 总部相邻版本差异验证：赛事名称、日期、地点各部分和办赛经验简介分别显示 unchanged/changed 及旧值/新值；营业执照、现场照片、其他文档按资料项显示附件 added/removed/replaced，文件安全展示名、大小和 hash 摘要来自两份不可变快照，不暴露 storageKey。没有变化的项不得伪造变化；跨 application 拒绝，首版不接受客户端任选 from/to，也不能跨 submission 偷绑附件。
- 待审核申请进入详情后仍为待审核；有权审核员明确执行“开始审核”才进入审核中并记录实际人员、服务器时间和目标版本，重复/并发开始受幂等和冲突保护；开始人不获得独占权，另一有权审核员可以接续形成结论并记录自己的身份。
- 两名有权审核员对同一版本并发执行通过/驳回/要求补充等冲突动作时只能一个成功，最终状态和结果不得被覆盖；通过请求重复点击或响应丢失重试时至多创建一个 Event、一条来源关系和一条有效承办关系，事务失败时全部不创建。
- 独立权限矩阵验证：申请审核权限不依赖 `EventGrant`；仅有赛事 grant 者不能审核申请，有申请审核权限但无赛事 grant 者可共享查看/处理；提交过该申请任一版本的本人即使具有申请审核权限也不能开始或形成结论。
- 驳回和要求补充均不创建 Event，且历史中动作语义不同：待补充可在原申请生成 Vn+1；驳回后原申请所有编辑/重交命令均被后端拒绝，但可新建独立申请，原申请及审核历史仍可按权限只读查询。
- 正式赛事可追溯到唯一获批申请版本；历史/直接创建赛事仍可正常访问且不伪造来源。
- `EventOrganizerAppointment` 与人员 `EVENT_BASIC_INFO_VIEW` 授权分开验证：机构关系不直接放行个人，人员授权也不等于机构关系；批准时两者与赛事创建同事务成功或全部回滚。
- 批准时两名有效申请经办人都获得同一新赛事基本信息只读权，跨机构经办人拒绝；两人均不能 PATCH 赛事、执行申请/赛事审核、读取未指派材料任务或下载其附件。总部随后创建任务并只指派其中一人时，仅被指派人按现有任务规则办理，另一人仍只能看赛事基本信息。
- 现有材料任务、附件、不可变版本和审核历史在升级、重启及新页面接入后保持可读和原权限行为。
- Web 与小程序分别验证空态、加载、失败、无权、重复操作和版本历史；小程序构建、开发者工具和真机证据分别记录。

## 10. 第一批后端开发决策收口

剩余业务规则已全部确认，B 阶段不再存在业务阻塞。实现必须按本规格一次性落实以下规则：

- 总部超级管理员是独立、受控初始化角色；普通 `SYSTEM_ADMIN` 不获得业务权限；
- 超级管理员管理两类申请权限及普通赛事管理员的明确赛事授权，人员停用继续由账号/成员 active 状态即时生效；
- 批准要求至少一名有效经办人；新增/撤销/恢复办理权同步对应来源的基本查看权，独立授权不受影响；
- 地域仅中国大陆，省/市必填、区县按实际层级可空，单一主要场地；
- 文件格式、数量、10 MB 上限及场地现状照片规则按第 3.2 节执行；
- 补充要求和驳回原因必填；补充次数不限且无期限，不自动逾期驳回；
- 获批赛事为内部“筹备中”，不自动发布；申请审核权不派生赛事管理权，不自动创建资料任务。

### 10.1 可由开发确定的技术细节

在不改变已确认业务语义的前提下，开发可直接决定并在 ADR/代码评审中记录：

- Nest DTO/class、Prisma 表/列/索引的最终命名，以及草稿 JSON 与投影列的物理组织；
- 严格日历日期解析器、跨字段 validator、字段级错误码和 OpenAPI 表达；
- revision CAS、Serializable/行锁、幂等键、不可变触发器和事务重试的实现细节；
- 相邻版本差异是请求时从不可变快照计算还是保存可重建投影，以及附件 added/removed/replaced 的算法；
- 分页、排序、缓存、日志字段、审计上下文和不泄露对象存在性的错误响应细节；
- 私有存储 key、hash/格式特征检测、上传超时和基础设施硬上限。技术安全上限必须与业务 requirement 分层，不得自行变成正式文件规则；
- 在业务确认地域范围后，行政区标准数据集、版本固定、代码/名称快照和升级策略。

### 10.2 已排除出第一批

- 总部后续材料任务的名称、截止和人员配置：获批不自动建任务已经确认，后续继续走现有任务流程；
- 申请方撤回/作废、错误批准撤销、额外多人会签、通知，以及未来申请资料要求的自助配置/发布；
- 一场赛事多家主办/承办/协办关系、后续赛事信息变更；
- 时分、时区、多赛段、经纬度和更细地址扩展。

这些能力不在首版 API 中出现；“暂不实现”不等于为其定义相反业务规则。

### 10.3 已确认，不再重复询问

- 首版字段及地点三部分、日期顺序、办赛经验简介；三项必交资料与选交其他文档；
- 同机构有权经办人共享办理、实际人员留痕、CAS、防跨机构和提交版本不可变；
- 待补充可改范围、申请机构不可变、草稿保存、Vn+1 回待审核、全部必交内容重验及相邻版本差异；
- 显式开始审核但不独占、共享接续、禁止自审、并发唯一结果；补充与驳回语义；
- 获批原子创建赛事/来源/机构关系和最小基本信息查看权，不复用宽泛角色，不自动创建材料任务。
