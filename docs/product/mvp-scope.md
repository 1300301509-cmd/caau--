## 1. 两端分工建议

依据：原型交互复杂度、共享业务对象与当前分层规划（[module-map.md](../architecture/module-map.md)）；以下各行均为工程/产品建议，非已确认首版需求。Web 是授权管理与复杂操作入口，小程序是移动办理入口，两端共享 API，不共享数据库客户端或强行共享 UI。

| 板块 | 小程序建议 | Web 后台建议 | 首闭环范围 |
| --- | --- | --- | --- |
| 经营总览 | 我的赛事、待办、审核结果，不搬全经营驾驶舱 | 授权赛事进度与逾期待办；完整经营指标后续 | 仅任务进度摘要，不用原型静态业绩 |
| 财务中心 | 后续按需查看本人/机构授权结算摘要 | 预算版本、实际、对账与审批，先确认口径 | 不进入 |
| 运营中心 | 当前赛事信息、任务要求、证据提交 | 创建赛事、分配承办方与任务；排赛另立功能 | 赛事/分配进入，不迁全部 8 门和排赛器 |
| 协同中心 | 待办、材料草稿、提交与退回反馈 | 任务管理、审核队列、版本及历史 | 进入；先单任务单级审核，无通用流程设计器 |
| 承办方门户 | 作为首版主要工作入口，复用 tasks/files | 总部查看同一任务；必要时经办人可用 Web 办理 | 材料闭环进入；报名缴费不进入 |
| 增长中心 | 后续轻量线索跟进/素材提交，先证实需要 | 内容计划、渠道数据、归因与线索处理 | 不进入，不创建 CRM 空壳 |
| 俱乐部球队 | 后续球队/报名与发布赛事信息 | 机构与球队管理；教务是否独立系统另评估 | 不进入；先补独立系统证据 |
| 赞助权益 | 后续合同范围内证据查看/确认 | 合同权益拆分、交付管理与结案 | 不进入 |
| 裁判管理 | 后续本人资质、指派场次、执法报告 | 资质复核、排班、争议与纪律管理 | 不进入 |
| 资料中心 | 当前任务关联模板与授权附件 | 任务要求/模板维护；完整发布版本库后续 | 仅任务附件和模板快照，不建全资料库 |
| 智能助手 | 后续只读问答入口，普通业务不依赖模型 | 后续受控查询与草稿生成 | 不进入；不以 AI 代替任务创建/审核 |
| 数据管理 | 不设置万能数据管理菜单 | 账号/组织/赛事授权的必要管理；业务编辑归所属域 | 必要授权进入，财务维护/通用导入不进入 |

小程序建议导航为“待办、赛事、我的”，不是 12 菜单复制；Web 建议为“赛事、任务审核、组织与授权”，只有实际启用功能才出现入口。不承诺全部板块或六种角色均进入首版。

## 2. 推荐首个完整业务闭环

**Q-01（已挂起，待用户对接负责人后恢复）**：是否同意首个完整业务闭环采用“总部建赛事并分配承办方任务 → 承办方提交材料 → 总部通过或退回 → 双方查看结果与历史”？

依据：requirements H-002 和 agent.md §11 只是原有建议；本轮原型 F-03/04/05/12 已有相邻交互和写入片段，且真实断点集中在授权、任务创建、受控附件与审核，适合先验证两端共享数据和跨机构协作。它不依赖支付、教务、我奥、渠道或 AI 账号，也不必先处理未成年人报名资料。相比财务闭环，核算口径依赖更少；相比报名闭环，外部教务和个人数据边界更可控。**这是优先级建议，不是已获用户批准。**

### 建议参与者与前置条件

- 一个总部赛事管理员、一个具审核权限的总部人员、两个承办组织及其经办人；采用合成身份和两个赛事做隔离测试。管理员可兼任审核员，但提交人与审核人不能相同（候选权限见 role-permissions）。
- 总部与承办成员关系、赛事授权为可受控维护记录，而不是前端传入机构参数或修改数据库后才可工作。
- 一个示范材料任务，内容先用无个人数据的合成办赛材料。任务要求包含标题、说明、承办组织、截止日、审核人、必需材料说明/模板版本。
- 上述字段是候选最小输入；真实材料清单、实际审核岗位和期限由 Q-01 确认后逐项细化，不能把原型 8 门/时限自动固化。

### 建议正常与异常流程

1. 总部 Web 创建赛事，关联承办组织并显式授予赛事范围；创建并分配材料任务。承办方不能仅靠猜测 ID 发现其他赛事。
2. 承办方小程序打开任务，阅读固定版本的要求，创建草稿、上传附件；后端确认对象上传完成和归属，再允许绑定。
3. 承办方提交：验证必填项/附件，创建不可变提交快照和版本号，任务进入待审核；草稿不等于提交完成。
4. 总部 Web 读取该版本及附件，通过或填写退回原因；写入审核人与时间。禁止直接修改 status 绕过动作或审核旧版本。
5. 退回后承办方看到原因，编辑新草稿、再次提交形成下一版本；通过后双端看到相同结果和历史。历史不得覆盖；通过后重开/撤回暂不做，后续另定规则。
6. 上传中断可重试，失败不产生“已提交”假象；提交重试幂等。多人同版本并发审核只允许一个结论，其他请求报告冲突。
7. 站内待办/结果列表就是首闭环通知渠道；不依赖微信订阅消息、短信或实时推送。切页/刷新可获取一致状态，离线草稿同步暂不做。

### 建议状态迁移

| 当前状态 | 动作与角色 | 下一状态 | 必须校验 |
| --- | --- | --- | --- |
| 待提交/草稿 | 承办方保存 | 不变 | 操作/组织/赛事/任务范围；并发版本 |
| 待提交/草稿 | 承办方提交 | 待审核 | 要求完整、附件可用、形成提交快照、幂等键 |
| 待审核 | 指定总部审核人退回 | 已退回 | 当前提交版本、非本人提交、原因必填 |
| 已退回 | 承办方编辑并重新提交 | 待审核 | 新版本，保留旧材料与退回记录 |
| 待审核 | 指定总部审核人通过 | 已通过 | 当前版本、审核权、禁止自审 |
| 已通过 | 任意直接修改历史/状态 | 拒绝 | 首闭环无隐式重开或删除动作 |

状态词、单级审核及不重开规则为建议；确认后纳入正式 requirements 和接口契约。

## 3. 验收标准（建议，尚未执行）

每条须有实际测试/录屏或日志证据；原型现有代码与空工程目录不能满足本表。

| 编号 | 可检查场景与通过标准 | 验证层级 |
| --- | --- | --- |
| AC-01 | 通过 Web 创建赛事、授权、任务，无需手改数据库；正确承办方小程序能看到，另一组织不能看到 | Web E2E + 小程序真机 |
| AC-02 | 承办方完成草稿、上传、提交，总部读到相同字段和文件；总部通过后双方查询得到同一状态/版本 | API 集成 + 双端流程 |
| AC-03 | 退回必须有原因；承办方修改再交产生新版本；旧提交和审核结果可回看且不可覆盖 | 状态单测 + PostgreSQL 集成 + 双端 |
| AC-04 | 未登录返回 401；无权角色/跨组织/跨赛事请求无数据泄漏，变更失败；列表、详情、数量、附件直链均覆盖反例 | API 越权用例 |
| AC-05 | 承办方不能审核、改变任务要求/审核人；审核员不可自审；前端伪造 role 或 status 不生效 | API 权限/状态反例 |
| AC-06 | 必填材料缺失/非法类型/超限/未完成上传被拒绝；错误关联另一赛事文件或他人文件失败；失败不生成有效提交 | 文件集成与负例 |
| AC-07 | 同一幂等提交重试只有一个版本；两次并发审核只有一个合法结果，另一请求明确冲突且不覆盖历史 | 隔离 PostgreSQL 并发测试 |
| AC-08 | API 重启与双端重新登录后赛事、任务、附件关联和历史不丢失；不能只依赖浏览器存储 | 持久化集成 |
| AC-09 | 权限撤销/账号禁用后下一次业务请求被拒绝，不能申请新下载地址；短期已签发地址的有效期被记录验证 | 会话/权限/下载测试 |
| AC-10 | 创建、授权、提交、退回、通过及失败关键原因可追踪请求和操作人；日志不记录令牌、文件正文及多余个人数据 | 审计集成与人工自检 |
| AC-11 | 弱网或上传/提交失败时能明确重试，不错误显示成功；普通业务在无 AI、无第三方接口时仍完整可用 | 双端异常场景 |
| AC-12 | 小程序开发者工具和至少一次真机验证登录、HTTPS 请求、上传下载、退回再交；Web 端完成审核；平台账号不足标阻塞而非通过 | 平台验收 |

测试金额/身份/材料均为合成数据。文件大小/格式、安全扫描策略、会话期限等常规工程配置在实施时固定并补充具体边界测试，不把原型 5MB 直接当业务约束。生产试点还须独立完成备份恢复、发布与隐私检查，不包含在“构建通过”含义内。

## 4. 代码分层检查与调整建议

**结论（工程建议）：保留单仓库、三应用和模块化单体，不需要换框架或按菜单拆后端。** 当前实际尚无源码，本轮只记录收敛输入，不改架构基线或创建空模块；采纳后在 CAAU-002/003 更新 module-map，若依赖边界有实质变更再记 ADR。

| 规划点 | 建议变化/保留 | 依据与理由 |
| --- | --- | --- |
| 应用/共享契约/数据库依赖方向 | 保留 repository.md 基线；小程序与 Web 各自 UI，API 统一授权 | 原型本地/数据库两套事实和角色提示不可靠（F-01/04/05） |
| overview → reporting | 保留只读聚合边界，按确认事实聚合；首版无需独立报表库 | 原型硬编码经营数字未实时联动（F-01） |
| operations → events、registrations | 首闭环先 events + tasks + files；报名延后，排赛后续归 events 内独立能力或按复杂度拆 scheduling | 运营实有节点交付与浏览器排赛，不能全塞报名模块（F-03） |
| collaboration / organizer → tasks | 保留共享任务事实；明确 tasks 拥有任务要求、提交版本、审核历史与状态机 | 原型分别保存状态而无审核链（F-04/05） |
| 8 门、物料交付与赛果 | 不把全部门表单硬建一张万能任务表；通用材料审核归 tasks，后续赛果归竞赛域、金额归 finance、权益归 sponsorship | 原型节点混入合同/回单字段，赛后名次未关联赛程（F-03/05） |
| files 与 resources | files 管对象与授权传输；tasks 管材料业务关联。首版仅任务模板快照，不初始化完整 resources 发布系统 | 原型“可下载”不等于源文件存在或 audience 授权（F-10） |
| organizations / permissions / auth | 显式组织成员 + 赛事授权 + 动作权限；审计是横切底座，不建审计菜单才能启用 | 填 organizer_id 未给承办方权限，任务 owner 字符串不是授权（F-12） |
| clubs → organizations、teams | 保留基础归属；教务课程、考勤、课消不是球队成员表，后续评估独立 academics 域/外部适配器 | 当前只见外部嵌入入口，没有代码证据，不能假定直接迁入 teams（F-07） |
| data-management | 明确为管理入口组合，赛事创建归 events、财务维护归 finance、授权归 permissions、审计由对应业务写入 | 已查明并非通用改表/导入工具；不建立万能后台写库模块（F-12） |
| AI / growth / sponsorship / referees | 保留规划名，延后建代码；AI 只能经业务公开接口，无第二套规则 | 实际多为演示或未核验外部能力（F-06/08/09/11） |

首闭环候选对象：内部用户/会话、组织/成员、角色授权/赛事授权、赛事、任务要求版本、材料草稿/提交快照、审核记录、文件与业务关联、审计。此处不是已确认表名或 ER 图；CAAU-003/004 再确定外键、唯一性、事务边界和数据最小化。

## 5. 初始化输入与后续关口

- **可沿用的工程决策：** TypeScript 单仓库、三个独立应用、REST/OpenAPI、PostgreSQL、服务端统一规则（当前架构基线）。本轮未核验版本；CAAU-002 必须查官方版本/兼容性并固定锁文件，不沿用 agent.md 的历史检索声明。
- **工程骨架最小目标：** 三应用构建、同一健康接口、配置示例、真实检查工具与依赖边界。不为 12 板块生成空目录，不导入原型账号和历史快照。
- **业务实施阻塞：** Q-01 按用户指令挂起，不将建议闭环写成已确认数据库/业务接口。通用工程工具、应用骨架、健康接口及开发环境可独立推进。待用户完成对接后，再逐次澄清审核岗位、材料清单与组织协作，不重复催问或一次提问全部问题。
- **后续模块依赖：** 报名需字段/组别/年龄/审核/退费规则和教务系统边界；财务需核算与审批口径；我奥需官方接口及授权；增长需渠道和归因来源；赞助/裁判需合同/治理职责。均延后到对应模块，非本轮自动承诺。
- **外部资源：** 微信身份/测试与发布资源、域名、云存储等在需要真机和预发布前落实；不阻塞本轮文档，不进行外部连接、付费或发布。
