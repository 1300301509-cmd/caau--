# CAAU 业务智能体方案（CAAU-049）

状态：2026-09-22 架构确认；B1 已实现 Web 赛程页最小入口、Agent 会话/任务、LangGraph PostgreSQL checkpoint、千问适配层和纯调整预览。当前不保存或发布赛程；真实千问、小程序和真机仍待验证。运行与边界见[业务智能体赛程预览](../runbooks/agent-platform.md)。

## 1. 产品目标

CAAU 智能体不是独立聊天机器人，而是现有赛事业务的自然语言操作入口。用户可以询问业务数据、生成方案、调整草稿并发起受控写操作；所有真实数据仍由原业务模块持有，所有写入仍经过原接口、权限、状态机、并发控制和审计。

首个闭环选择赛程编排，因为仓库已经具备确定性的生成、逐场调整、冲突校验、不可变版本和发布接口。调整/发布已有 CAS，生成尚缺 expectedRevision；现有 lastCommandId 去重仍需补足持久命令回执。示例：

> 用户：把周六下午第二场移到周日上午 10 点，放到 1 号场地。
>
> 智能体：定位当前赛事和场次，读取当前 revision，生成一张变更预览卡，说明原时间、目标时间、场地及冲突检查。用户确认后，智能体调用现有逐场调整命令形成新草稿版本；发布赛程仍是另一个明确动作。

智能体不得直接连接 Prisma、执行 SQL、修改数据库文件、伪造当前用户或建立第二套排赛算法。

## 2. 产品体验

### 2.1 入口

建议第一阶段放在总部 Web 的全局智能体侧栏，同时带入当前页面、当前赛事和当前模块作为可见上下文。用户可以切换赛事，但候选范围只能来自服务端返回的有权资源。后续可在承办方小程序增加同一 Agent 服务入口；两端共享会话身份和业务工具，不复制规则。

页面不能只显示连续对话文本。每次业务动作使用结构化卡片：

- 当前作用范围：赛事、模块和用户身份；
- 智能体理解的目标和必要参数；
- 变更前后差异、冲突和影响；
- 当前账号是否有权执行，以及拒绝原因；
- “确认执行”“修改条件”“取消”操作；
- 执行后的业务版本、实际状态和可跳转页面。

### 2.2 动作分级

| 等级          | 例子                               | 执行规则                                           |
| ------------- | ---------------------------------- | -------------------------------------------------- |
| L0 查询       | 查看本周赛程、材料缺口、待办       | 可直接执行，只返回当前账号有权读取的数据           |
| L1 计算/草案  | 生成候选赛程、分析冲突、草拟通知   | 可直接计算，不保存业务草稿；保存归 L2              |
| L2 可恢复写入 | 调整一场比赛、修改未发布草稿       | 先展示结构化差异和影响，用户确认后执行             |
| L3 发布/审批  | 发布赛程、通过申请、批准材料       | 独立确认；必须具备专门能力，不能由宽泛聊天权限派生 |
| L4 高影响操作 | 权限授予、批量变更、财务动作、删除 | 首期不开放；后续需专门流程、复核或多人审批         |

“请直接帮我改”可表达操作意图，但首期不能跳过 L2/L3 的结构化确认。查询回答不得伪装成已经执行，工具失败也不得用自然语言声称成功。

## 3. 权限模型

### 3.1 判定公式

每次工具调用按以下条件共同判断：

`有效身份 × 业务能力 × 数据范围 × 资源关系 × 当前状态 × 动作风险`

- **有效身份**：当前服务端会话对应的 `InternalUser`，用户和成员都必须有效；模型不能接收或选择 actorId。
- **业务能力**：如 `schedule.read`、`schedule.draft.generate`、`schedule.draft.adjust`、`schedule.publish`，不要只用一个“可以使用 AI”的开关。
- **数据范围**：全部赛事、明确授权赛事、承办机构所属赛事或本人球队。
- **资源关系**：`EventGrant`、有效承办关系与办理资格、`TeamMembership` 等继续表达各自关系，不能互相冒充。
- **当前状态**：已发布、待审核、审核中等状态继续限制可执行动作。
- **动作风险**：决定是否需要预览、一次确认、额外复核或禁止 Agent 执行。

### 3.2 首期角色矩阵（建议，具体授予待确认）

| 身份                    | 赛程查询                 | 生成候选/调整草稿            | 发布赛程                                       | 其他赛事                                    |
| ----------------------- | ------------------------ | ---------------------------- | ---------------------------------------------- | ------------------------------------------- |
| 总部超级管理员          | 全部有权读取             | 可执行，但仍经后端校验和确认 | 可确认发布                                     | 可处理全局范围，但不得绕过状态机、CAS和审计 |
| 获授权赛事管理员        | 仅获授权赛事             | 仅获授权赛事                 | 仅在具备 `schedule.publish` 时                 | 无权赛事拒绝                                |
| 当前赛事有效承办经办人  | 仅本机构当前承办赛事     | 可按明确能力生成和调整       | 建议首期不默认拥有发布能力；是否授予由业务决定 | 其他机构或赛事拒绝                          |
| 审核员                  | 按原审核范围查询相关信息 | 不允许调整赛程               | 不允许                                         | 不能通过 Agent 扩大审核范围                 |
| 基本信息查看者/球队账号 | 仅其原接口允许的只读投影 | 不允许                       | 不允许                                         | 内部赛程草稿和敏感字段不可见                |

当前 `scheduling` 服务把赛事操作权限用于读取、生成、调整和发布。若要实现“权限低的账号能改草稿但不能发布”，落地前必须把权限拆成上述细粒度能力；仅在提示词中描述权限不算实现。

### 3.3 双重校验

Agent Orchestrator 可以根据当前能力减少展示的工具，但这只是体验优化。每一个工具真正执行时必须携带当前服务端会话，由原业务服务重新鉴权。前端隐藏按钮、模型拒绝、工具未展示都不能代替后端授权。

## 4. 系统结构

```text
Web / 小程序
  │ 当前登录会话、当前赛事、用户输入
  ▼
Agent API（apps/api/src/modules/ai）
  ├─ LangGraph.js 状态图、会话编排与流式输出
  ├─ 工具注册表与参数校验
  ├─ 风险分级、确认票据与执行预算
  ├─ 上下文检索与权限过滤
  └─ 运行轨迹、模型版本、工具结果
          │ 严格 JSON Schema 工具调用
          ▼
业务工具适配层
  ├─ scheduling：读、生成、调整、发布
  ├─ teams：球队与赛事球队
  ├─ materials：材料与审核
  └─ event-*：申请、物料、赛事情况
          │ 调用现有公开 service / HTTP 契约
          ▼
原业务模块 → authorization → PostgreSQL / 私有文件
```

模型只提出结构化工具调用。Agent API 负责把调用绑定到当前会话、校验参数、获取确认、限制调用次数并执行。业务工具适配层调用原有业务用例，不能复制权限或事务逻辑。

采用 LangGraph.js 单 Agent 加业务工具组，通过模型适配层接入千问或混元。终端 pi-agent 用于开发，不嵌入产品运行时。查询允许模型选择受控工具，写入采用固定的“预览—等待确认—重新鉴权及版本校验—执行”节点。PostgreSQL checkpoint 由 `@caau/database` 提供持久化入口；恢复不等于业务命令只执行一次，必须配合持久命令回执。模型和供应商封装在 `ai` 模块内，业务模块不直接依赖模型 SDK。详见 [ADR-0019](../adr/0019-agent-orchestration.md)。

## 5. 工具契约

每个 Agent 工具必须登记：

- 稳定名称与版本，如 `schedule.adjust_draft.v1`；
- 输入和输出 JSON Schema，禁止自由文本直接进入业务命令；
- 所需业务能力和资源 ID 提取方式；
- `READ / DRAFT / WRITE / PUBLISH` 风险等级；
- 是否需要确认及确认票据有效期；
- 幂等方式、`commandId` 和 `expectedRevision`；
- 最大调用次数、超时和可重试错误；
- 审计字段及敏感字段脱敏规则。

首批赛程工具：

1. `event.list_accessible.v1`：沿用 `listCompetitionEvents` 读取当前用户有权管理的比赛，不能借用更宽的基本信息查看范围。
2. `schedule.get.v1`：读取赛事当前赛程、revision、状态和 issues。
3. `schedule.preview_adjustment.v1`：复用现有确定性规则计算单场调整差异和冲突，不保存业务数据；需要新增纯预览能力。
4. `schedule.adjust_draft.v1`：确认后，以 matchId、目标时间、场地、expectedRevision 调用调整接口，形成新草稿版本。
5. `schedule.generate_draft.v1`：后续接入；这是保存业务草稿的写操作，需先补齐版本保护并确认。
6. `schedule.publish.v1`：在零冲突、专门发布能力和独立确认都满足时调用现有发布接口。

不提供 `execute_sql`、`update_anything`、任意 HTTP 请求或通用文件系统工具。新业务进入 Agent 前，必须先有稳定、可独立验收的领域 API。

## 6. 赛程修改的完整流程

1. **解析上下文**：从页面上下文和有权赛事列表确定 eventId；有歧义时让用户选择，不猜测。
2. **读取权威状态**：调用 `schedule.get.v1`，取得当前 revision、场次、状态和已有冲突。
3. **解析目标场次**：用日期、顺序、球队等信息匹配；多条匹配时显示候选。
4. **生成变更预览**：展示原时间/场地、目标时间/场地、受影响场次及预计动作等级。
5. **预检查**：可调用相同确定性规则形成候选结果；模型不自行判断“没有冲突”。
6. **权限与确认**：服务端重新检查 `schedule.draft.adjust` 和赛事范围，生成绑定 userId、eventId、参数摘要、revision、过期时间的一次性确认票据。
7. **执行**：用户确认后用固定 commandId 和 expectedRevision 调用原调整服务。
8. **处理并发**：遇到 409 时重新读取；展示其他人已推进的版本和新差异，不自动覆盖或静默重试新 revision。
9. **结果回执**：展示实际新 revision、当前冲突、草稿状态和跳转入口；不自动发布。
10. **发布**：用户另行要求且具备 `schedule.publish` 时，再展示发布版本和影响并独立确认。

确认票据不能只存在前端，也不能仅靠“用户说过确认”。参数、资源或 revision 任一变化，旧票据立即失效。

## 7. 数据、记忆与知识

智能体上下文分三层：

- **即时会话**：当前对话、页面和待确认动作；过期后不得继续执行。
- **业务事实**：始终通过有权 API 实时读取，数据库是唯一事实来源。
- **知识资料**：赛事规则、操作手册和制度文档可进入检索库，但必须保存来源、版本和访问范围，回答时给出来源。

B1 已把记忆分为三级：L1 会话层保存必要近期 turn、短摘要、当前 event/match 结构化字段；L2 任务层保存 owner、目标、步骤、资源、baseline revision、预览/有效期和 checkpoint thread。恢复时重新检查身份、授权、资源版本和期限，旧预览没有执行授权。L3 本批只记录边界，不创建表或向量库；偏好如默认场地或常用时段只有在用户明确保存且有字段归属后才能持久化，知识必须有来源、版本和访问范围。模型从历史聊天推断的内容不能直接成为业务默认值。

模型请求只发送完成当前任务所需的最少字段。银行账户、身份证件、未成年人名单、私有附件原文等不得默认进入模型上下文。自然语言对话不写入业务审计正文；业务审计保存结构化命令、实际 actor、时间、资源、revision 和结果。

## 8. 审计、可观测与安全

至少记录两类证据：

- **业务审计**：由原业务事务记录谁对哪个资源做了什么、版本和结果；Agent 操作也必须落到同一业务审计。
- **Agent 轨迹**：session/turn、模型与提示版本、所提供工具、工具调用名称、参数摘要、确认票据、延迟、token、结果状态和错误；敏感参数只存摘要或脱敏值。

必须防范：提示注入、工具输出中的恶意指令、越权资源 ID、参数替换、重复执行、确认后偷换参数、无限工具循环和模型服务超时。采用工具白名单、严格 schema、每轮调用预算、超时、限流、幂等、CAS、确认票据和服务端重新鉴权。

模型不可用时，原 Web 和小程序业务功能必须继续可用。Agent 是新的操作入口，不成为核心业务唯一入口。

## 9. 分阶段落地

阶段编号统一见[分阶段计划](../planning/caau-049-agent-platform.md)；A 为方案确认。

### B. 只读赛事助手与纯预览

- Web 智能体侧栏、Agent 会话和流式响应；
- 有权赛事列表、当前赛程和冲突解释；
- 无写工具，先验证身份、数据范围、拒绝和审计。

### C. 赛程草稿协作

- 接入生成候选与逐场调整工具；
- 结构化差异卡、一次性确认票据、CAS/409 处理；
- 不开放发布工具。

### D. 受控发布

- 拆分 `schedule.publish` 专门能力；
- 发布前零冲突校验、独立确认和权限回归；
- 加入模型/工具离线评测和真实多角色端到端验收。

### E. 扩展工作流

- 按成熟度逐项接入材料查询、申请状态、物料缺口、球队管理等工具；
- 每项先有业务 API、权限矩阵、风险等级和确定性测试；
- 主动提醒先生成待办或建议，不直接执行写操作。

### 后续评估：多角色与主动智能体

- 根据业务需要评估异步任务、审批链、定时巡检和多智能体分工；
- 批量、高影响或跨赛事动作必须单独设计，不由聊天工具自然扩张。

## 10. 验收指标

首期至少建立以下评测集：

- 相同表达和口语别名能正确定位赛事/场次；歧义时询问而非猜测；
- 有权赛事成功、无权赛事拒绝，传入他人 eventId/matchId 仍拒绝；
- 审核员、基本查看者和球队账号无法通过提示诱导获得写工具；
- L2 未确认不写入，确认参数变化后旧票据失效；
- 409 后不覆盖他人修改，未知响应使用同一 commandId 重试且不重复写；
- 工具失败、超时或模型中断不虚报完成；
- 发布前有冲突时服务端拒绝，模型不能说服系统绕过；
- Agent 写入与人工页面写入产生相同业务版本和审计证据；
- 敏感字段不进入模型输入、轨迹和错误日志；
- 关闭 Agent 或模型服务不可用时原业务入口正常工作。

评测采用确定性断言加语义评分：权限、工具名、参数、确认和数据库结果使用确定性检查；意图理解和解释质量使用固定样例与评分规则。每次修改提示、模型或工具描述都重跑。

## 11. 本轮建议决策

建议确认以下产品原则后进入 A 阶段：

1. 首个 Agent 场景选定“赛程查询 + 草稿调整”，先不自动发布。
2. Web 为首个入口，小程序后续复用同一 Agent 服务。
3. 承办经办人是否默认拥有赛程草稿调整能力；发布权限是否只给总部赛事管理员/超级管理员。
4. L2 变更必须预览确认，L3 发布必须独立确认。
5. 对话和 Agent 轨迹的保存期限、可查看人员及生产模型服务的数据处理要求。
