# 赛事竞赛组别与组内排程（CAAU-099）

## 本期采用的业务规则

一场赛事可以有多个竞赛组别，例如「U12 男子组」。赛事参赛队伍必须归属某个竞赛组别；正式对阵的双方必须属于同一组别。「所有队伍两两交手一次」在有多个组别时按**各组内部**解释，比赛总数为各组 `n × (n - 1) / 2` 之和。赛事的场地和时间由各组共同占用，不能为每组分别计算后产生重叠。

竞赛组别与后续可能出现的组内 A/B 分池是两种不同概念。本期只实施竞赛组别，不自动划分分池。U12 等名称不自动推导年龄截止日、资格或名单合规性；这些需要另行确定报名和审查规则。

## 数据与业务入口

- 组别属于赛事，以稳定 ID 关联。名称可编辑，停用后保留历史；同赛事有效组别名称不能冲突。
- 球队主档案可复用于不同赛事，组别归属存于独立的赛事参赛记录。一个球队主档案在同一赛事仍只对应一条参赛记录；同俱乐部不同年龄/性别阵容应使用独立球队档案与参赛名单。
- 现存没有组别的赛事参赛记录保持「待归组」，由有权管理员显式归组。迁移不得猜测组别，也不得改写既有已发布赛程和不可变历史。
- 新增参赛队伍时必须选择当前赛事有效组别。归组变更携带参赛记录 revision；旧候选、预览或确认票据在参与者组别变化后失效。
- Web、小程序球队列表和赛程应展示组别；在多个同名球队或同名场次之间先用组别缩小范围。

## 排程与智能体

- 服务端在常规生成、候选独立审计、草稿确认、人工调整和发布前核对组别归属，并把组别快照写入新场次与版本。跨组对阵、未归组参赛记录、组别与当前参赛记录不一致都属于硬冲突。
- 组别改名后，旧草稿中的组别标签仍作为历史快照展示；要调整或发布，须重新生成包含当前组别名称的新草稿。旧确认票据没有组别绑定信息时只能重新预览，不能直接执行。
- 赛事继续使用统一赛程版本，组别场次共享场地和时段冲突检查。组内单循环分别生成；单败淘汰不得跨组引用前置比赛。已发布历史保持可读，但不能借旧组别数据绕过新的发布校验。
- 智能体的模型只提议组别范围及球队信息；服务端在当前授权赛事中解析真实组别 ID。多个组别而请求未指定范围时，助手询问是某一组还是全部组别。球队建档与测试球队生成也必须在预览中标明归属组别，再经原确认流程写入。
- 仅重排某一组时，当前必须已有同一赛事的单循环 DRAFT，且其他组场次完整、无冲突。候选沿用赛事级日期、时段、场地和参赛配置，将其他组场次全部固定，重新计算选定组后再对合并的整份赛程审计；若没有合格基线或需要改变赛事级配置，须选择全部组别重新编排。单组候选保存时仍只新增一个赛事级 DRAFT 版本。
- 需求、候选、票据和回执分别绑定组别 ID、参赛关系修订及基线版本；对话摘要只能辅助「刚才那组」的指代，不作为当前组别事实。

## 验收

用同一赛事下至少两个组别验证：各组组内对阵数正确、没有跨组比赛、同一场地跨组时间不冲突；未归组/改组/停用组别会拒绝新的生成或确认；旧发布版本可读；不同客户端和智能体调用同一后端校验。验证真实授权与撤权、版本冲突、回执重放、隔离 PostgreSQL 与两端展示。微信开发者工具、真机、真实模型和远程环境分别记录。
