# CAAU-063 排程需求收集（当前交付边界）

来源：用户明确要求在统一助手内收集整周排程要求；以下是**需求采集流程**，不是已获确认的实际排程业务规则。详情、实现取舍见 [ADR 0025](../adr/0025-agent-planning-requirement-revisions.md)，进度见[任务清单](../planning/roadmap.md)。

## 角色、数据范围与流程

当前赛事有管理操作权限的用户，在 Web 或小程序的统一助手中**明确**说“收集排程需求”或给出具体赛事球队限制，才建立独立 `SCHEDULE_PLANNING` 需求单；闲聊、泛泛问“如何排赛”、赛程只读查询和单场改期不建立需求单。缺赛事、同名参赛球队、年份日期或条件含义不明先请求选择/澄清。页面赛事只作提示，不覆盖进行中的单场任务；明确提出其它有权赛事须再次核验。每项条件绑定此赛事的有效 `EventTeam` 参与记录，不改永久球队档案。

当前可记录：

- 整套候选请求中的“10 天内”可从当前有权赛事最新资料的开始日期计算含首日的 10 个北京时间自然日；无赛事资料时可使用已保存赛程配置的开始日期。来源写入需求并展示，赛事资料结束日期短于请求期限时先澄清；两处都没有有效开始日期时追问具体日期。对于“所有队伍都必须比过一场”，须追问是至少一场还是每两队交手一次；明确单循环后才可确认需求。由程序安排全部当前有效参赛球队两两唯一对阵，仍以候选预览为结果，不因聊天确认正式赛程。

- 包含年份的赛事计划日期范围（单次最多 31 天为当前技术限额，不是正式赛制或赛事时间硬规则）；星期限制落实为范围内的具体日期，不能以当前周猜测年份。若先说“D队只能周三”，记为待补条件，补全日期才变成明确日期。
- 参赛球队 `ONLY`（只在指定日期/时段安排）、`AVAILABLE`（此时段可安排，**不**表示其它日期必然不可用）、`BLOCK`（此时段不可安排）；完整起止时刻用 HH:mm，单说星期表示全天；“上午”之类缺起止时刻须澄清。每条条件为 `MUST` 必须满足或 `PREFER` 尽量满足，来源与人工确认状态逐条展示。
- 两支赛事参赛球队的 `PREFER` 倾向相遇或 `AVOID` 尽量避免相遇；这只是对现有对阵安排的**偏好**，不保证两队会有一场比赛，也不能添加比赛、改变晋级规则或擅自决定赛制。“优先对阵”但没有明确含义须澄清。
- 每天上午／下午／晚上的场数上限可作为独立 `DAYPART_CAPACITY` 硬条件逐轮补充。需求单记录每个时段的名称、最多场数、明确的开始／结束时间，以及按整个赛事或每个场地统计的口径；未说出的钟点与口径保持待补。完整的三个时段均被设置时，候选只使用这些时段，空档不安排比赛；两端需求卡在人工确认前明确显示此含义。已记录的日期、球队和其它条件在补充时保留，不因新的短句重新索取。

多轮“改成周三和周五”替换已可唯一引用的同队条件，“取消 D 队时间限制”撤销旧条件；不能唯一引用时要求用户指明。每条已记录条件保留原对话来源，刷新和重新登录从有权数据库会话恢复。展示赛事、版本、状态、摘要、待补字段、具体日期和可以确定的矛盾（例如同队同日同时间既必须可安排又禁止）；这只是必要冲突检查，**不**保证整周赛程可解，零冲突也不意味着球队或场地有空。

用户只能点击**仅确认需求（不生成赛程）**确认当前已完整且无明显矛盾的版本。确认只更改需求状态，不生成/覆盖赛程，不创建单场任务、预览、执行票据或调度命令；“好的”不是确认。确认后再修改/撤销条件使旧确认失效，须刷新核对并重新确认；旧版本 CAS 返回 409。若参赛记录停用，历史来源仍在但确认在当前视图标为失效，不能沿用。撤权后历史、来源和确认均不得对原用户返回或送入模型，跨账号/跨赛事访问同样拒绝；其它无权新会话可以继续普通聊天。

## 当前尚未确认

队伍额外非标准时间文字、跨周超过技术限额的排赛需求、赛制变化、比赛轮次和晋级规则、硬/软条件与其他赛事规则的优先级、真实排程算法及发布/审批授权都**未因本功能而确定**。不得把示例日期、球队和手工确认动作转成正式业务默认值。微信开发者工具、真机、Studio 官方页面登录后的人工交互和远程环境仍需分别验收。
