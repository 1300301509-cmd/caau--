# CAAU 智能体球队端小程序（CAAU-046）

状态：A 阶段产品规格与差距分析；尚未编码，文中“建议”与“待确认”不构成已确认业务规则。

## 1. 目标与首版边界

新增独立微信小程序“CAAU 智能体球队端”，建议工程目录为 `apps/team-miniapp`，使用独立构建产物和独立 AppID。首版只覆盖：

1. 球队用户建立、查看和维护自己有权管理的球队基础档案。
2. 检索对球队公开且当前开放报名的赛事，并查看经过明确白名单裁剪的公开详情。

建议一级页面为【找比赛】【我的球队】【我的】。报名提交、支付、订单继续由原外部小程序负责；外部接口提供并确认前，不实现报名动作或伪造跳转闭环。本阶段不做 AI 对话、球员名单或球员敏感资料采集。

球队端复用同一个 API、PostgreSQL、`@caau/api-client`、`InternalUser`、`Team` 和 `TeamMembership`，不复制球队库。球队用户不因使用本应用获得 `ORGANIZER`、赛事管理、审核或承办申请权限。

## 2. 现场核对结果

### 2.1 已有能力

| 能力         | 当前事实                                                                                                                | 可复用部分                                                 |
| ------------ | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 球队主档案   | `Team` 保存 JSON 档案、active、revision、录入机构、创建/更新人；已有不可变 `TeamVersion`                                | 主档案、CAS 修订、版本留痕可继续使用                       |
| 球队账号关系 | `TeamMembership` 以 `teamId + userId` 唯一，带 active；授权代码已允许有效成员读取和编辑所属球队                         | 可作为球队端数据范围锚点                                   |
| 赛事球队     | `EventTeam` 按 `eventId + teamId` 唯一，复制加入当时的 profile 和 `sourceTeamRevision`                                  | 保持赛事参赛资料快照，不从主档案动态联表                   |
| 参赛名单     | `EventTeamRoster` 属于赛事球队并独立版本化                                                                              | 不进入首版球队档案；不能用主档案覆盖                       |
| 球队 API     | 已有球队列表、创建、更新，以及赛事球队列表/加入/更新                                                                    | DTO、校验和事务可参考，但现有创建接口面向总部/承办业务范围 |
| 微信身份     | `WechatIdentity` 已按 `appId + openId` 唯一、按 `appId + userId` 唯一，并关联同一 `InternalUser`；小程序会话使用 Bearer | 数据结构可容纳同一用户在不同 AppID 下的不同 OpenID         |
| 跨端撤销     | 用户停用、改密/重置会撤销会话；业务授权逐请求复核                                                                       | 可继续作为统一会话治理基础                                 |
| 赛事信息     | `Event` 有名称、说明、内部生命周期；获批申请会产生只含名称、日期、地点的版本化 profile                                  | 可作为未来公开投影的来源之一，但不能原样公开               |
| 客户端契约   | Nest OpenAPI 生成 `@caau/api-client`，Taro transport 已存在                                                             | 新应用只消费生成客户端，不依赖其他应用源码                 |

### 2.2 当前不能满足首版的部分

1. `Team.organizationId` 当前必填且语义是录入机构；球队自行建档没有合理的承办机构可挂靠，不能创建虚假机构或借用承办方。
2. `TeamMembership` 没有成员角色、邀请来源、认领过程、接受时间、撤销原因或历史；数据库运行账号当前仅获其读取权限，没有受控写入流程。
3. 现有 `POST /teams` 要求调用人是总部超级管理员，或是目标机构的 `ORGANIZER/EVENT_MANAGER`；普通球队用户无法自助建档。
4. 现有球队列表未做服务端分页/检索，且 DTO 混合总部录入字段、内部备注和球队自维护字段；不应原样暴露给球队端。
5. 当前微信配置只有一组 AppID/AppSecret；登录及绑定明确要求有效 `ORGANIZER`，无法给无承办方角色的球队用户使用。
6. 当前绑定凭证只能由承办方密码 Web 会话创建。球队端没有已确认的密码 Web 前置流程，也没有邀请/认领凭证。
7. `EventLifecycleState` 目前只有 `PREPARING_INTERNAL`；没有赛事公开发布、下架、公开版本或报名开放状态。
8. 现有 `/events` 是内部授权列表，不是公开目录；返回的 profile 结构未形成稳定公开契约。
9. 报名开始/截止目前属于办赛材料/申请资料，不是已确认的赛事公开报名权威字段；没有外部报名系统映射和资格校验接口。
10. 现有 API 不能分别表达“赛事当前可报名”和“某支球队是否符合资格”。

## 3. 核心产品流程

### 3.1 首次进入与微信身份

建议流程：同意服务协议和隐私政策 → `wx.login` → API 按球队端 AppID 交换 OpenID → 恢复已绑定的 `InternalUser`，或进入受控建档/认领流程。

- OpenID 只由服务端通过微信接口取得，不接受客户端提交。
- 新 AppID 下的 OpenID 与承办方小程序 OpenID不同；不得仅凭昵称、手机号、姓名或 UnionID 自动合并用户。
- 已有 `InternalUser` 如需复用，应通过一次性跨应用关联凭证、已有密码会话或管理员明确邀请来证明控制权，再把新 AppID 的 `WechatIdentity` 绑定到同一用户。
- 无既有账号的用户，建议在完成微信校验并确认建档后创建一个 `InternalUser`，再原子创建 Team 与 OWNER 关系。是否允许立即生效仍是业务待确认项。
- 微信身份绑定只证明“这个微信属于该用户”；`TeamMembership` 才证明“该用户可以管理这支球队”，两者不得合并为一个隐式规则。

### 3.2 新球队建档

建议用户填写首版最小档案，确认可能存在的相似球队提示，然后提交。服务端在一个事务中创建：

1. 新球队主档案；
2. 初始不可变版本；
3. 当前用户的 OWNER 管理关系及关系历史；
4. 审计记录。

同名、相同联系人或相同手机号只做核对提示，不自动合并或转移所有权。为避免把未确认规则固化，首版字段沿用现有名称、负责人、联系方式、省、市及现有选填字段作为兼容候选；哪些字段对球队自助建档必填需确认。

### 3.3 既有球队邀请／认领

既有球队必须按稳定 `teamId` 认领，建议使用短时、一次性、高熵且数据库仅存摘要的邀请凭证：

1. 有权发起者选择已有球队并生成邀请；
2. 球队用户在球队端完成微信登录后兑换；
3. 服务端锁定邀请和球队，复核邀请未过期、未使用、目标及当前关系；
4. 按确认的审批规则创建或激活 `TeamMembership`；
5. 记录发起者、接受者、时间、结果和撤销历史。

存在有效 OWNER 时，新成员邀请建议由 OWNER 发起；尚无成员的历史球队由谁发起或批准，需在实施前确认。认领不改写历史 `TeamVersion`、`EventTeam` 或 `EventTeamRoster`，也不把球队用户加入录入机构。

### 3.4 球队档案维护

【我的球队】只列出当前用户具有有效关系的球队。更新携带 `expectedRevision`；409 时重新读取权威版本并保留本地输入供核对，不做最后写入覆盖。归档、转让唯一 OWNER、成员撤销和球队合并都需要单独规则；未确认前不在首版提供。

### 3.5 找比赛

总部先形成一个明确的公开版本并发布；下架后立即从球队端目录消失，已打开详情再次请求时也不得继续返回。球队端只查询公开投影，不调用内部 `/events`。

建议列表默认只显示：`publicationStatus=PUBLISHED` 且 `registrationState=OPEN` 的赛事。详情至少可候选展示名称、日期、公开地点、公开说明、公开组别/类别、报名窗口和外部报名提示；字段须由总部发布时逐项确认，不能从内部申请或办赛材料中整包透传。

响应必须并列表达：

- `registrationState`：赛事层面的 `NOT_OPEN / OPEN / CLOSED / SUSPENDED`；
- `eligibility.status`：针对所选球队的 `NOT_EVALUATED / UNKNOWN / ELIGIBLE / INELIGIBLE`；
- `eligibility.reasonCodes`：可机器处理的原因码，公开文案另行映射。

“OPEN”只代表报名窗口开放，不代表当前球队符合资格。“UNKNOWN/NOT_EVALUATED”不得显示为“可报名”。外部报名接口未接入前，页面只说明报名渠道尚未接入，不提交报名、订单或支付数据。

## 6. 公开字段与禁止字段

公开赛事 DTO 应使用明确 allowlist 和独立查询，不返回内部 Event 实体或任意 JSON。首版候选公开字段：赛事 ID、公开标题、公开摘要、开始/结束日期、公开地区/场馆文本、报名起止时间、公开组别/类别、发布版本和更新时间。

以下信息默认禁止进入球队端，除非未来逐字段另行确认：

- 承办申请及办赛材料附件；
- 营业执照、场地照片原文件；
- 银行账户、合同及线下确认；
- 申请人/审核人身份、意见、原因和审核历史；
- 内部备注、审计、grant、机构内部关系；
- 非公开手机号和联系人；
- 私有对象键、下载地址或内部版本 JSON。

## 7. 接口差距

### 7.1 建议新增的球队端接口

以下仅为设计草案，路径和字段在 B 阶段契约评审后确定：

| 用例           | 建议能力                                           | 现状                                         |
| -------------- | -------------------------------------------------- | -------------------------------------------- |
| 球队端认证模式 | 按 client/app key 返回球队端微信能力               | 当前只有全局单 AppID 能力位                  |
| 微信登录/注册  | 按球队端 AppID 交换 code，恢复或建立受限主体       | 当前只允许 active organizer                  |
| 跨 AppID 关联  | 创建并兑换目标 AppID 的一次性关联 intent           | 当前 intent 绑定单一承办方 AppID 和密码会话  |
| 我的球队       | 服务端分页列出当前用户有效关系                     | 当前 `listTeams` 无分页且 DTO 面向内部工作台 |
| 自助建档       | 原子创建 Team、版本、OWNER 关系                    | 当前依赖录入机构和内部角色                   |
| 邀请/认领      | 创建、查看、兑换、撤销受控邀请                     | 当前没有写接口和过程模型                     |
| 球队详情/更新  | 球队端专用 DTO、字段白名单及 CAS                   | 当前更新逻辑可复用，但 DTO 含内部字段        |
| 公开赛事检索   | 仅返回已发布、未下架的公开投影，支持服务端分页筛选 | 当前只有内部授权 `/events`                   |
| 公开赛事详情   | 返回指定公开版本和报名状态                         | 当前无公开发布版本                           |
| 球队资格       | 对 `teamId + eventId` 返回独立资格结果             | 当前无规则或接口                             |

### 7.2 不应复用为球队端接口的现有能力

- 不直接开放内部 `/events`、承办申请、办赛材料或私有附件接口。
- 不允许球队用户调用 `POST /events/:eventId/teams`；该接口代表把主档案加入赛事，并非报名。
- 不把 `EventTeam.active` 当作报名状态，也不从它反推球队资格。
- 不把赛事赛程 `PUBLISHED` 当作赛事公开发布；二者生命周期不同。
- 不用 `ORGANIZER` 角色绕过球队关系校验。

## 8. 数据兼容方案

### 8.1 保留与扩展

1. `Team.id`、现有 profile、revision、版本和所有 `EventTeam` 关系原样保留，不复制或回填新表副本。
2. 将现有必填 `organizationId` 的语义演进为可空的“历史录入机构/来源机构”（最终字段命名待迁移设计）；旧数据值保持不变，自助创建不伪造机构。
3. 为 `TeamMembership` 增加独立角色、状态时间及关系历史，或增加配套版本/事件表；现有 active 关系按迁移策略映射为建议的 OWNER/MANAGER 之一，具体映射必须先确认，不能静默赋予所有权。
4. 新增邀请/认领 intent，数据库只存凭证摘要；使用、过期、撤销和冲突均可审计。
5. `WechatIdentity` 继续关联同一 `InternalUser`；保留 `appId` 作用域唯一约束。服务端配置从单 AppID 演进为受控客户端注册表，每个 AppID 独立 Secret、用途和允许的认证流程。
6. `Session` 建议记录逻辑客户端或 AppID 作用域，以支持按应用撤销、审计和风控；是否新增 client enum 或 client registration 外键在 B 阶段决定。
7. 新增独立赛事公开发布聚合及不可变公开版本；发布时从已确认字段生成 allowlist 快照，不让球队端查询内部 profile JSON。
8. 报名状态与资格结果分开存储或计算；没有权威资格规则时返回 `NOT_EVALUATED/UNKNOWN`，不伪造合格。

### 8.2 不变式

- 修改 Team 不自动更新任何 EventTeam 或 roster。
- 认领 Team 不改变历史比赛资料、录入机构、创建人或历史操作者。
- 下架赛事不删除 Event、EventTeam、赛程或历史公开版本。
- 同一微信在不同 AppID 下的 OpenID 不相等也不要求相等；UnionID 只能用于提示/风控，不能自动合并。
- 球队端会话不派生组织角色、EventGrant 或承办申请 grant。

## 9. 应用与依赖设计

`apps/team-miniapp` 应为独立 workspace 应用，拥有自己的 `package.json`、Taro 配置、页面配置、测试、`project.config.json` 和输出目录。建议包名 `@caau/team-miniapp`，项目名与构建产物不得覆盖 `@caau/miniapp`。

依赖方向：

```text
apps/team-miniapp ──> @caau/api-client ──HTTP──> apps/api ──> @caau/database
```

禁止：

- 从 `apps/miniapp`、`apps/admin` 或 `apps/api` 相对导入源码；
- 前端引入 `@caau/database`、Prisma、NestJS、服务端密钥；
- 复制生成客户端或手写与 OpenAPI 平行的业务实体；
- 在 Taro 环境变量、构建产物或日志中放 AppSecret。

B 阶段接入时需把新应用加入 `scripts/check-boundaries.mjs` 的受检单元及前端集合；根级递归 build/typecheck/test、格式检查和小程序构建产物检查也要明确覆盖两个小程序，不能默认现有脚本已完整覆盖。

## 10. 分阶段验收计划

### A 阶段：现状核对、规格与设计（本轮）

- 核对 Team、TeamMembership、EventTeam、微信身份与赛事信息事实。
- 交付页面清单、权限矩阵、接口差距、数据兼容、架构决策和集中待确认问题。
- 只检查文档链接、格式和差异；不新增应用、接口、迁移或依赖。

### B 阶段：身份、关系和公开赛事后端

建议先确认业务问题，再实施前向迁移、球队端多 AppID 认证、建档/邀请/认领、公开发布/下架、公开检索和资格独立响应。验收应覆盖跨 AppID 不自动合并、邀请不可重放、越权拒绝、无角色扩张、历史数据兼容、CAS、下架即时生效和敏感字段不出契约。

### C 阶段：独立小程序工程与页面

建立 `apps/team-miniapp`，接入生成客户端，完成三 tab、登录、建档/认领、档案维护、赛事列表/详情及各种失败状态。验证独立构建目录、边界检查、两小程序互不覆盖、模拟器响应式和无敏感日志。

### D 阶段：外部报名集成（接口提供后另立项）

确认外部系统权威字段、赛事 ID 映射、跳转/授权、资格、错误恢复和隐私后再实现。不在 B/C 阶段预留一个可误认为已可报名的假按钮。

### E 阶段：正式微信与生产验收

为球队端独立提供 AppID、AppSecret、合法 HTTPS 域名、项目成员和测试微信号；分别验证开发者工具正式项目与真机登录、跨 AppID 关联、新建/认领、会话撤销和下架。补做生产密钥、TLS、可信代理、多实例限流、监控、备份恢复及独立安全评审。本地注入交换器不能替代本阶段。

## 11. 必须确认的业务问题

以下问题集中等待产品/业务确认，实施时不得把建议直接写成规则：

1. 是否要求登录后才能浏览公开赛事，还是允许未登录访客浏览？
2. 新微信用户能否立即自助创建球队并生效，还是需总部审核、邀请码或其他准入？
3. 自助建档的正式必填字段是什么；现有负责人和联系电话是否对其他球队成员可见？
4. 一个用户能管理几支球队，一支球队允许几个 OWNER/MANAGER；是否需要只读成员？
5. 新建球队与库中疑似同名球队冲突时，是允许继续创建、要求认领，还是进入人工核对？
6. 尚无成员的历史球队，由总部、原录入机构还是其他主体发起邀请/批准认领？
7. 已有成员的球队由谁邀请、撤销成员和转让唯一 OWNER；最后一名 OWNER 如何保护？
8. 被归档球队能否被认领、恢复或继续登录查看？
9. 现有 `TeamMembership.active=true` 数据应映射为 OWNER、MANAGER 还是逐条人工确认？
10. 同一自然人已有承办方账号时，允许关联到同一个 `InternalUser`，还是要求业务隔离？由哪种已登录会话或管理员动作证明关联？
11. 没有密码账号的球队用户如何恢复、更换或解绑微信；丢失微信后的人工核验责任方是谁？
12. 总部发布赛事的正式公开字段、发布人、复核机制、下架原因及已下架详情可见期限是什么？
13. 哪个系统是报名起止时间、组别、地区和资格规则的权威来源？现有办赛材料中的时间能否进入公开赛事仍需确认。
14. “当前可报名”的精确定义是什么：仅时间窗口，还是还受暂停、名额、外部系统可用性影响？
15. 球队资格首版依据哪些字段和规则；规则缺失时页面文案采用“待核验”还是不显示？
16. 外部报名小程序未来采用小程序跳转、H5、二维码还是服务端 API；赛事与球队 ID 如何映射？
17. 是否允许公开承办机构名称、场馆详细地址和报名联系人；手机号等字段的最小披露范围是什么？
18. 产品名中的“智能体”首版只作为品牌名称，还是有已确认的智能能力？本轮按用户指令不做 AI 对话。
