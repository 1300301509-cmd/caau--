# CAAU 智能体球队端小程序（CAAU-046）

状态：A 阶段产品规格与技术设计；首版账号—球队、赛事展示及报名窗口管理规则已确认，尚未编码。文中未列入“已确认规则”的建议与待确认项不构成业务规则。

## 1. 目标与首版边界

新增独立微信小程序“CAAU 智能体球队端”，建议工程目录为 `apps/team-miniapp`，使用独立构建产物和独立 AppID。首版只覆盖：

1. 球队用户建立、查看和维护自己有权管理的球队基础档案。
2. 检索对球队公开且当前开放报名的赛事，并查看经过明确白名单裁剪的公开详情。

建议一级页面为【找比赛】【我的球队】【我的】。报名提交、支付、订单继续由原外部小程序负责；外部接口提供并确认前，不实现报名动作或伪造跳转闭环。本阶段不做 AI 对话、球员名单或球员敏感资料采集。

球队端复用同一个 API、PostgreSQL、`@caau/api-client`、`InternalUser`、`Team` 和 `TeamMembership`，不复制球队库。球队用户不因使用本应用获得 `ORGANIZER`、赛事管理、审核或承办申请权限。

### 1.1 已确认的首版账号—球队规则

1. 一个球队账号只管理一支球队。
2. 用户填写全部必填资料后立即建档，之后可以编辑。
3. 建档只表示球队主档案和账号绑定已建立，不表示总部认证、赛事报名或参赛资格通过。
4. 首版不开发成员管理、成员邀请、关系角色分配、负责人转移或历史球队认领。
5. 账号与球队的唯一绑定由后端维护；每次读取和修改都按当前认证用户复核，不接受客户端传入其他球队作为授权依据。
6. 重复点击或网络重试必须幂等，不得为同一账号创建第二支球队。
7. 不按名称或手机号自动绑定历史球队；认领流程后置到独立阶段。

### 1.2 已确认的首版赛事展示规则

1. 只有持有赛事发布权限的总部人员可以手动发布和下架赛事；前端按钮不是权限边界。
2. 球队端列表、检索和详情只读取当前已发布的公开版本。
3. 承办申请获批、批准办赛、赛程发布及其他内部状态变化都不得自动公开赛事。
4. 下架后，公开列表、检索和详情接口都必须停止提供该赛事的公开内容；不能只在前端隐藏入口或继续允许旧详情深链访问。
5. 公开接口使用独立 DTO 和字段白名单，禁止返回内部申请附件、银行账户、审核记录及非公开联系方式。
6. 每次发布和下架都保留实际操作人、服务器时间、动作及对应版本记录，不覆盖历史。

### 1.3 已确认的首版报名窗口规则

1. 承办方可填写报名开始、截止时间并提交总部审核；提交值只有总部同意后才能成为当前生效窗口。
2. 持有相应赛事管理权限的总部人员可直接填写或修改生效窗口，无需承办方再次确认。
3. 待审核候选值与当前生效窗口分开保存，任何待审核内容不得覆盖当前值。
4. 球队端只读取当前生效窗口，并由 API 使用服务器时间计算报名状态，不信任客户端时钟或客户端自行推导的权威状态。
5. 总部直接修改须保存实际操作人、服务器时间及修改前后的完整窗口值。
6. 报名窗口生效与赛事公开发布相互独立；没有已发布公开版本时，球队端仍不得查看赛事。
7. 现有获批办赛材料中的 `registrationStart`/`registrationEnd` 优先作为初始生效窗口来源，不重复要求承办方填写，也不建立第二套权威当前值。

### 2.2 当前不能满足首版的部分

1. `Team.organizationId` 当前必填且语义是录入机构；球队自行建档没有合理的承办机构可挂靠，不能创建虚假机构或借用承办方。
2. `TeamMembership` 当前只有 `teamId + userId` 唯一约束，没有“一个用户最多绑定一支球队”的数据库约束；数据库运行账号当前仅获其读取权限，也没有自助建档时受控创建绑定的流程。
3. 现有 `POST /teams` 要求调用人是总部超级管理员，或是目标机构的 `ORGANIZER/EVENT_MANAGER`；普通球队用户无法自助建档。
4. 现有球队列表未做服务端分页/检索，且 DTO 混合总部录入字段、内部备注和球队自维护字段；不应原样暴露给球队端。
5. 当前微信配置只有一组 AppID/AppSecret；登录及绑定明确要求有效 `ORGANIZER`，无法给无承办方角色的球队用户使用。
6. 当前微信绑定凭证只能由承办方密码 Web 会话创建；球队端没有适合无承办方角色用户的首次微信身份建立流程。
7. `EventLifecycleState` 目前只有 `PREPARING_INTERNAL`；没有赛事公开发布、下架、公开版本或报名开放状态。
8. 现有 `/events` 是内部授权列表，不是公开目录；返回的 profile 结构未形成稳定公开契约。
9. 办赛材料已将 `registrationStart`/`registrationEnd` 保存到不可变提交，并由总部整套审核；但材料通过目前只更新材料状态，不会投影为赛事级当前生效窗口，球队端没有稳定读取入口。
10. 当前没有独立的承办方窗口变更申请、总部直接修改、当前值版本或防旧申请覆盖机制。
11. 现有 API 不能分别表达“赛事当前可报名”和“某支球队是否符合资格”。

## 3. 核心产品流程

### 3.1 首次进入与微信身份

建议流程：同意服务协议和隐私政策 → `wx.login` → API 按球队端 AppID 交换 OpenID → 恢复已绑定的 `InternalUser` → 查询该账号唯一的球队绑定；无球队时进入新建档流程，有球队时进入工作区。

- OpenID 只由服务端通过微信接口取得，不接受客户端提交。
- 新 AppID 下的 OpenID 与承办方小程序 OpenID不同；不得仅凭昵称、手机号、姓名或 UnionID 自动合并用户。
- 已有 `InternalUser` 如需复用，应通过一次性跨应用关联凭证、已有密码会话或管理员定向动作来证明控制权，再把新 AppID 的 `WechatIdentity` 绑定到同一用户。
- 无既有账号的用户可在完成微信校验后建立受限的 `InternalUser`；提交完整必填球队资料时，再建立该用户唯一的球队绑定。
- 微信身份绑定只证明“这个微信属于该用户”；后端维护的 `TeamMembership` 才证明“该用户可以管理这支球队”，两者不得合并为隐式规则。

### 3.2 新球队建档

用户填写全部必填资料后提交，建档立即生效并可继续编辑。服务端必须在一个事务中创建：

1. 新球队主档案；
2. 初始不可变版本；
3. 当前用户与该球队的唯一绑定；
4. 审计记录。

创建用例必须同时使用数据库唯一约束和幂等请求标识：同一账号重复点击、客户端超时重试或两个并发请求只能得到同一球队；如果账号已经绑定球队，服务端返回该球队或明确冲突，不得创建第二支。客户端生成的 teamId 不能作为绕过账号唯一绑定的依据。

同名、相同联系人或相同手机号可以做核对提示，但不自动合并、认领或转移历史球队。首版字段沿用现有名称、负责人、联系方式、省、市及现有选填字段作为兼容候选；正式必填字段清单仍需确认。

建档成功页及球队详情必须明确说明“已建档，不代表总部认证或参赛资格通过”，不得使用“认证成功”“审核通过”或“获得参赛资格”等文案。

### 3.3 历史球队认领与成员管理（首版排除）

首版不提供历史球队认领、成员邀请、成员列表、角色分配、多人协作或负责人转移入口，也不建设对应写接口。数据库中既有球队不会因新账号的名称或手机号相似而自动绑定。未来认领必须另立项设计稳定 teamId、控制权证明、冲突处理与审计，且不得改写历史 `TeamVersion`、`EventTeam` 或 `EventTeamRoster`。

### 3.4 球队档案维护

【我的球队】首版只呈现当前账号唯一绑定的球队，不作为多球队列表。读取和更新目标由服务端根据认证用户解析；即使客户端篡改 teamId，也必须拒绝跨球队访问。更新携带 `expectedRevision`；409 时重新读取权威版本并保留本地输入供核对，不做最后写入覆盖。成员管理、负责人转移、球队合并及认领先后置。

### 3.5 赛事发布与找比赛

持有明确赛事发布权限的总部人员在总部端手动形成公开版本并发布，或手动下架。服务端在每次动作时重新校验当前人员、总部身份和赛事发布权限；申请审核权、赛事查看权、赛程发布权或其他内部权限不得隐式派生赛事公开权限。具体哪些总部岗位取得该权限仍需确认。

申请获批、批准办赛、办赛材料通过、赛程发布及其他内部状态变化只更新各自业务域，不调用赛事公开发布命令。只有显式发布动作可以使公开版本对球队端可见。

球队端列表、检索和详情只查询当前 `publicationStatus=PUBLISHED` 的公开投影，不调用内部 `/events`。下架事务生效后，列表和检索不再返回该赛事，详情接口对旧 eventId、收藏或深链也不再返回公开内容；前端可清除缓存并显示已下架，但不能以隐藏入口代替服务端限制。

首版“找比赛”还要求赛事当前开放报名，因此列表在已发布基础上再按 `registrationState=OPEN` 筛选。详情至少可候选展示名称、日期、公开地点、公开说明、公开组别/类别、报名窗口和外部报名提示；正式白名单字段仍需确认，不能从内部 Event、申请或办赛材料中整包透传。

响应必须并列表达：

- `registrationState`：赛事层面的 `NOT_OPEN / OPEN / CLOSED / SUSPENDED`；
- `eligibility.status`：针对所选球队的 `NOT_EVALUATED / UNKNOWN / ELIGIBLE / INELIGIBLE`；
- `eligibility.reasonCodes`：可机器处理的原因码，公开文案另行映射。

“OPEN”只代表报名窗口开放，不代表当前球队符合资格。“UNKNOWN/NOT_EVALUATED”不得显示为“可报名”。外部报名接口未接入前，页面只说明报名渠道尚未接入，不提交报名、订单或支付数据。

### 3.6 报名窗口维护与旧申请失效

赛事级报名窗口使用一个独立的当前聚合保存唯一生效值：`eventId`、开始/截止时间、revision、来源类型及来源记录。承办方提交的是候选变更请求，请求保存候选时间及提交时的 `baseWindowRevision`；提交或审核期间，当前生效窗口保持不变。

总部同意候选请求时必须在同一事务内锁定当前窗口和请求，并同时满足：请求仍为待审核状态、`baseWindowRevision` 等于当前 revision、审核人具有当前赛事权限。成功后当前 revision 严格递增、写入生效版本并结束请求。任一条件不满足返回 409，不能把候选值重放到新窗口上。

总部直接修改也锁定当前窗口，携带 `expectedRevision` 并在同一事务内：

1. 写入修改前后的完整时间值、实际操作人和服务器时间；
2. 递增当前窗口 revision；
3. 将基于旧 revision 的待审核/审核中请求标记为 `SUPERSEDED`（已失效），记录失效原因和触发该修改的总部人员；
4. 提交事务后才对球队端可见。

双重保护用于防止旧申请覆盖：直接修改会主动失效旧请求；即使遗漏、延迟任务或并发审核再次尝试，审核事务的 `baseWindowRevision` CAS 仍会失败。系统不得自动把旧请求“换基准”到新 revision，也不得提供忽略冲突的强制通过；承办方如仍需修改，必须读取最新生效窗口后重新提交新请求。

现有获批办赛材料作为初始来源：材料审核通过时，若赛事尚无生效窗口，则从该获批不可变提交中投影报名起止时间并记录 `sourceSubmissionId`；若总部已直接建立了更新的生效窗口，则材料批准不得反向覆盖。迁移历史已获批材料时同样只为“尚无当前窗口”的赛事初始化，并以来源唯一约束防止重复应用。后续窗口变更使用独立请求和同一个当前聚合，不重新提交营业执照、银行账户等整套材料。

球队端 API 只返回当前生效窗口和由服务器当前时间计算出的 `registrationState`。窗口变更生效但赛事未发布时，公开接口仍不返回赛事；赛事已发布但没有生效窗口时如何展示仍列为待确认问题。

| 已绑定球队账号       | 是                       | 否；重复请求返回既有结果或冲突   | 仅服务端解析出的唯一绑定球队               | 否             | 否             | 否             |
| 历史录入机构成员     | 沿现有内部权限           | 沿现有内部权限，不属于球队端流程 | 沿现有内部权限，不由球队端规则扩大或缩小   | 首版无新能力   | 沿赛事权限     | 仅原有授权范围 |
| 总部超级管理员       | 是                       | 沿现有管理能力                   | 沿现有管理能力                             | 首版不新增流程 | 沿现有赛事权限 | 沿原有授权     |
| 承办方经办人         | 是                       | 不因球队端扩权                   | 仅沿现有录入范围，不自动取得球队账号的绑定 | 否             | 沿原有赛事权限 | 沿原有授权     |

首版不引入 OWNER/MANAGER/VIEWER 等球队关系角色。所有球队端接口以后端维护的账号—球队唯一绑定为边界，前端隐藏按钮或客户端提交的 teamId 不构成授权。

赛事公开写权限仅授予具有明确赛事发布权限的总部人员；球队账号、承办方，以及仅有审核权、赛事查看权或赛程发布权的人员均不得据此发布或下架。具体总部角色/grant 分配仍待确认，但后端必须按每次请求校验，不以总部页面可见性代替。

报名窗口候选提交限于当前赛事有效承办方；提交不授予生效权限。总部同意候选及直接修改要求相应赛事管理权限，二者均逐请求复核。球队账号只能通过公开接口读取已发布赛事的当前生效窗口和服务器计算状态，不能读取待审核候选、驳回原因或内部窗口历史。

## 6. 公开字段与禁止字段

公开赛事 DTO 必须使用明确 allowlist 和独立查询，不返回内部 Event 实体、任意 profile JSON 或先返回整包再由前端删字段。首版候选公开字段：赛事 ID、公开标题、公开摘要、开始/结束日期、公开地区/场馆文本、报名起止时间、公开组别/类别、公开版本和发布时间；正式字段仍需逐项确认。

以下信息禁止进入球队端公开响应：

- 承办申请及办赛材料附件、营业执照和内部场地文件；
- 银行账户、合同及线下确认；
- 申请人/审核人身份、审核意见、原因和审核记录；
- 内部备注、审计上下文、grant 和机构内部关系；
- 未明确列入公开白名单的手机号、联系人及其他联系方式；
- 私有对象键、内部下载地址或内部版本 JSON。

公开版本只保存可公开字段快照及必要发布元数据。发布/下架操作历史属于总部内部记录，不随公开详情返回。

## 7. 接口差距

### 7.1 建议新增的球队端接口

以下仅为设计草案，路径和字段在 B 阶段契约评审后确定：

| 用例           | 建议能力                                                             | 现状                                        |
| -------------- | -------------------------------------------------------------------- | ------------------------------------------- |
| 球队端认证模式 | 按 client/app key 返回球队端微信能力                                 | 当前只有全局单 AppID 能力位                 |
| 微信登录/注册  | 按球队端 AppID 交换 code，恢复或建立受限主体                         | 当前只允许 active organizer                 |
| 跨 AppID 关联  | 创建并兑换目标 AppID 的一次性关联 intent                             | 当前 intent 绑定单一承办方 AppID 和密码会话 |
| 我的球队       | 由服务端按账号返回零个或唯一绑定球队                                 | 当前 `listTeams` 是无分页的内部工作台列表   |
| 自助建档       | 幂等、原子创建 Team、版本和账号唯一绑定                              | 当前依赖录入机构且无 userId 唯一约束        |
| 球队详情/更新  | 球队端专用 DTO、服务端解析绑定、字段白名单及 CAS                     | 当前更新逻辑可参考，但允许客户端指定任意 id |
| 总部发布/下架  | 仅赛事发布权限可调用，显式动作、CAS/幂等并记录实际操作人、时间和版本 | 当前无赛事公开写接口                        |
| 发布历史       | 总部授权读取发布/下架动作及不可变版本，不进入球队端公开 DTO          | 当前无公开版本历史                          |
| 窗口候选提交   | 承办方基于当前 revision 提交起止时间供总部审核                       | 当前时间只随整套办赛材料提交                |
| 窗口审核       | 总部同意时校验请求状态及 base revision，过期请求返回 409             | 当前没有独立窗口审核                        |
| 窗口直接修改   | 有赛事管理权限总部人员以 CAS 修改当前值并失效旧请求                  | 当前没有赛事级生效窗口                      |
| 窗口历史       | 授权方读取来源、前后值、实际操作人、服务器时间和 revision            | 当前只能查看材料提交/审核历史               |
| 公开赛事检索   | 仅返回当前已发布投影，支持服务端分页筛选                             | 当前只有内部授权 `/events`                  |
| 公开赛事详情   | 仅当前已发布时返回公开版本和报名状态，下架后停止提供                 | 当前无公开发布版本                          |
| 球队资格       | 对 `teamId + eventId` 返回独立资格结果                               | 当前无规则或接口                            |

### 7.2 不应复用为球队端接口的现有能力

- 不直接开放内部 `/events`、承办申请、办赛材料或私有附件接口。
- 不允许球队用户调用 `POST /events/:eventId/teams`；该接口代表把主档案加入赛事，并非报名。
- 不把 `EventTeam.active` 当作报名状态，也不从它反推球队资格。
- 不把申请获批、批准办赛、办赛材料通过或赛事赛程 `PUBLISHED` 当作赛事公开发布；各自生命周期独立且不得自动调用发布命令。
- 不用 `ORGANIZER` 角色绕过球队关系校验或取得赛事发布权限。
- 不在下架后继续通过公开详情接口返回最后版本，也不只依赖客户端过滤、缓存失效或隐藏入口。
- 不让待审核窗口覆盖当前值，不从客户端时钟计算权威报名状态，也不让旧请求在总部直接修改后重新覆盖。
- 不把报名窗口生效当作赛事发布；公开可见性和报名状态分别判断。

## 8. 数据兼容方案

### 8.1 保留与扩展

1. `Team.id`、现有 profile、revision、版本和所有 `EventTeam` 关系原样保留，不复制或回填新表副本。
2. 将现有必填 `organizationId` 的语义演进为可空的“历史录入机构/来源机构”（最终字段命名待迁移设计）；旧数据值保持不变，自助创建不伪造机构。
3. 以 `TeamMembership` 或等价的一对一绑定作为账号—球队权限锚点，并增加数据库层的 userId 唯一保证；迁移前必须检查既有用户是否关联多个不同 teamId（无论当前 active 状态），发现冲突时阻断并人工处理，不静默选择或删除。
4. 自助建档在同一事务内写入 Team、TeamVersion、唯一绑定和审计，并使用账号唯一约束及幂等请求标识抵御重复点击和并发创建。
5. 首版不增加成员角色、邀请、负责人转移或历史球队认领模型；这些能力后置时另做迁移和权限设计。
6. `WechatIdentity` 继续关联同一 `InternalUser`；保留 `appId` 作用域唯一约束。服务端配置从单 AppID 演进为受控客户端注册表，每个 AppID 独立 Secret、用途和允许的认证流程。
7. `Session` 建议记录逻辑客户端或 AppID 作用域，以支持按应用撤销、审计和风控；是否新增 client enum 或 client registration 外键在 B 阶段决定。
8. 新增独立赛事公开发布聚合及不可变公开版本；发布时从已确认字段生成 allowlist 快照，不让球队端查询内部 profile JSON。聚合保存当前发布状态和版本号，版本/动作历史保存实际操作人、服务器时间、动作与公开字段快照，禁止覆盖历史。
9. 发布和下架由同一赛事公开聚合以事务、CAS 和幂等命令处理；发布权限后端逐请求校验。申请、办赛批准和赛程模块不得直接写公开状态。
10. 新增赛事级唯一当前报名窗口、不可变窗口版本及候选变更请求。候选请求保存 `baseWindowRevision`；当前窗口版本保存来源类型（获批材料、承办方获批变更或总部直接修改）、可空 `sourceSubmissionId/sourceRequestId`、前后值、实际操作人和服务器时间。
11. 获批材料投影使用 `materialEventId + approved submissionId` 作为来源，来源只能应用一次；仅在不存在当前窗口时初始化。后续所有入口读写同一个当前聚合，不另建“材料窗口”和“球队端窗口”两套当前值。
12. 总部直接修改和候选批准都锁定当前窗口并使用 revision/CAS；直接修改同步把旧基准待审请求变为 `SUPERSEDED`，审批端再次以 base revision 复核，形成主动失效加提交时拒绝的双重保护。
13. 球队端报名状态由 API 使用服务器时间与当前生效窗口计算；响应可以包含生效起止时间和状态，但不暴露待审请求或内部版本历史。具体边界时刻语义和时区展示仍需确认。
14. 报名状态与资格结果分开存储或计算；没有权威资格规则时返回 `NOT_EVALUATED/UNKNOWN`，不伪造合格。

### 8.2 不变式

- 修改 Team 不自动更新任何 EventTeam 或 roster。
- 首版不认领历史 Team；未来认领也不得改变历史比赛资料、录入机构、创建人或历史操作者。
- 下架赛事不删除 Event、EventTeam、赛程或历史公开版本，但公开列表、检索和详情查询都不再返回内容。
- 待审核报名窗口永不参与球队端状态计算；总部直接修改后，基于旧 revision 的请求不能批准或自动重放。
- 窗口生效不改变赛事公开状态，赛事发布/下架也不改写窗口版本。
- 同一微信在不同 AppID 下的 OpenID 不相等也不要求相等；UnionID 只能用于提示/风控，不能自动合并。
- 球队端会话不派生组织角色、EventGrant 或承办申请 grant。

## 9. 应用与依赖设计

`apps/team-miniapp` 应为独立 workspace 应用，拥有自己的 `package.json`、Taro 配置、页面配置、测试、`project.config.json` 和输出目录。建议包名 `@caau/team-miniapp`，项目名与构建产物不得覆盖 `@caau/miniapp`。

依赖方向：

```text
apps/team-miniapp ──> @caau/api-client ──HTTP──> apps/api ──> @caau/database
```

禁止：

- 从 `apps/miniapp`、`apps/admin` 或 `apps/api` 相对导入源码；
- 前端引入 `@caau/database`、Prisma、NestJS、服务端密钥；
- 复制生成客户端或手写与 OpenAPI 平行的业务实体；
- 在 Taro 环境变量、构建产物或日志中放 AppSecret。

B 阶段接入时需把新应用加入 `scripts/check-boundaries.mjs` 的受检单元及前端集合；根级递归 build/typecheck/test、格式检查和小程序构建产物检查也要明确覆盖两个小程序，不能默认现有脚本已完整覆盖。

## 10. 分阶段验收计划

### A 阶段：现状核对、规格与设计（本轮）

- 核对 Team、TeamMembership、EventTeam、微信身份与赛事信息事实。
- 交付页面清单、权限矩阵、接口差距、数据兼容、架构决策和集中待确认问题。
- 只检查文档链接、格式和差异；不新增应用、接口、迁移或依赖。

### B 阶段：身份、唯一绑定和公开赛事后端

建议先确认剩余业务问题，再实施前向迁移、球队端多 AppID 认证、单账号单球队绑定、幂等即时建档、公开发布/下架、公开检索和资格独立响应。验收必须覆盖：

- 必填资料不完整时拒绝建档且不产生 Team、版本或绑定；完整后立即创建可编辑档案，但响应不声称总部认证或参赛资格通过；
- 同一账号顺序重复、超时重试和并发建档都只产生一个 Team、一份首版本和一个绑定；
- 数据库约束禁止同一账号绑定第二支球队，失败事务不遗留孤立 Team；
- 服务端按认证用户解析唯一球队，篡改 teamId、跨账号及跨球队读取/更新均拒绝；
- 名称或手机号相同不触发历史球队绑定；没有认领、邀请、角色或转移接口；
- 只有有效赛事发布权限的总部人员可以发布/下架；无该权限的总部人员、仅有审核权者、承办方和球队账号均拒绝，权限撤销后下一次请求立即拒绝；
- 申请获批、批准办赛、办赛材料通过和赛程发布均不产生公开版本，只有显式发布成功后列表与详情可见；
- 发布后公开列表、检索和详情返回同一当前版本；下架事务成功后，三类接口及旧详情深链均停止提供公开内容；
- 每次发布/下架保留实际操作人、服务器时间、动作和版本；历史不可改删，并覆盖重复命令、并发发布/下架和旧 revision 冲突；
- 使用契约级字段白名单和反例响应测试，确保内部申请附件、银行账户、审核记录、非公开联系方式及内部 JSON 不进入公开接口；
- 现有办赛材料 Vn 获批后，仅在无当前窗口时以其不可变报名时间初始化一次；重复审批命令/迁移不重复建版本，已有总部新值不被材料来源覆盖；
- 承办方提交候选后，当前窗口和球队端状态不变；总部同意后才原子生效，退回或拒绝保持原值；
- 有相应赛事管理权限的总部人员可直接 CAS 修改，无权限、失权或旧 expectedRevision 均拒绝；历史准确记录前后值、实际操作人和服务器时间；
- 构造候选 R1 基于窗口 V1，随后总部直接修改到 V2：R1 在同一事务中变为 `SUPERSEDED`；即使并发审批、重放旧命令或绕过列表直接调用，base revision 校验仍返回 409，V2 不变；
- 反向竞态中若 R1 先批准为 V2，总部仍以 V1 发起直接修改则返回 409，必须读取 V2 后明确重试，不能静默覆盖；
- 待审核值不进入公开 DTO；球队端状态由可控服务器时间边界测试验证，客户端伪造时间不改变结果；窗口生效但赛事未发布时仍不可见；
- 跨 AppID 不自动合并、无组织角色扩张、旧数据迁移冲突阻断、球队资料 CAS 和公开敏感字段隔离。

### C 阶段：独立小程序工程与页面

建立 `apps/team-miniapp`，接入生成客户端，完成三 tab、登录、即时建档、唯一球队档案维护、赛事列表/详情及各种失败状态。验证重复点击只有一次创建请求结果、建档后显示非认证/非资格提示、无认领或成员管理入口；赛事下架后刷新列表消失，已打开详情或旧深链重新请求显示不可用且不残留公开内容；报名状态只渲染 API 返回结果，不使用设备时间覆盖。配套端验证承办方提交后仍显示当前生效值与待审候选、总部直接修改后旧候选明确显示已失效。另验证独立构建目录、边界检查、两小程序互不覆盖、模拟器响应式和无敏感日志。

### D 阶段：外部报名集成（接口提供后另立项）

确认外部系统权威字段、赛事 ID 映射、跳转/授权、资格、错误恢复和隐私后再实现。不在 B/C 阶段预留一个可误认为已可报名的假按钮。

### E 阶段：正式微信与生产验收

为球队端独立提供 AppID、AppSecret、合法 HTTPS 域名、项目成员和测试微信号；分别验证开发者工具正式项目与真机登录、跨 AppID 关联、幂等新建、唯一球队隔离、会话撤销和下架。补做生产密钥、TLS、可信代理、多实例限流、监控、备份恢复及独立安全评审。本地注入交换器不能替代本阶段。

## 11. 必须确认的业务问题

以下问题集中等待产品/业务确认，实施时不得把建议直接写成规则：

1. 是否要求登录后才能浏览公开赛事，还是允许未登录访客浏览？
2. 自助建档的正式必填字段是什么；负责人和联系电话在球队端如何展示和保护？
3. 新建球队与库中疑似同名球队并存时，除明确提示外是否需要后台重复记录队列？首版不能自动认领。
4. 已绑定球队归档后，账号能否继续查看或恢复；仍不得改绑或再建第二支球队，除非未来另立规则。
5. 现有数据如发现同一 `InternalUser` 关联多个不同 teamId（包括非 active 关系），由谁人工裁决；迁移不得静默选择。
6. 同一自然人已有承办方账号时，允许关联到同一个 `InternalUser`，还是要求业务隔离？由哪种已登录会话或管理员动作证明关联？
