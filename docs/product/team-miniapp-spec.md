# CAAU 智能体球队端小程序（CAAU-046）

状态：A 阶段产品规格与技术设计；首版账号—球队、赛事展示及报名窗口管理规则已确认，尚未编码。文中未列入“已确认规则”的建议与待确认项不构成业务规则。

## 1. 目标与首版边界

新增独立微信小程序“CAAU 智能体球队端”，建议工程目录为 `apps/team-miniapp`，使用独立构建产物和独立 AppID。首版只覆盖：

1. 球队用户建立、查看和维护自己有权管理的球队基础档案。
2. 检索总部已发布赛事，按报名状态等条件筛选并查看经过明确白名单裁剪的公开详情。

建议一级页面为【找比赛】【我的球队】【我的】。报名提交、支付、订单继续由原外部小程序负责；外部接口提供并确认前，不实现报名动作或伪造跳转闭环。本阶段不做 AI 对话、球员名单或球员敏感资料采集。

球队端复用同一个 API、PostgreSQL、`@caau/api-client`、`InternalUser`、`Team` 和 `TeamMembership`，不复制球队库。球队用户不因使用本应用获得 `ORGANIZER`、赛事管理、审核或承办申请权限。

### 1.1 已确认的首版账号—球队规则

1. 一个球队账号只管理一支球队。
2. 用户填写全部必填资料后立即建档，之后可以编辑。
3. 建档只表示球队主档案和账号绑定已建立，不表示总部认证、赛事报名或参赛资格通过。
4. 首版不开发成员管理、成员邀请、关系角色分配、负责人转移或历史球队认领。
5. 账号与球队的唯一绑定由后端维护；每次读取和修改都按当前认证用户复核，不接受客户端传入其他球队作为授权依据。
6. 重复点击或网络重试必须幂等，不得为同一账号创建第二支球队。
7. 不按名称或手机号自动绑定历史球队；认领流程后置到独立阶段。

### 1.2 已确认的首版赛事展示规则

1. 只有持有赛事发布权限的总部人员可以手动发布和下架赛事；前端按钮不是权限边界。
2. 球队端列表、检索和详情只读取当前已发布的公开版本。
3. 承办申请获批、批准办赛、赛程发布及其他内部状态变化都不得自动公开赛事。
4. 下架后，公开列表、检索和详情接口都必须停止提供该赛事的公开内容；不能只在前端隐藏入口或继续允许旧详情深链访问。
5. 公开接口使用独立 DTO 和字段白名单，禁止返回内部申请附件、银行账户、审核记录及非公开联系方式。
6. 每次发布和下架都保留实际操作人、服务器时间、动作及对应版本记录，不覆盖历史。

### 1.3 已确认的首版报名窗口规则

1. 承办方只填写现有七项办赛材料中的报名开始、截止时间，不增加独立窗口表单或要求重复填写。
2. 总部通过整套材料时，在同一事务内批准并生效该不可变提交版本的报名窗口；未能生效时整套材料也不能被标记为通过。
3. 草稿、待审核、审核中和退回补充版本中的时间都不是当前生效值，不影响球队端状态。
4. 持有相应赛事管理权限的总部人员可直接填写或修改生效窗口，无需承办方再次确认，并保留修改历史。
5. 球队端只读取当前生效窗口，并由 API 使用服务器时间计算“报名未开始 / 报名中 / 报名结束”，不信任客户端时钟。
6. 报名窗口生效与赛事公开发布相互独立；没有已发布公开版本时，球队端仍不得查看赛事。
7. 材料审核通过与总部直接修改竞争同一个窗口 revision；发现已被另一操作更新时返回冲突并提示核对，不允许静默覆盖。

### 1.4 已确认的首版赛事目录范围

已发布赛事的球队端公开详情只包含：

- 赛事名称；
- 总部确认的比赛开始/结束日期、城市和场馆；
- 承办机构名称；
- 当前生效的报名开始/截止时间及服务器计算的报名状态；
- 总部确认的赛事介绍、参赛组别和参赛要求；
- 为公开场景单独配置的咨询联系方式。

目录支持按赛事名称、地区、比赛日期和报名状态筛选。公开咨询联系方式是独立公开字段，不从办赛材料联系人、申请人、机构成员或其他内部手机号自动复制。参赛组别和要求首版只用于展示，不形成资格规则；球队建档或赛事显示“报名中”都不表示报名成功。外部报名未接入前不提供提交、占位、预约、支付或其他伪报名功能。只有当前已发布赛事可见，内部附件、银行账户和审核历史不得进入响应。

### 2.2 当前不能满足首版的部分

1. `Team.organizationId` 当前必填且语义是录入机构；球队自行建档没有合理的承办机构可挂靠，不能创建虚假机构或借用承办方。
2. `TeamMembership` 当前只有 `teamId + userId` 唯一约束，没有“一个用户最多绑定一支球队”的数据库约束；数据库运行账号当前仅获其读取权限，也没有自助建档时受控创建绑定的流程。
3. 现有 `POST /teams` 要求调用人是总部超级管理员，或是目标机构的 `ORGANIZER/EVENT_MANAGER`；普通球队用户无法自助建档。
4. 现有球队列表未做服务端分页/检索，且 DTO 混合总部录入字段、内部备注和球队自维护字段；不应原样暴露给球队端。
5. 当前微信配置只有一组 AppID/AppSecret；登录及绑定明确要求有效 `ORGANIZER`，无法给无承办方角色的球队用户使用。
6. 当前微信绑定凭证只能由承办方密码 Web 会话创建；球队端没有适合无承办方角色用户的首次微信身份建立流程。
7. `EventLifecycleState` 目前只有 `PREPARING_INTERNAL`；没有赛事公开发布、下架、公开版本或报名开放状态。
8. 现有 `/events` 是内部授权列表，不是公开目录；返回的 profile 结构未形成稳定公开契约。
9. 办赛材料已将 `registrationStart`/`registrationEnd` 保存到不可变提交，并由总部整套审核；但材料通过目前只更新材料状态，不会投影为赛事级当前生效窗口，球队端没有稳定读取入口。
10. 当前材料提交没有记录窗口基准 revision，材料批准与总部直接修改也没有共享同一 CAS，因此尚不能安全处理并发。
11. 当前没有总部直接修改窗口、窗口版本或历史接口。
12. 现有 API 不能分别表达“赛事当前可报名”和“某支球队是否符合资格”。

## 3. 核心产品流程

### 3.1 首次进入与微信身份

建议流程：同意服务协议和隐私政策 → `wx.login` → API 按球队端 AppID 交换 OpenID → 恢复已绑定的 `InternalUser` → 查询该账号唯一的球队绑定；无球队时进入新建档流程，有球队时进入工作区。

- OpenID 只由服务端通过微信接口取得，不接受客户端提交。
- 新 AppID 下的 OpenID 与承办方小程序 OpenID不同；不得仅凭昵称、手机号、姓名或 UnionID 自动合并用户。
- 已有 `InternalUser` 如需复用，应通过一次性跨应用关联凭证、已有密码会话或管理员定向动作来证明控制权，再把新 AppID 的 `WechatIdentity` 绑定到同一用户。
- 无既有账号的用户可在完成微信校验后建立受限的 `InternalUser`；提交完整必填球队资料时，再建立该用户唯一的球队绑定。
- 微信身份绑定只证明“这个微信属于该用户”；后端维护的 `TeamMembership` 才证明“该用户可以管理这支球队”，两者不得合并为隐式规则。

### 3.2 新球队建档

用户填写全部必填资料后提交，建档立即生效并可继续编辑。服务端必须在一个事务中创建：

1. 新球队主档案；
2. 初始不可变版本；
3. 当前用户与该球队的唯一绑定；
4. 审计记录。

创建用例必须同时使用数据库唯一约束和幂等请求标识：同一账号重复点击、客户端超时重试或两个并发请求只能得到同一球队；如果账号已经绑定球队，服务端返回该球队或明确冲突，不得创建第二支。客户端生成的 teamId 不能作为绕过账号唯一绑定的依据。

同名、相同联系人或相同手机号可以做核对提示，但不自动合并、认领或转移历史球队。首版字段沿用现有名称、负责人、联系方式、省、市及现有选填字段作为兼容候选；正式必填字段清单仍需确认。

建档成功页及球队详情必须明确说明“已建档，不代表总部认证或参赛资格通过”，不得使用“认证成功”“审核通过”或“获得参赛资格”等文案。

### 3.3 历史球队认领与成员管理（首版排除）

首版不提供历史球队认领、成员邀请、成员列表、角色分配、多人协作或负责人转移入口，也不建设对应写接口。数据库中既有球队不会因新账号的名称或手机号相似而自动绑定。未来认领必须另立项设计稳定 teamId、控制权证明、冲突处理与审计，且不得改写历史 `TeamVersion`、`EventTeam` 或 `EventTeamRoster`。

### 3.4 球队档案维护

【我的球队】首版只呈现当前账号唯一绑定的球队，不作为多球队列表。读取和更新目标由服务端根据认证用户解析；即使客户端篡改 teamId，也必须拒绝跨球队访问。更新携带 `expectedRevision`；409 时重新读取权威版本并保留本地输入供核对，不做最后写入覆盖。成员管理、负责人转移、球队合并及认领先后置。

### 3.5 赛事发布与找比赛

持有明确赛事发布权限的总部人员在总部端手动形成公开版本并发布，或手动下架。服务端在每次动作时重新校验当前人员、总部身份和赛事发布权限；申请审核权、赛事查看权、赛程发布权或其他内部权限不得隐式派生赛事公开权限。具体哪些总部岗位取得该权限仍需确认。

申请获批、批准办赛、办赛材料通过、赛程发布及其他内部状态变化只更新各自业务域，不调用赛事公开发布命令。只有显式发布动作可以使公开版本对球队端可见。

球队端列表、检索和详情只查询当前 `publicationStatus=PUBLISHED` 的公开投影，不调用内部 `/events`。下架事务生效后，列表和检索不再返回该赛事，详情接口对旧 eventId、收藏或深链也不再返回公开内容；前端可清除缓存并显示已下架，但不能以隐藏入口代替服务端限制。

首版目录查询始终先限定当前已发布版本，再按可选筛选条件查询。公开详情固定由发布快照提供赛事名称、总部确认的比赛日期/城市/场馆、承办机构名称、赛事介绍、参赛组别、参赛要求和独立公开咨询联系方式；报名窗口从赛事级当前生效聚合读取，不从发布快照、待审材料或客户端缓存读取。公开快照的具体结构化字段见第6节。

参赛组别和要求只作为展示文本/结构化条目，不运行资格判断。响应显式返回 `eligibility.status=NOT_EVALUATED`，不得因球队档案匹配、窗口为 OPEN 或前端筛选命中而改成合格。报名窗口状态只使用 `NOT_STARTED / OPEN / CLOSED`，分别显示“报名未开始 / 报名中 / 报名结束”。

“OPEN”只代表当前服务器时间位于生效窗口内，不代表当前球队符合资格或已经报名。目录没有报名动作；外部报名接口未接入前，页面只说明报名渠道尚未接入，不创建 EventTeam、报名、订单或支付数据。

### 3.6 材料审核、总部直接修改与并发冲突

赛事级报名窗口使用独立当前聚合保存唯一生效值：`eventId`、开始/截止时间、revision、来源类型及来源记录。为确保首次“无窗口”也能锁定和比较，建议每个赛事预先建立 revision 0、时间为空的窗口锚点；旧赛事迁移采用同样锚点，不把待审材料当作当前值。

承办方继续在七项办赛材料草稿中填写报名时间。每次正式提交生成不可变材料版本时，同时保存当时读取到的 `registrationWindowBaseRevision`。草稿、待审核、审核中和退回补充状态只展示材料版本中的候选时间，不写当前窗口。

总部通过整套材料时，由材料审核用例在原审核事务中调用报名窗口模块的公开事务服务，并按固定锁顺序锁定材料聚合和窗口锚点。事务必须同时满足：材料 submission 仍是当前审核版本、材料 revision 未变化、审核人权限有效、submission 的窗口基准 revision 等于当前窗口 revision。成功时一次性完成：

1. 材料状态变为 `APPROVED`；
2. 当前窗口写入该 submission 的报名时间并递增 revision；
3. 追加窗口版本，来源记为材料 submission；
4. 材料审核动作、窗口版本和审计同事务提交。

任何窗口 revision 不一致都返回 409，整个事务回滚，材料不能先通过、窗口稍后补写。审核页面重新读取并并列显示“当前生效窗口”和“本材料版本窗口”，提示总部核对。系统不得自动 rebase 旧 submission，也不得提供忽略冲突的静默覆盖。冲突后的正式处置尚待确认，候选方案为：退回补充并从旧版本预填、基于最新 revision 重交；或由有权总部人员在刷新后执行独立的“以该材料版本窗口为准”确认命令，以最新 expectedRevision、二次确认和完整前后值历史原子批准。第二种方案如采用，也不能复用首次失败命令或绕过再次鉴权。

持有相应赛事管理权限的总部人员可直接修改窗口，命令携带 `expectedRevision`。服务端锁定同一窗口锚点，校验 revision 后写入前后完整值、实际操作人、服务器时间及新版本。材料审核与直接修改无论谁先提交，后提交者持有的旧 revision 都会得到 409：

- 直接修改先成功：旧待审材料仍保留且不影响当前值，但不能被批准；需核对并退回重提。
- 材料批准先成功：总部仍基于旧窗口发起的直接修改失败；需读取材料已生效的新值后明确重试。

后续不建立独立承办方窗口申请，承办方仍只通过七项材料提交时间，总部直接修改与材料审批共同写一个当前聚合。对于实施前已经获批的历史材料，是否自动初始化窗口、由总部逐场确认后导入，或只作为只读候选来源仍待确认；在规则确定前，迁移只能建立空锚点和输出只读核对清单，不得自动把历史值设为生效。无论最终选择何种方式，都必须记录唯一 `sourceSubmissionId`，已有总部窗口版本不得反向覆盖，重复迁移不得重复建版本。

球队端 API 只返回当前生效窗口，并使用服务器当前时间计算三个展示状态：`NOT_STARTED`（报名未开始）、`OPEN`（报名中）、`CLOSED`（报名结束）。设备时间不得改变权威结果。窗口生效但赛事未发布时，公开接口仍不返回赛事；赛事已发布但没有生效窗口时如何展示，以及起止边界和时区语义，仍列为待确认问题。

## 6. 公开字段与禁止字段

公开赛事 DTO 必须使用明确 allowlist 和独立查询，不返回内部 Event 实体、任意 profile JSON 或先返回整包再由前端删字段。首版逻辑契约收敛为：

```text
PublicEventSummary {
  eventId, name,
  competitionDate: { startDate, endDate },
  location: { regionCode, regionName, cityCode, cityName, venueName },
  organizerName,
  registration: { startsAt, endsAt, status },
  eligibility: { status: NOT_EVALUATED },
  publicationVersion, publishedAt
}
PublicEventDetail extends PublicEventSummary {
  introduction,
  groups[],
  participationRequirements[],
  publicContact
}
```

列表和详情共用同一公开投影；列表返回摘要字段，详情增加完整介绍、组别、要求和公开咨询方式，二者都不得出现白名单外字段。`publicContact` 必须来自单独公开配置，不能把内部报名联系人、办赛材料手机号或成员资料映射进来。其具体字段格式属于首批开发阻塞问题。

目录查询参数限定为：赛事名称关键词、地区、比赛日期和报名状态，加技术分页参数。名称使用服务端规范化模糊检索；地区使用结构化代码而非自由文本等值比较；比赛日期命中赛事日期区间；报名状态使用服务器时间计算后的 `NOT_STARTED/OPEN/CLOSED`。所有筛选都隐含 `publicationStatus=PUBLISHED`，客户端不能请求包含未发布数据。

以下信息禁止进入球队端公开响应：

- 承办申请及办赛材料附件、营业执照和内部场地文件；
- 银行账户、合同及线下确认；
- 申请人/审核人身份、审核意见、原因和审核记录；
- 内部备注、审计上下文、grant 和机构内部关系；
- 除独立 `publicContact` 外的手机号、联系人及其他联系方式；
- 私有对象键、内部下载地址或内部版本 JSON。

公开版本只保存可公开字段快照及必要发布元数据。发布/下架操作历史属于总部内部记录，不随公开详情返回。

## 7. 接口差距

### 7.1 建议新增或扩展的接口

以下仅为设计草案，路径和字段在 B 阶段契约评审后确定：

| 用例           | 建议能力                                                               | 现状                                        |
| -------------- | ---------------------------------------------------------------------- | ------------------------------------------- |
| 球队端认证模式 | 按 client/app key 返回球队端微信能力                                   | 当前只有全局单 AppID 能力位                 |
| 微信登录/注册  | 按球队端 AppID 交换 code，恢复或建立受限主体                           | 当前只允许 active organizer                 |
| 跨 AppID 关联  | 创建并兑换目标 AppID 的一次性关联 intent                               | 当前 intent 绑定单一承办方 AppID 和密码会话 |
| 我的球队       | 由服务端按账号返回零个或唯一绑定球队                                   | 当前 `listTeams` 是无分页的内部工作台列表   |
| 自助建档       | 幂等、原子创建 Team、版本和账号唯一绑定                                | 当前依赖录入机构且无 userId 唯一约束        |
| 球队详情/更新  | 球队端专用 DTO、服务端解析绑定、字段白名单及 CAS                       | 当前更新逻辑可参考，但允许客户端指定任意 id |
| 公开资料草稿   | 总部配置名称、日期、地区/场馆、承办机构、介绍、组别/要求和独立咨询方式 | 当前 Event/profile 不具备完整稳定白名单     |

| 材料批准联动   | 整套材料通过与窗口版本生效同事务；revision 冲突则整体返回 409          | 当前批准材料不会写赛事窗口                  |
| 窗口直接修改   | 有赛事管理权限总部人员以 CAS 修改当前值                                | 当前没有赛事级生效窗口                      |
| 窗口历史       | 授权方读取来源、前后值、实际操作人、服务器时间和 revision              | 当前只能查看材料提交/审核历史               |
| 公开赛事检索   | 仅返回当前已发布投影；支持名称、地区、比赛日期、服务器报名状态及分页   | 当前只有内部授权 `/events`                  |
| 公开赛事详情   | 返回确认字段、独立公开联系人及当前生效窗口；下架后停止提供             | 当前无公开发布版本                          |

建议的逻辑 HTTP 契约如下；是否使用匿名 `/public` 或需认证的球队端前缀由 B-01 决定，但二者都只能访问同一个公开投影：

| Method  | 逻辑路径                                 | 请求/响应要点                                                                                           |
| ------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| GET     | `/public/events`                         | query：`name`、`regionCode`、`competitionDate`、`registrationStatus`、分页；返回 `PublicEventSummary[]` |
| GET     | `/public/events/:eventId`                | 仅已发布时返回完整 `PublicEventDetail`；下架、未发布或不存在不泄露内部记录                              |
| GET/PUT | `/events/:eventId/public-profile`        | 总部读取/保存公开资料草稿；PUT 携带 `expectedRevision`，使用专用写 DTO                                  |
| POST    | `/events/:eventId/publication/publish`   | 携带草稿 revision 和幂等键，校验发布权限后冻结新公开版本                                                |
| POST    | `/events/:eventId/publication/unpublish` | 携带 publication revision 和幂等键，原子停止全部公开读取                                                |
| GET     | `/events/:eventId/publication/history`   | 仅授权总部读取发布/下架动作和版本，不复用公开 DTO                                                       |
| GET/PUT | `/events/:eventId/registration-window`   | 授权总部读取当前值/历史或以 `expectedRevision` 直接修改；具体拆分路径由契约评审决定                     |

`competitionDate=D` 的建议语义是日期区间包含 D；`regionCode` 同时接受约定层级的省/市代码；`registrationStatus` 只能取 `NOT_STARTED/OPEN/CLOSED` 并在数据库查询时使用同一个服务器时刻计算。多个条件按 AND 组合，先限定已发布再筛选和分页。若 B-07 最终允许无窗口赛事发布，`registration` 必须显式可空且不能伪造状态；否则发布命令直接拒绝。

### 7.2 不应复用为球队端接口的现有能力

- 不直接开放内部 `/events`、承办申请、办赛材料或私有附件接口。
- 不允许球队用户调用 `POST /events/:eventId/teams`；该接口代表把主档案加入赛事，并非报名。
- 不把 `EventTeam.active` 当作报名状态，也不从它反推球队资格。
- 不把申请获批、批准办赛、办赛材料通过或赛事赛程 `PUBLISHED` 当作赛事公开发布；各自生命周期独立且不得自动调用发布命令。
- 不用 `ORGANIZER` 角色绕过球队关系校验或取得赛事发布权限。
- 不在下架后继续通过公开详情接口返回最后版本，也不只依赖客户端过滤、缓存失效或隐藏入口。
- 不让草稿、待审、审核中或退回材料里的窗口覆盖当前值，不从客户端时钟计算权威报名状态，也不让旧材料版本在总部直接修改后静默覆盖。
- 不把报名窗口生效当作赛事发布；公开可见性和报名状态分别判断。

## 8. 数据兼容方案

### 8.1 保留与扩展

1. `Team.id`、现有 profile、revision、版本和所有 `EventTeam` 关系原样保留，不复制或回填新表副本。
2. 将现有必填 `organizationId` 的语义演进为可空的“历史录入机构/来源机构”（最终字段命名待迁移设计）；旧数据值保持不变，自助创建不伪造机构。
3. 以 `TeamMembership` 或等价的一对一绑定作为账号—球队权限锚点，并增加数据库层的 userId 唯一保证；迁移前必须检查既有用户是否关联多个不同 teamId（无论当前 active 状态），发现冲突时阻断并人工处理，不静默选择或删除。
4. 自助建档在同一事务内写入 Team、TeamVersion、唯一绑定和审计，并使用账号唯一约束及幂等请求标识抵御重复点击和并发创建。
5. 首版不增加成员角色、邀请、负责人转移或历史球队认领模型；这些能力后置时另做迁移和权限设计。
6. `WechatIdentity` 继续关联同一 `InternalUser`；保留 `appId` 作用域唯一约束。服务端配置从单 AppID 演进为受控客户端注册表，每个 AppID 独立 Secret、用途和允许的认证流程。
7. `Session` 建议记录逻辑客户端或 AppID 作用域，以支持按应用撤销、审计和风控；是否新增 client enum 或 client registration 外键在 B 阶段决定。
8. 新增独立赛事公开资料草稿、发布聚合及不可变公开版本；发布快照仅含赛事名称、确认日期/地区/场馆、承办机构显示名、介绍、组别、参赛要求、独立公开咨询方式及必要元数据。报名窗口保持独立当前聚合，查询时受发布可见性保护，不复制成第二权威。版本/动作历史保存实际操作人、服务器时间、动作与公开字段快照，禁止覆盖。
9. 发布和下架由同一赛事公开聚合以事务、CAS 和幂等命令处理；发布权限后端逐请求校验。申请、办赛批准和赛程模块不得直接写公开状态。
10. 新增赛事级唯一当前报名窗口和不可变窗口版本；建议使用每赛事 revision 0 的空窗口锚点保证首次写入也可锁定。窗口版本保存来源类型（获批材料或总部直接修改）、可空 `sourceSubmissionId`、前后值、实际操作人和服务器时间。
11. 在既有 `HostingApplicationSubmission` 或等价关联快照中保存 `registrationWindowBaseRevision`。草稿不固定基准，正式提交时从同一事务读取当前窗口 revision；退回后新版本重新读取，不自动修改旧 submission。
12. 材料批准与总部直接修改都锁定同一个窗口并使用 revision/CAS。材料批准要求 submission 基准等于当前 revision，并与材料 `APPROVED`、窗口版本和审计同事务提交；冲突时整个批准回滚。总部直接修改携带 expected revision 并记录前后值。
13. 历史已获批材料的初始化策略尚待确认。规则确定前只建立空窗口锚点和只读核对清单，不自动生效；未来若导入，使用 `materialEventId + approved submissionId` 唯一来源并禁止覆盖已有总部版本。后续承办方仍在七项材料原字段填写，不增加候选请求表或第二套表单。
14. 球队端报名状态由 API 使用服务器时间与当前生效窗口计算为 `NOT_STARTED/OPEN/CLOSED`；响应可以包含生效起止时间和状态，但不暴露材料候选或内部版本历史。具体边界时刻语义和时区展示仍需确认。
15. 报名状态与资格字段分开表达；首版资格固定返回 `NOT_EVALUATED`，不根据组别、要求或球队档案推断，也不伪造合格。

### 8.2 不变式

- 修改 Team 不自动更新任何 EventTeam 或 roster。
- 首版不认领历史 Team；未来认领也不得改变历史比赛资料、录入机构、创建人或历史操作者。
- 下架赛事不删除 Event、EventTeam、赛程或历史公开版本，但公开列表、检索和详情查询都不再返回内容。
- 草稿、待审核、审核中和退回补充材料中的报名时间永不参与球队端状态计算；总部直接修改后，基于旧窗口 revision 的 submission 不能批准或自动换基准。
- 窗口生效不改变赛事公开状态，赛事发布/下架也不改写窗口版本。
- 同一微信在不同 AppID 下的 OpenID 不相等也不要求相等；UnionID 只能用于提示/风控，不能自动合并。
- 球队端会话不派生组织角色、EventGrant 或承办申请 grant。

## 9. 应用与依赖设计

`apps/team-miniapp` 应为独立 workspace 应用，拥有自己的 `package.json`、Taro 配置、页面配置、测试、`project.config.json` 和输出目录。建议包名 `@caau/team-miniapp`，项目名与构建产物不得覆盖 `@caau/miniapp`。

依赖方向：

```text
apps/team-miniapp ──> @caau/api-client ──HTTP──> apps/api ──> @caau/database
```

禁止：

- 从 `apps/miniapp`、`apps/admin` 或 `apps/api` 相对导入源码；
- 前端引入 `@caau/database`、Prisma、NestJS、服务端密钥；
- 复制生成客户端或手写与 OpenAPI 平行的业务实体；
- 在 Taro 环境变量、构建产物或日志中放 AppSecret。

B 阶段接入时需把新应用加入 `scripts/check-boundaries.mjs` 的受检单元及前端集合；根级递归 build/typecheck/test、格式检查和小程序构建产物检查也要明确覆盖两个小程序，不能默认现有脚本已完整覆盖。

## 10. 分阶段验收计划

### A 阶段：现状核对、规格与设计（本轮）

- 核对 Team、TeamMembership、EventTeam、微信身份与赛事信息事实。
- 交付页面清单、权限矩阵、接口差距、数据兼容、架构决策和集中待确认问题。
- 只检查文档链接、格式和差异；不新增应用、接口、迁移或依赖。

### B 阶段：身份、唯一绑定和公开赛事后端

建议先确认剩余业务问题，再实施前向迁移、球队端多 AppID 认证、单账号单球队绑定、幂等即时建档、公开发布/下架、公开检索和资格独立响应。验收必须覆盖：

- 必填资料不完整时拒绝建档且不产生 Team、版本或绑定；完整后立即创建可编辑档案，但响应不声称总部认证或参赛资格通过；
- 同一账号顺序重复、超时重试和并发建档都只产生一个 Team、一份首版本和一个绑定；
- 数据库约束禁止同一账号绑定第二支球队，失败事务不遗留孤立 Team；
- 服务端按认证用户解析唯一球队，篡改 teamId、跨账号及跨球队读取/更新均拒绝；
- 名称或手机号相同不触发历史球队绑定；没有认领、邀请、角色或转移接口；
- 只有有效赛事发布权限的总部人员可以发布/下架；无该权限的总部人员、仅有审核权者、承办方和球队账号均拒绝，权限撤销后下一次请求立即拒绝；
- 申请获批、批准办赛、办赛材料通过和赛程发布均不产生公开版本，只有显式发布成功后列表与详情可见；
- 发布后公开列表、检索和详情返回同一当前版本；下架事务成功后，三类接口及旧详情深链均停止提供公开内容；
- 每次发布/下架保留实际操作人、服务器时间、动作和版本；历史不可改删，并覆盖重复命令、并发发布/下架和旧 revision 冲突；
- 使用契约级字段白名单和反例响应测试，详情只含已确认目录字段；内部申请附件、银行账户、审核记录、非公开联系方式及内部 JSON 不进入公开接口；
- 独立公开咨询方式由总部显式配置；即使内部报名联系人或手机号存在，也不自动填入、兜底或随内部值变化；
- 名称关键词、结构化地区、比赛日期和 `NOT_STARTED/OPEN/CLOSED` 四类筛选在服务端执行；分页前过滤发布状态，未发布和已下架赛事在任意组合及详情 ID 直查中均不可见；
- 组别和参赛要求按发布快照展示，但资格始终为未评估；不同球队档案不会改变目录结果为“合格”；
- 球队建档、窗口 OPEN、查看详情和重复点击任何页面均不创建 EventTeam、报名、订单或支付记录，也没有成功/已占位文案；
- 承办方只在七项办赛材料原字段填写报名时间；草稿、Vn 待审核/审核中和退回补充均不改变当前窗口或球队端状态；
- 每次材料正式提交保存当时窗口 revision；整套材料批准与该 submission 时间生效同事务，成功只产生一个新窗口版本，重复审批命令不重复写入；
- 有相应赛事管理权限的总部人员可直接 CAS 修改，无权限、失权或旧 expectedRevision 均拒绝；历史准确记录前后值、实际操作人和服务器时间；
- 构造材料 submission S1 基于窗口 V1，随后总部直接修改到 V2：批准 S1 返回 409，材料保持未批准且 V2 不变；审核页面刷新显示 V2 与 S1 值，不能静默覆盖或自动 rebase；
- 反向竞态中若 S1 先批准并生效为 V2，总部仍以 V1 发起直接修改则返回 409，必须读取 V2 后明确重试；验证任一事务失败时材料状态、窗口、版本和审计均不部分提交；
- 历史材料迁移先验证“空锚点 + 只读核对清单 + 零自动生效”；待初始化策略确认后，再按选择补充显式导入验收，任何方式都不得重复建版本或覆盖已有总部窗口；
- API 分别在开始前、窗口内、截止后返回 `NOT_STARTED/OPEN/CLOSED` 及对应中文展示；待审值不进入公开 DTO，客户端伪造时间不改变结果，窗口生效但赛事未发布时仍不可见；
- 跨 AppID 不自动合并、无组织角色扩张、旧数据迁移冲突阻断、球队资料 CAS 和公开敏感字段隔离。

### C 阶段：独立小程序工程与页面

建立 `apps/team-miniapp`，接入生成客户端，完成三 tab、登录、即时建档、唯一球队档案维护、目录四类筛选、赛事详情及各种失败状态。验证重复点击只有一次创建请求结果、建档后显示非认证/非资格提示、无认领或成员管理入口；赛事下架后刷新列表消失，已打开详情或旧深链重新请求显示不可用且不残留公开内容；报名状态只渲染 API 返回结果，不使用设备时间覆盖。配套端验证材料草稿/提交页继续使用原报名时间字段；审核冲突时并列显示当前生效值与材料版本值并提示核对，不把材料误显示为已通过。冲突处置 UI 待业务选择后验收，当前不预设只能退回重交。另验证独立构建目录、边界检查、两小程序互不覆盖、模拟器响应式和无敏感日志。

### D 阶段：外部报名集成（接口提供后另立项）

确认外部系统权威字段、赛事 ID 映射、跳转/授权、资格、错误恢复和隐私后再实现。不在 B/C 阶段预留一个可误认为已可报名的假按钮。

### E 阶段：正式微信与生产验收

为球队端独立提供 AppID、AppSecret、合法 HTTPS 域名、项目成员和测试微信号；分别验证开发者工具正式项目与真机登录、跨 AppID 关联、幂等新建、唯一球队隔离、会话撤销和下架。补做生产密钥、TLS、可信代理、多实例限流、监控、备份恢复及独立安全评审。本地注入交换器不能替代本阶段。

### 11.2 可后置事项

以下内容不阻塞第一批“单球队档案 + 已发布赛事目录”开发：

- 历史球队认领、成员邀请、角色分配、负责人转移和球队合并。
- 同名球队后台重复记录处理队列；首版只提示且不自动认领。
- 球队归档后的恢复、改绑政策；首版不提供归档/改绑入口。
- 微信丢失后的人工恢复、主动解绑及换绑；正式发布前必须补齐，但不阻塞基础接口和页面开发。
- 外部报名小程序跳转、赛事/球队 ID 映射、报名提交、名额、订单、支付和退款。
- 根据组别或要求自动判断球队资格；首版固定为未评估，不阻塞展示。
- 报名人工暂停、名额已满和外部系统不可用状态；首版状态只来自生效时间窗口。
- AI 对话、球员名单及球员敏感资料。

### 11.3 可由开发确定的技术实现细节

以下内容不需要再次作为业务问题询问，但实施时必须写入 ADR/契约并验证：

- 表名、索引名、UUID、外键及当前表/版本表的具体拆分方式。
- CAS 锁顺序、事务隔离级别、幂等键格式、409 错误码和重试策略。
- 下架或未发布详情统一返回 404 还是业务不可见错误；对客户端不得泄露记录是否存在。
- 分页采用 cursor 还是 page，默认/最大 page size，以及名称检索规范化和必要索引。
- 地区代码的数据字典版本及前端选择器实现，但不能退回自由文本作为筛选权威值。
- `Cache-Control`、ETag、日志脱敏、审计 context 白名单和限流参数。
- Taro 页面组件、加载骨架、空态、触控尺寸和响应式实现。
- OpenAPI operationId、DTO 类名和生成客户端函数名；生成文件仍禁止手改。
- 隔离测试 fixture、可控服务器时钟和并发屏障的具体实现。
