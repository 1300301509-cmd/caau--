# 赛事级承办关系最小设计（待确认，不实施）

状态：CAAU-018 通用设计提案，未实施。CAAU-027 已确认“赛事承办申请通过后，将申请机构登记为该赛事承办方”，并在[赛事承办申请产品规格](event-hosting-application-spec.md)与[ADR-0010](../adr/0010-event-hosting-application.md)中采用独立机构承办关系；关系基数、类型、经办人员和授权联动仍未确认。当前产品不得把 `ORGANIZER EventGrant` 或材料任务指派显示成赛事承办关系。

## 1. 必须区分的四件事

| 概念 | 建议职责 | 当前实现 |
| --- | --- | --- |
| 承办机构 | 记录哪一个机构与赛事存在正式承办关系及其关系生命周期 | **未实现** |
| 经办人员 | 记录某个承办机构下哪些成员可代表该机构处理该赛事；人员变化不能改写机构关系历史 | **未实现赛事级关系** |
| 赛事访问权限 | 允许成员访问赛事范围；撤权应立即生效，但不删除业务归属和历史 | `EventGrant`，继续只表达授权 |
| 材料任务指派 | 决定某一材料任务当前由哪个机构、经办人和审核范围办理 | `TaskScope`、任务 assignment generation 与历史，继续保持独立 |

赛事承办关系是业务事实，访问授权是安全能力，任务指派是具体工作责任；三者不能用同一行记录互相冒充。

## 2. 候选最小结构

只有在业务问题确认后才考虑迁移：

- `EventOrganizerAppointment`：独立 UUID、`eventId`、`organizationId`、关系状态/生效区间、创建人与时间。它只表达赛事与承办机构的正式关系，不直接充当权限。
- `EventOrganizerAgent`：独立 UUID、`appointmentId`、`organizationMemberId`、状态/生效区间、创建人与时间。它表达某机构在该赛事上的经办人员，不预设人数上限。
- 关系变更采用追加历史或明确失效时间，不覆盖创建者、原机构或原经办历史。
- `EventGrant` 仍由授权用例单独维护。将人员设为经办人是否自动授予、撤销何种 grant，必须先确认；即使联动，也应在一个受审计事务中分别写业务关系与授权记录。
- `TaskScope`、任务指派代次和 `AssignmentHistory` 不改为外键依赖上述关系，避免历史任务因赛事承办关系变化而被重写。

该结构没有唯一约束来限定“一个赛事只能有一家承办机构”或“只能有一名经办人”；基数须由业务确认后决定。

## 3. 与现有材料任务兼容

1. 现有任务不反向推导、不自动补写赛事承办关系；任务里的机构和经办人继续是该任务的权威当前指派，历史保持不变。
2. 现有 `ORGANIZER EventGrant` 不迁移成承办关系；它只保留访问能力。
3. 将来创建新任务时，可在业务确认后选择以下策略之一：仅提示所选机构/人员与赛事承办关系不一致；强制必须来自有效承办关系；或允许总部明确例外并审计。当前不选择策略。
4. 赛事承办关系变更不得自动转移既有任务。现行规则仍是：同机构换经办人走任务交接；跨机构不得直接转移，需关闭旧任务并新建任务。
5. 撤销赛事级经办关系是否同时影响未关闭任务、草稿和下载权限必须单独定义；在确认前，现有 `TaskScope` 权限规则不变。

## 4. 实施前必须确认的业务问题

1. 一个赛事能否有多个承办机构；是否区分主办、承办、协办等关系类型？
2. 同一承办机构可有多少名赛事经办人；是否需要主经办人、备用经办人或不同职责？
3. 指派由谁发起、谁确认；创建赛事时是否必填，还是允许稍后补充？
4. 关系何时生效、能否预设生效时间；撤销、替换和恢复如何记录？
5. 机构或经办人停用后，业务关系是保留并标记失效，还是必须先交接？
6. 经办人员是否必须属于承办机构；跨机构借调是否允许，如何审计？
7. 建立承办关系是否自动创建赛事访问授权；授予哪些角色、撤销时是否保留其他来源的授权？
8. 有访问授权但没有承办关系的人员能做什么；有承办关系但授权暂未生效时页面如何提示？
9. 新材料任务是否必须指派给赛事承办关系中的机构/人员；允许例外时由谁批准？
10. 赛事承办关系变更对已有草稿、已提交版本、未关闭任务和任务交接的影响是什么？
11. 是否需要机构接受/拒绝指派，以及通知、截止时间和超时规则？
12. 哪些字段需要对总部、承办方和外部用户可见；是否涉及个人联系方式等敏感信息？

这些问题确认前，不创建表、不增加接口，也不在 UI 中显示“已指定承办方”。
