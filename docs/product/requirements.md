- R-020：承办方可在本赛事自由新增办赛材料，单份提交、单份审核，不依赖固定五项清单；替代 R-011 的整包部分，保留不可变版本与历史。
- R-021：待提交、待审核、审核中、退回修改、审核通过由业务动作驱动；明确开始审核后进入审核中，退回重交进入待审核。

- R-023：在线页面自动同步提交与审核变化；断线恢复、撤权、输入保留和数据隔离纳入验收。

- R-025：俱乐部/球队可跨承办方报名；承办方只能看与其赛事有关的俱乐部资料。报名由外部小程序负责，接口待提供。
- R-026：后续参赛展示字段和人工缴费三状态按新规格记录；本轮仍只做承办方办赛材料，不提前开发球队审核或支付。
- R-027：历史指令：下一阶段先建设总部 Web 后台整体框架并保留 12 个原型导航板块；其首页视觉和多模块铺开方案已被用户否定，由 R-028 取代当前前端范围。
- R-028：总部 Web 改为参考 Tabler 的紧凑、专业、高信息密度风格；当前前端只呈现资料审核一个业务模块，原规划模块不进入导航。复用现有资料提交、共享审核、历史与后端权限，不引入 Bootstrap，不改数据库或扩展业务规则。继续明确标识本地测试身份，不开发正式账号体系。（2026-09-15 用户修订指令）
- R-029：资料审核以一个个承办方为首层列表，每个承办方有自己的 Logo，再进入对应资料任务与审核详情。当前仓库尚无 Logo 字段或文件，真实 Logo 资源提供前只能使用明确标记的名称首字占位，不得伪造品牌图形。（2026-09-15 用户截图及补充指令）
- R-030：当前总部前端新增赛事管理入口，只向总部赛事管理员提供其有权赛事列表、现有字段（名称、说明）创建和详情查看；不搬运完整旧工作台，不扩展赛事字段，不创建材料任务或实现信息变更审批。（2026-09-16 用户指令）
- R-031：`ORGANIZER EventGrant` 继续只表示赛事访问授权，不得重新定义或展示为赛事承办关系。赛事级承办机构与经办人员模型本轮只提交最小设计和待确认问题，暂不实施，也不擅自限定一个赛事只有一名经办人。（2026-09-16 用户确认）
- R-032：历史指令：承办方小程序首页曾收敛为一个大“材料提交”入口并移除tabBar；该首页布局已由R-033取代，但无tabBar、状态保护和既有业务规则不变。
- R-033：小程序按“选择测试身份→主页→选择业务板块→主页下方子模块→功能页”进入。主页含可替换的本地赛事横幅、紧凑板块网格；当前仅“材料审批”，默认选中并显示“材料提交”“审核进度”。进度仅供承办方查看状态、退回原因和历史，不授予总部审批权；身份切换保持次要位置，子页返回恢复所选板块。先确认主页视觉，再统一内部页面。（2026-09-16 用户修订指令）
- R-034：资料审核 Web 正常同步时不展示连接状态、最近核对时间、轮询间隔或由此产生的占位；自动轮询、断线重连、返回前台刷新、权限复核和未保存输入保护保持。只有持续无法更新、会话过期或权限失效时显示单一、简洁、可操作的异常提示，不重复弹出。（2026-09-16 用户指令）
- R-035：承办方小程序页面顶部使用紧凑双列区域：左侧赛事状态栏只显示当前承办身份有权赛事名称和方向箭头，不显示“当前赛事”、任务数或“切换”文字；右侧以较小正方形区域等比展示用户提供的CAAU Logo，不拉伸或裁切。点击赛事栏时页面布局不位移，背景暗化并显示固定尺寸的赛事选择窗口；赛事过多时只在窗口内部上下滚动。主页所选赛事作为“材料提交”“审核进度”的上下文，子页只展示该赛事的任务、材料和状态；赛事列表及访问仍由后端授权决定，不增加承办范围。（2026-09-16 用户修订指令）
- R-036：正式赛事创建前新增“赛事承办申请”：承办方提交新申请；首版申请表固定为赛事名称、开始日期、结束日期、赛事地点，正式提交时四项必填，结束日期不得早于开始日期，草稿可暂不完整。申请资料必交营业执照、简介（办赛经验）、现场照片，选交其他文档；具体文件格式、大小和数量仅列实现建议，未确认前不得作为业务规则，也不得新增业务必填项。承办申请审核使用独立权限，不依赖正式赛事 `EventGrant`；有权总部审核员共享查看和处理，明确点击“开始审核”进入审核中但不独占领取，其他有权审核员可接续，打开详情不自动开始。每一步记录实际操作人、服务器时间和提交版本；禁止审核本人提交的申请，同一版本冲突审核只能一个成功且不得覆盖结果。要求补充材料后，承办方可在同一原申请中修改并重交形成新版本，旧版本和历史完整保留；驳回终止当前申请，不得恢复编辑或重交，但可另建新申请，原申请及审核历史完整保留。总部通过后系统自动创建正式赛事并将申请机构登记为该赛事承办方，未通过不创建赛事。申请人只表示本次提交人，不默认是唯一赛事经办人；同一申请机构内具有申请办理权限的有效经办人可共同查看、编辑、提交申请及补充版本，不限定创建人。所有写操作保留实际操作人和历史，以并发控制防止多人编辑覆盖；禁止跨机构访问，已提交版本不可修改。申请通过时，该机构当时有申请办理权限的有效经办人自动获得新赛事基本信息查看权；该最小权限不包含赛事修改、审核或任何材料任务办理，不得复用会附带这些能力的宽泛角色。承办机构关系与人员访问授权分别记录。获批不自动创建材料任务，总部后续创建任务并指定办理人，沿用现有任务权限规则；既有办赛材料提交与审核完整保留为获批后的后续流程。不把人员查看授权或 `EventGrant` 当承办关系。资料格式/大小/数量和特殊情况、申请办理及独立审核权限的授予/撤销管理、批准时无有效经办人的处理及获批后新增经办人/撤权/停用的查看权联动、后续材料任务具体配置仍待确认，不得自行补成规则。（2026-09-17 用户指令及补充；设计见[赛事承办申请产品规格](event-hosting-application-spec.md)）

## CAAU-005 当前指令与已确认执行规则

用户已授权先提出全段技术设计，再交付第一段真实赛事/任务创建、机构/经办/审核指派、材料要求配置和发布、指定经办方查询，以及必要总部 Web 页面；上传/提交/审核完整实现留第二段。验收使用真实业务 API，不以权限探测代替。技术设计见 [ADR-0004](../adr/0004-material-workflow.md)。

第二段规则已由用户本轮确认（取代第一段未决项）：
- R-014：截止后可保存草稿，禁止正式提交；由总部赛事管理员延期后才能提交。后端用服务器时间校验，延期必须记录操作者、时间、原因及新旧截止时间。
- R-015：同机构换经办人，新经办人接管现有草稿与材料，保留原编辑记录；旧经办人立即失去任务办理权限；重指派与授权变更同事务。
- R-016：首版禁止跨机构直接转移；需要时关闭原任务，再为新机构建新任务。不得自动复制原材料/历史或授予新机构访问权。
- R-017：V1/V2 等提交及审核记录不可修改；保留原提交人、审核人和时间，不因交接改写。

第二段实现真实后端 API：私有文件上传/确认/绑定/下载、草稿并发控制、幂等不可变提交、整包审核与材料级退回原因、重交、延期/同机构交接。验收必须使用真实业务接口；后续页面和微信验收另记。

第三段用户明确授权总部 Web 与承办方 Taro 界面，交互与路径见 [页面设计](material-workflow-ui.md)，实际验收见 roadmap。R-018：配置和发布不得超出当前实际上传格式/大小能力，技术上限不等于正式业务默认。R-019：模板属于总部发布任务的材料要求，不是承办方提交材料。总部仅在发布前可为每项材料上传或移除可选模板；发布时模板与 RequirementVersion 一同冻结，发布后不得悄然替换/删除。当前被指派机构的 active ORGANIZER 才能经后端鉴权下载；其他机构、SYSTEM_ADMIN、审核员、无权/撤权用户拒绝。模板与承办材料共用私有对象存储、安全原文件名显示与格式/大小/哈希校验，但关系和下载权限独立。真实模板库、跨版本改版、微信正式登录/开发者工具/真机仍需单独验收；本地身份入口必须明确标记。
