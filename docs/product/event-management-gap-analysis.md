# 赛事创建、承办指定与信息变更：现状和待确认问题

状态：CAAU-013 产品梳理，2026-09-15；CAAU-018 于2026-09-16只追加当前入口事实。CAAU-027 于2026-09-17新增了“承办方先申请、总部通过后创建赛事并登记申请机构”的已确认前置流程，设计见[赛事承办申请产品规格](event-hosting-application-spec.md)，仍未实施。本文件其余内容保留当时现状和问题，问题中的选项不是建议或已确认规则。赛事级机构/人员的独立候选结构和兼容边界另见[最小设计](event-organizer-relationship-design.md)。

此前确认的高层方向来自 [requirements.md](requirements.md) R-024～R-026：总部指定承办方并填写赛事基础信息；承办方申请赛事信息变更，由总部确认；报名后相关俱乐部需要获知变更，但通知不由CAAU发送。R-036 现补充了承办方自行发起新赛事申请的创建路径；总部直接创建/指定路径是否继续作为并行正式业务方式仍待确认。赛事获批后的信息变更和外部通知边界不因前置申请设计而自动确定。

## 1. 当前正式实现

### 1.1 赛事创建

| 项目 | 当前事实 | 证据 |
| --- | --- | --- |
| 创建入口 | 总部Web `/events` 向 `POST /api/v1/events` 提交赛事名称和说明；`/workspace`只留隐藏兼容入口 | `apps/admin/src/features/events/EventPage.tsx`、`apps/api/src/modules/materials/materials.controller.ts` |
| 数据字段 | `Event`只有id、name、description、createdBy、createdAt；与独立`EventScope`共享id | `database/prisma/schema.prisma` |
| 权限 | 需要 `events.create`；创建事务同时建立授权锚点，创建人取得赛事管理员范围 | `MaterialsService`、`AuthorizationService.createEventAnchor` |
| 查询 | 总部赛事管理员只看有active EVENT_MANAGER grant的赛事；承办方/审核员只通过可见任务间接看到赛事 | `MaterialsService.visibleEvents` |
| 验证 | 创建、范围查询、审计、越权及重启持久性已有真实PostgreSQL/API/Chromium证据 | `docs/planning/roadmap.md` CAAU-004/005 |

当前没有赛事草稿/发布状态、赛事编号、赛季、大区、举办日期、报名窗口、场馆、组别、联系人或公开说明等结构化字段。名称和说明可承载文字不等于这些字段已实现。

### 1.2 指定承办方

当前实现是**材料任务级指派**，不是`Event`上的赛事级承办关系：

1. 总部先创建赛事。
2. 在旧工作台创建材料任务草案时选择承办机构、经办人和单一审核员。
3. 服务端建立该任务的`TaskScope`及赛事授权，`MaterialTask`通过scope关联当前经办关系。
4. 旧整包任务发布前可以走指派更新，但服务端禁止跨机构替换；发布后同机构交接使用专用动作，跨机构必须关闭原任务并新建任务。
5. 新版单份任务的创建API只要求赛事、承办机构、经办人和任务名，审核采用赛事共享授权；当前没有对应总部Web创建入口，演示由受控命令调用API追加。

`AssignmentHistory`/新版指派历史保留任务经办变更，但不能回答“这个赛事的法定/主承办方是谁”。同一赛事技术上可以有多个指向不同机构的任务，当前没有事件级唯一性或主/协办语义。

### 1.3 赛事信息修改和变更申请

当前均未实现：

- 没有 `PATCH /events/:id` 或赛事版本接口，Web也没有编辑赛事入口。
- 没有承办方变更申请对象、草稿、提交、撤回、总部确认/退回或状态。
- 没有变更前后值快照、申请理由、附件、申请人/确认人、服务器时间或并发revision。
- 没有区分报名开始前、报名后、比赛临近或比赛结束后的可变字段。
- 没有把已确认变更同步给材料任务、外部报名系统或通知责任方的事务/outbox/API。
- 通用`AuditRecord`可以记录已有接口动作，但不能替代不存在的业务申请和确认历史。

## 2. 与已确认方向的差距

| 已确认方向 | 当前覆盖 | 缺口 |
| --- | --- | --- |
| 总部填写赛事基础信息 | 仅名称、说明 | 基础字段清单、校验、草稿/发布、版本和Web表单均缺 |
| 总部指定承办方 | 仅材料任务级承办机构/经办人 | 赛事级关系、主/协办、多机构、有效期和替换规则未定义 |
| 承办方申请变更 | 无 | 申请主体、可变字段、状态、原因/附件、并发和权限均缺 |
| 总部确认 | 无 | 有权确认人、通过/退回、是否可改申请内容、审计和生效事务均缺 |
| 报名后通知相关俱乐部 | 已确认CAAU不发送 | 外部责任方、目标俱乐部来源、接口载荷、触发/重试/送达证据均缺 |
| 不影响既有材料历史 | 材料提交/审核历史已不可变 | 赛事变更如何影响当前任务上下文、截止和后续提交尚未定义 |

因此，不能把现有“创建赛事 + 创建材料任务”描述成“完整指定承办并支持赛事变更”。

## 3. 开始设计前待确认问题

### A. 赛事基础信息

1. **Q-EVT-01：**“赛事基础信息”的正式字段有哪些？需逐项确认，例如赛事名称、编号、赛季/年份、大区、比赛日期、报名窗口、场馆、地址、组别、规模、公开说明和联系人；示例不代表默认全部采用。
2. **Q-EVT-02：**哪些字段面向俱乐部公开，哪些只供总部/承办方履约，哪些属于敏感联系人信息？
3. **Q-EVT-03：**赛事是否有草稿、已发布、进行中、结束、取消等生命周期？各状态由谁触发，哪些状态允许修改？状态名称尚未确认。
4. **Q-EVT-04：**总部创建赛事时必须一次填完，还是可保存草稿后发布？赛事“发布”和材料任务“发布”是否两个独立动作？

### B. 指定承办方

5. **Q-EVT-05：**一个赛事只能有一个主承办组织，还是允许主办/承办/协办多个组织？如果多组织，各自能看到和办理什么？
6. **Q-EVT-06：**应在赛事级先指定组织，再在各任务指定经办人；还是继续只做任务级指派？现有任务如何映射不能由技术方自行决定。
7. **Q-EVT-07：**承办关系生效后，总部能否更换组织？报名开始前、已有材料草稿、已有不可变提交或赛事进行中时规则是否不同？
8. **Q-EVT-08：**同一承办组织内是单经办人、多人共享还是负责人+经办人；谁有提交赛事变更申请的权限？

### C. 变更申请内容和流程

9. **Q-EVT-09：**哪些赛事字段允许承办方申请变更，哪些只能由总部直接维护或永远不可改？
10. **Q-EVT-10：**一次申请是多个字段的整包变更，还是每个字段独立确认？总部能否部分通过？
11. **Q-EVT-11：**申请是否必须填写原因、期望生效时间和证明附件？各项的必填条件、格式和大小尚未确认。
12. **Q-EVT-12：**承办方提交后能否撤回或修正；若总部已开始处理，是否必须退回后再提交新版本？
13. **Q-EVT-13：**总部确认由赛事管理员、专门审核员还是其他岗位执行？是否允许创建赛事或指定承办的人确认，是否需要多人确认？
14. **Q-EVT-14：**总部拒绝/退回是否必须有原因；承办方是否可以基于原申请重交并保留V1/V2历史？
15. **Q-EVT-15：**多个在途申请修改同一字段时，是禁止并行、排队还是允许并发后冲突？采用哪种业务规则尚未确认。
16. **Q-EVT-16：**紧急变更是否有不同处理路径、时限或事后补确认要求？不能因“紧急”文案自行绕过确认。

### D. 生效、历史及现有材料

17. **Q-EVT-17：**总部确认后是立即生效，还是可指定未来生效时间？谁能取消尚未生效的变更？
18. **Q-EVT-18：**赛事历史需要保存哪些内容：完整版本快照、字段差异、申请/确认人员和时间、原因、附件、外部交付状态？
19. **Q-EVT-19：**赛事日期/场馆等变化是否自动改变材料任务截止或要求？若不自动，是否只提示总部另行延期；不得无规则改写已发布要求和提交历史。
20. **Q-EVT-20：**承办组织变化时，旧组织的草稿、附件、提交和历史如何处理？现行材料规则禁止跨机构直接搬迁，但是否完全沿用到赛事级变更仍需确认。
21. **Q-EVT-21：**已审核通过的办赛材料是否因赛事信息变化需要重新提交/审核；由谁发起，哪些字段变化触发？

### E. 外部报名小程序和俱乐部通知

22. **Q-EVT-22：**外部报名系统的赛事ID与CAAU赛事ID如何映射，哪个系统是各个赛事字段的权威来源？
23. **Q-EVT-23：**何时算“已有报名”，相关俱乐部清单从哪里取得；CAAU是否只输出事件，还是提供查询接口供外部系统拉取？
24. **Q-EVT-24：**CAAU确认变更后交付给哪个责任方/系统；最小载荷包含哪些字段，是否包含变更前后值和生效时间？
25. **Q-EVT-25：**外部通知失败、重复、延迟或部分送达由谁重试和对账；CAAU需要保存“已交付外部系统”还是“俱乐部已收到”的哪一级证据？
26. **Q-EVT-26：**哪些变更必须通知俱乐部，哪些仅内部留痕；通知渠道、文案和最终发送责任不属于CAAU当前已确认范围。

### F. 验收与历史数据

27. **Q-EVT-27：**首个验收最少需要几类赛事、承办组织、变更类型和总部确认人；是否必须覆盖报名后变更及外部接口失败？
28. **Q-EVT-28：**现有仅有名称/说明的赛事如何处理：保持旧记录、人工补录、还是后续建立新版本；未确认前不得批量回填或修改历史。
29. **Q-EVT-29：**正式试点需要哪些非敏感合成样例和字段口径；不得用演示值替代业务默认。

## 4. 后续关口

在上述问题得到业务确认前：

- 不新增赛事字段、变更状态表、接口或页面；
- 不把任务级承办关系提升为赛事级唯一承办事实；
- 不修改现有材料截止、授权、不可变版本或历史迁移；
- 不建设报名入口、俱乐部通知或支付模块；
- 不以外部报名小程序“可能具备”的能力作为已存在接口。

确认后应先更新 [requirements.md](requirements.md) 的规则与验收，再形成技术设计；接口变更仍遵循先改Nest DTO/控制器、再生成契约的流程。微信登录、开发者工具正式项目、真机及HTTPS环境继续独立保留为待办。
