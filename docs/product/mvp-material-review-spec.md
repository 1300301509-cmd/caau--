# 首版：办赛材料提交与总部审核

状态：已确认，2026-09-08。来源：用户完成业务负责人对接后提供的首版规则。本文是 CAAU-004、CAAU-005 的产品依据；与早期候选方案冲突时，以本文为准。

## 目标与范围

首版解决承办方办理赛事时的材料提交与总部审核。总部无需开发人员或手改数据库，即可创建赛事、指定承办机构和经办人、发布材料任务并完成审核；承办方在小程序完成待办、草稿、上传和提交。

首版包含：赛事、承办机构与经办人指定、材料任务、任务要求与模板版本、草稿、不可变提交版本、整包审核、退回重交、附件受控访问、完整历史及审计记录。

首版不包含支付、完整报名、智能排赛、财务模型、增长、赞助、裁判、俱乐部教务和 AI。它们不得作为本轮顺带开发的模块。

## 角色与责任

| 角色 | 可以做什么 | 明确禁止 |
| --- | --- | --- |
| 总部赛事管理员 | 创建赛事；指定承办机构和经办人；发布或更新未开始办理的任务要求；指定审核员 | 代替承办方填写或提交材料；修改已提交版本；以赛事管理员身份绕过审核记录 |
| 承办方经办人 | 查看本机构被分配的赛事和任务；填写、保存草稿、上传、正式提交；处理退回并重新提交 | 修改总部任务要求；查看其他承办方资料；审核自身材料 |
| 总部审核员 | 查看分配给自己的待审核任务、提交版本和历史；通过或整包退回 | 直接修改承办方提交内容；修改任务要求；审核自己的提交 |
| 系统管理员 | 管理账号、组织、授权和安全日志 | 因系统管理员身份自动获得业务资料、任务或审核权限 |

后端必须同时校验身份、动作权限、组织范围、赛事范围、任务指派和审核员指派。前端隐藏入口不是权限控制。

## 两端范围

小程序导航只保留“待办”“赛事”“我的”。经办人在其中查看分配任务、阅读要求、保存草稿、上传、提交、查看退回原因和版本历史。提交中必须有加载反馈、防重复提交和字段旁错误提示；弱网或上传失败不能显示“提交成功”。

Web 后台提供赛事创建、承办机构和经办人指派、任务要求维护、审核队列及历史查看。后台不把大表格照搬到手机端。

## 任务与材料要求

总部发布的任务必须包含截止时间、材料清单和模板版本。承办方只能读取这一版要求；任务要求在承办方开始办理后不得被悄然改写。若后续允许改版，必须创建可追溯的新要求版本，并明确对既有草稿和提交的影响；首版不实现这一复杂分支。

首个“赛前办赛信息包”包含：

1. 办赛基础信息确认表：时间、场馆、组别、负责人。
2. 场馆及场地确认材料。
3. 安全、医疗和应急方案。
4. 竞赛执行方案。
5. 物料搭建或现场 VI 方案。

每一项材料要求需要配置必交与否、填写说明、模板版本、支持格式、文件大小上限、截止时间，以及示例或合格标准。正式格式和大小数值由总部配置；开发与测试只使用合成材料配置，不能把原型数值当正式规则。

## 提交与审核流程

```text
总部创建赛事并指定承办方/经办人
  → 发布材料任务
  → 承办方保存草稿、上传材料
  → 正式提交 V1（不可修改快照）
  → 审核员通过，或整包退回并标记问题材料
  → 承办方以 V1 内容生成新草稿
  → 正式提交 V2、V3 …
```

- 草稿可以修改；正式提交后形成不可变版本，不能被覆盖。
- 审核员通过或退回时必须针对当前提交版本执行；审核动作记录人员、时间、结论及原因。
- 退回必须指定不合格材料，并填写退回原因和修改要求；可以重设修改截止时间。
- 首版采用整包通过或整包退回，退回时明确标记需修改的材料；不实现逐项通过或部分通过。
- 退回后系统从上次提交内容生成新草稿。重新提交产生新版本；V1、V2、V3 和全部审核记录永久保留。
- 首版不提供通过后的隐式重开、删除历史或直接改状态能力。

## 截止、延期、交接与关闭（第二段已确认）

- 截止后仍可保存草稿，但禁止正式提交；后端以服务器时间检查，客户端时间不决定放行。总部赛事管理员延期后才能再次提交。
- 延期保留操作人、操作时间、原因和新旧截止时间，不修改已发布要求或已提交版本中的历史截止信息。
- 同机构更换经办人：新经办人接管现有草稿和材料，原编辑记录保留。旧经办人立即失去任务办理权限；指派和授权变更必须在同一事务中完成。
- 首版不允许跨机构直接转移。需更换承办方时关闭原任务、为新机构创建新任务；原机构材料与历史不能自动复制或授权给新机构。
- V1/V2 等提交与审核记录永久不可修改，保留当时的提交人、审核人和时间，不因经办人交接改写。

## 数据与安全规则

- 以两个赛事、两个承办方验证数据隔离：承办方 A 无论伪造网址、赛事 ID 或任务 ID，都不能读取、修改或下载承办方 B 的数据。
- 附件由后端授权上传、绑定和下载。文件不是公开链接；下载请求和短期访问地址都必须再次检查当前权限。
- 重复点击或网络重试提交必须使用幂等机制，只产生一个提交版本。
- 并发审核同一版本只允许一个结论；其他请求返回明确冲突，不能覆盖历史。
- 刷新、退出重登和服务器重启后，赛事、任务、草稿、提交版本、审核记录和附件关联必须持久存在。
- 创建赛事、指派、发布任务、保存/提交、退回、通过和关键失败均记录具体人员与时间；审计与日志不记录令牌、文件正文或不必要个人数据。

## 第三段实现约束与首版待办

任务要求的格式与大小必须处于后端当前上传能力内，前端配置/上传提示与服务器保存/发布校验保持一致；技术上限不是总部正式默认大小。每项要求可有一个总部草案模板；发布时以 RequirementVersion 关联快照冻结，只有当前指派承办机构经办人可下载。模板库、跨版本要求改版和跨任务复用文件仍是后续范围。

已实现 Taro 业务页面和 Web 闭环不代表 MVP-02/09 微信运行验收；正式微信登录、开发者工具与真机另记。浏览器承办联调界面不是正式小程序平台的替代交付。

## 开发顺序

1. CAAU-004：内部身份与会话、组织成员、赛事授权、动作权限、审核员指派和审计基础。真实微信登录须等 AppID 与平台资源就绪；开发测试身份不能被误称为真实微信验收。
2. CAAU-005：赛事、承办方指派、任务要求、材料草稿、受控文件、不可变提交版本、整包审核和版本历史。
3. CAAU-010：以两赛事、两承办方的合成数据完成 API、Web、小程序、微信开发者工具和真机验收；真机资源未就绪时任务保持未完成。

开发时每个状态转换、权限反例、文件授权、幂等与并发规则均须有 PostgreSQL 集成测试；接口先更新 Nest DTO/控制器，再运行契约生成，前端仅消费 `@caau/api-client`。
