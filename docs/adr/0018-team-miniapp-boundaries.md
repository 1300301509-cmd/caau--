# ADR-0018：独立球队端小程序、球队主体与赛事公开边界

- 状态：部分采纳；首版账号—球队、赛事展示及报名窗口规则已确认，其余业务问题待确认，尚未实施
- 日期：2026-09-21
- 关联任务：CAAU-046

## 背景

现有承办方小程序服务有组织角色的内部经办用户；球队主档案、赛事球队快照和球队账号关系已落库，但没有球队端建档/认领流程。赛事只有内部筹备态和内部授权查询，也没有面向球队的发布/下架及报名可用性契约。

球队端需要独立 AppID、独立发布节奏和独立信息架构，同时必须复用同一个球队库、身份主体、API 和数据库。直接复制承办方小程序、给球队用户授予 `ORGANIZER`、直接开放内部赛事接口，都会破坏权限与数据边界。

## 决策

### 1. 独立应用，复用契约

实施阶段新增 `apps/team-miniapp`，建议 workspace 名称为 `@caau/team-miniapp`。它独立配置、构建和发布，只依赖 `@caau/api-client`；不得引用 `apps/miniapp` 或其他应用源码。两个小程序可以复用同一生成契约和无平台业务类型，但不通过复制源码形成两套规则。

### 2. 一个业务身份，多种受控凭据

`InternalUser.id` 继续作为人员主体，`WechatIdentity` 作为 AppID 作用域内的认证凭据。球队端新 AppID 产生的新 OpenID可以显式绑定到已有 `InternalUser`，也可以在获准自助建档时创建新的 `InternalUser`。不建立“球队用户表”或第二套会话系统。

服务端把微信配置从单一 AppID演进为受控客户端注册表，并根据目标客户端选择 AppID、Secret、允许流程和限流域。AppSecret 仍只在 API 端。建议 Session 记录逻辑客户端/AppID 作用域，以支持审计和按端撤销。

跨 AppID 关联必须有显式控制权证明：一次性关联 intent、现有密码会话或管理员定向邀请。姓名、手机号、昵称、OpenID 字符串或 UnionID 不足以自动合并。当前承办方专用的 `activeOrganizer` 登录门槛不能沿用于球队端；球队端认证成功也不产生任何组织角色。

### 3. 首版为单账号—单球队绑定

球队端读写球队的授权锚点是后端维护的 `TeamMembership` 或等价一对一绑定及其有效状态，不是 `OrganizationMember`、`ORGANIZER`、`EventGrant`，也不是客户端传入的 teamId。首版确认一个球队账号只管理一支球队，不引入 OWNER/MANAGER/VIEWER 角色，不开发成员管理、邀请、负责人转移或历史球队认领。

用户填写全部必填资料后立即建档。新建用例在单一事务内创建 Team、首个版本、账号唯一绑定和审计；数据库必须保证 userId 最多关联一个 teamId，并配合幂等请求标识。重复点击、超时重试或并发创建只能返回同一结果或明确冲突，不能生成第二支球队，也不能留下无绑定的孤立 Team。

所有球队端读取和更新先由服务端根据认证用户解析唯一球队，再执行字段及 revision 校验。客户端篡改 teamId、访问其他账号球队或在已有绑定后再次建档均被拒绝。建档只代表主档案与账号绑定成立，不代表总部认证、报名成功或参赛资格通过。

名称、手机号及相似档案只可用于提示，不得自动认领历史球队。认领后置到独立阶段，届时重新设计控制权证明、冲突处理与审计。现有 `Team.organizationId` 记录历史录入机构；自助球队不应挂到虚假机构，实施迁移应保留旧值并允许新来源不带机构，具体字段重命名在迁移设计时确定。

### 4. 主档案与赛事快照继续隔离

`Team` 是球队长期主档案，`EventTeam` 和 `EventTeamRoster` 是某届赛事的独立快照。球队端建档、修改或账号绑定均不得自动更新 `EventTeam`、名单、赛程或历史版本。把 Team 加入 EventTeam 也不等同于报名。

### 5. 建立独立赛事公开聚合

球队端不调用内部 `/events`，也不读取任意 EventProfile JSON。实施阶段新增赛事公开聚合、当前状态和不可变公开版本。只有持有明确赛事发布权限的总部人员可以手动发布或下架；服务端逐请求复核总部身份、当前权限和目标赛事，不能从审核权、赛事查看权、承办关系或赛程发布权隐式派生。

发布命令从确认过的字段 allowlist 生成公开快照，并原子更新当前发布状态。下架命令原子取消当前公开可见性，但不删除内部赛事或历史版本。申请获批、批准办赛、办赛材料通过、赛程发布及其他内部状态变化都不得自动调用公开命令。

公开列表、检索和详情使用同一个服务端可见性判定，只返回当前有效的已发布版本。下架提交后，旧 eventId、收藏、深链和客户端缓存都不能使详情接口继续返回公开内容；前端隐藏入口不能替代服务端拒绝。

每次发布和下架都追加不可变记录，至少包含赛事、动作、公开版本、实际操作人和服务器时间。命令使用 revision/CAS 和幂等键处理重复、并发和未知网络结果；历史不得覆盖。具体状态表与版本表拆分方式在实施迁移中确定。

报名开放状态与球队资格是两个字段和两个判断：前者描述赛事报名窗口/暂停等全局状态，后者描述指定球队是否满足规则。没有权威资格规则时返回 UNKNOWN/NOT_EVALUATED，不推断为合格。

### 6. 报名窗口采用当前聚合与基准版本请求

现有办赛材料的不可变提交已包含 `registrationStart`/`registrationEnd`，整套材料通过也有实际审核动作，但当前实现不会把结果投影到 Event。实施时优先把获批材料提交作为初始生效窗口来源：只有赛事尚无当前窗口时才创建初始版本，并保存唯一 `sourceSubmissionId`；重复命令或历史迁移不能重复应用，已有总部新值不能被材料结果覆盖。

新增赛事级当前报名窗口、不可变窗口版本和候选变更请求。当前聚合是唯一权威值；请求只保存候选值及提交时的 `baseWindowRevision`。承办方提交不改当前聚合，总部同意时才在同一事务内锁定请求和当前窗口，以请求状态及 `baseWindowRevision == current.revision` 作为必要条件，成功后递增 revision 并记录来源。

有相应赛事管理权限的总部人员可携带 `expectedRevision` 直接修改。在同一事务中写入前后值、实际操作人和服务器时间，递增当前 revision，并把所有基于旧 revision 的待审核/审核中请求标记为 `SUPERSEDED`。审批路径仍必须再次校验 base revision；因此即使旧请求被并发重放或绕过列表直接调用，也只能得到 409，不能覆盖总部新值。系统不自动 rebase 旧请求，承办方必须基于最新窗口另行提交。

如果候选审批先提交，当前 revision 已递增，则仍持旧 `expectedRevision` 的总部直接修改也返回 409，要求总部读取新值后明确决定，避免相反方向的静默覆盖。所有命令采用幂等键，状态、版本、请求结果与审计同事务提交。

球队端只读取当前生效窗口；API 用服务器当前时间计算报名状态，不接受设备时间决定权。窗口生效不发布赛事，赛事发布/下架也不改窗口；公开接口先检查赛事当前已发布，再读取生效窗口。具体时间边界和时区展示仍待确认。

### 7. 外部报名继续隔离

首版仅展示公开赛事和状态。外部报名接口、ID 映射、支付和订单未提供前，不创建报名实体、不调用 `POST /events/:eventId/teams` 代替报名，也不提供会让用户误以为已经提交的按钮。未来集成作为独立阶段设计。

### 8. 敏感数据默认拒绝

公开 DTO 采用字段白名单和专用查询，禁止返回内部实体或任意 JSON 后再由前端裁剪。内部申请附件、办赛材料附件、营业执照、银行账户、合同、审核记录/意见、内部备注和未列入白名单的联系方式不可达；发布/下架操作历史也不进入球队端公开 DTO。公开字段变更必须先修改 Nest DTO/控制器和服务端投影，再生成客户端，禁止手改生成文件。

## 备选方案及否决理由

1. **复制球队库到新应用数据库**：产生双写、归属冲突和比赛快照误同步，否决。
2. **把球队用户设为 ORGANIZER**：将球队档案权限与办赛申请/赛事权限耦合，构成扩权，否决。
3. **复用承办方小程序同一 AppID 和代码包**：发布、权限、导航和平台资源无法独立治理，不符合明确要求，否决。
4. **按手机号/名称/UnionID 自动认领**：无法证明球队控制权或跨应用账号控制权；首版认领先后置，否决。
5. **直接公开内部 Event/Profile**：生命周期不足且字段边界不稳定，未来可能泄露敏感信息，否决。
6. **把 EventTeam 当报名记录**：其当前语义是赛事资料快照，不含外部报名状态、订单或支付，否决。

## 影响

- 数据库需要前向兼容迁移，增加账号单球队唯一约束及建档幂等记录，但不复制、重置或重写既有球队及赛事快照；迁移前发现同一用户关联多个不同 teamId（包括非 active 关系）时必须阻断并人工处理。
- authorization 需要支持多微信客户端和非 organizer 的球队端流程，并保持现有承办端行为不回归。
- teams 模块需要球队端专用建档、唯一球队读取/更新 DTO 和后端绑定校验；首版不增加成员、邀请、角色、转移或认领接口，内部 Web 接口可以保留。
- events 侧需要新的公开发布聚合、不可变版本/动作历史、显式发布权限策略和专用公开查询，不能只扩展现有内部列表过滤条件或依赖前端隐藏。
- 报名窗口需要唯一当前聚合、不可变版本和带基准 revision 的候选请求；复用获批办赛材料作为初始来源，后续请求和总部直接修改不得形成第二套当前值。
- `scripts/check-boundaries.mjs`、根构建/测试及小程序产物检查需要显式纳入新应用。
- 正式验收需要球队端独立 AppID、AppSecret、HTTPS 域名和真机资源；本地测试不等价于微信平台验收。
