# ADR-0034：赛程编排七因素与结构化提案

状态：本地实现；微信与真机待验，CAAU-103；2026-09-29。

## 背景

“按照早上 1 场、下午 2 场、晚上 1 场的时间给我编排赛程”能被路由为排程行动，但新需求和分时段续填使用自由文本 JSON 解析；格式偏差会变成泛化 503。既有旧提案结构还可能漏掉续填的分时段要求。原 `DAYPART_CAPACITY` 只有“最多”语义，无法准确表示用户没有说明上限还是每天必须排满的场数。每日时钟、场地、单场时长等也只在候选表单中，未贯穿需求单。

## 决策

- 生产模型对新建和续填需求都使用同一结构化提案。针对当前 `qwen-plus`，明确采用函数调用模式，模型输出仍由 Zod 校验；失败分类为无效输出并保留用户输入，不提交需求或赛程。一次模型调用只记一次用量，不为格式失败隐式重试执行。
- 需求单覆盖日期范围、每日可比赛时钟、每日及分时段场数、当前赛事参赛球队及组别、场地和单场比赛时长；换场缓冲和同队最短休息是候选算法还需核对的配置。赛事资料、当前参赛记录与现有赛程配置是受控来源，来源和版本保留在需求中，不能由模型编造内部 ID 或业务默认值。
- 没有每日总场数时须补齐早／午／晚三个时段的场数；确认时对所选组别的有效参赛名单记录摘要，之后增减或换组使旧确认失效。若用户完整重填六项赛程配置，该条件转为用户来源，不继续依赖旧赛程配置版本。
- 场数区分 `MAXIMUM`、`EXACT` 与 `UNRESOLVED`。裸说“早上 1 场、下午 2 场、晚上 1 场”保存数值并追问口径。只有完整时段起止、按赛事或每场地统计的范围、场数语义都明确时，需求才可确认。旧版未带模式的场数条件沿用原“最多”语义。
- 候选计算须采用确认需求中的日期与配置，按当前有效参赛记录和竞赛组别核对，搜索与独立校验分别执行场数约束。`EXACT` 对范围内每天逐日核对；有足够证据证明场次总数不可能满足时报告冲突，搜索未找到仍与已证明无解区分。候选保持独立预览，不写正式赛程。

## 后果与验收边界

条件保存在现有需求 JSON，不引入新的业务表；接口先更新 Nest DTO，再生成 Web／小程序客户端。真实千问的结构化提案、隔离库需求与候选、两端渲染、微信运行时和真机分层验收。一次本机真实模型通过只能证明该次提案，不证明长期供应商稳定。
