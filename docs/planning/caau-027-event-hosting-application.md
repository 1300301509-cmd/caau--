# CAAU-027 赛事承办申请分阶段计划

状态：A 设计阶段已形成待确认稿；B～D 未开始。任何业务代码、契约生成或数据库迁移必须等待用户确认设计及阻塞规则。

## 1. 任务定义

- **目标**：在正式赛事创建前增加承办方申请和总部审核流程；通过后原子创建赛事并登记申请机构承办关系，未通过不创建赛事；获批后继续使用现有办赛材料流程。
- **本轮范围（A）**：登记需求、产品规格、技术设计、分阶段计划和待确认规则。
- **本轮排除**：API、前端页面、Prisma schema、迁移、生成契约、依赖、测试数据及本地业务数据变更。
- **产品依据**：[赛事承办申请产品规格](../product/event-hosting-application-spec.md)。
- **技术依据**：[ADR-0010](../adr/0010-event-hosting-application.md)。

## 2. 总体交付顺序

严格按 A → 业务确认关口 → B → C → D 推进。不得为了展示页面先伪造接口或直接写数据库；接口变更先改 Nest DTO/控制器，再 `contract:generate`，两端只消费 `@caau/api-client`。

| 阶段 | 状态 | 主要交付 | 不包含 |
| --- | --- | --- | --- |
| A 规格与设计 | 待用户确认 | requirements、产品规格、ADR、阶段计划、任务登记 | 业务代码、schema、迁移、契约 |
| B 后端与数据库 | 未开始 | 追加迁移、申请/版本/文件/审核、原子批准、赛事来源、机构承办关系、人员基本信息查看授权、生成客户端 | 总部正式页面、小程序正式页面、材料任务自动创建（已确认不做） |
| C 总部 Web | 未开始 | 申请队列、版本/附件详情、三种审核动作、赛事来源/承办关系展示 | 小程序申请表、扩大后端权限 |
| D 承办方小程序 | 未开始 | 申请列表、草稿/资料/提交、补充版本、状态与历史、获批结果 | 总部审核操作、正式微信登录建设、未确认授权自动化 |

## 3. A：规格与技术设计

### 3.1 交付

- 在 `requirements.md` 登记首版赛事名称、开始/结束日期、结构化地点（省市区、详细地址、场馆名称）及办赛经验简介；提交时必填且结束日期不得早于开始日期。资料固定三项必交/一项选交，简介以文本满足，文件建议不成为规则；
- 产品规格明确地点三个部分、待补充可改范围/机构不可变/Vn+1全量重验、相邻版本字段与附件差异，以及资料版本、状态、两端入口、历史保留和集中阻塞清单；
- ADR 明确嵌套地点、办赛经验简介、草稿/提交/差异 DTO、严格日期及固定资料 fulfillmentType，以及聚合、授权、事务/幂等/并发和兼容；
- 本计划给出后端、总部页面、小程序页面的阶段门槛和验证证据。

### 3.2 验收

- 文档明确“未通过不创建赛事”“申请人不等于唯一经办人”“获批自动授予当时有效申请经办人最小基本信息查看权”“获批不创建材料任务、后续沿用现有任务流程”；
- 明确首版赛事名称、开始/结束日期、省/市/区、详细地址、场馆名称和办赛经验简介；草稿可不完整，提交时全部必填；地点不降为单一文本，日期逆序拒绝且同日允许；
- 明确记录三项必交和一项选交资料，不擅增资料；格式、大小、数量候选值单列为实现建议，特殊情况继续待确认，不把技术建议当业务规则；
- 状态表和状态机包含审核中；明确点击“开始审核”后进入，打开详情不改变状态；开始不独占，其他有权审核员可接续；
- 明确独立申请审核权限不依赖 `EventGrant`，每步记录实际人/时间/版本，禁止本人审核，同版本冲突只能一个成功且不覆盖；
- 明确同机构有权有效经办人共享办理、不限创建人，记录实际人/时间/revision/version，草稿CAS防覆盖，跨机构拒绝且已提交版本不可修改；
- 明确 NEEDS_SUPPLEMENT 只可改名称、日期、地点三个部分、办赛经验简介和附件，申请机构不可变；保存草稿、重交全量重验并生成 Vn+1，旧版本/附件/意见/历史保留，总部可看相邻版本字段和附件变化；
- 明确驳回终止原申请且只能另建新申请；承办机构关系与人员查看授权分记，查看权不含修改/审核/任务办理且不复用宽泛角色；
- 明确获批不创建材料任务，总部后续创建并指定办理人、沿用现有任务权限；办理/审核权限管理、获批后新增/撤权/停用联动及任务具体配置继续作为单独阻塞项；
- 链接检查、格式检查、`git diff --check` 和提交文件范围通过；
- 明确记录未运行应用构建、数据库和页面验收，因为本阶段没有实现。

## 4. B：后端、追加迁移与契约

### 4.1 准入

- A 获用户确认并提交；阻塞规则已写回 requirements/spec；
- 从 A 的干净提交继续，检查 Git 状态；
- 核对当前 Node/pnpm/Prisma/Nest 版本和官方文档；
- 不修改历史 migration，不 reset/删除数据卷，不操作远程数据库。

### 4.2 实施批次

**B1 数据模型与升级保护**

- 追加申请、提交版本、资料/附件、动作、命令、同机构申请办理 grant、独立申请审核 grant、赛事来源、初始赛事信息版本、机构承办关系及 `EventInformationAccessGrant(EVENT_BASIC_INFO_VIEW)`；人员查看授权含来源 handler grant/申请/版本且不复用宽泛 `EventGrant`；
- 实施不可变触发器、复合外键、唯一来源和一申请至多一赛事约束；
- 建立旧赛事/授权/任务/整包与单份材料/附件升级夹具和摘要对比。

**B2 申请方用例**

- 先实现 Nest DTO：草稿 form 仅允许 eventName、startDate/endDate、location.administrativeArea.{province,city,district}、location.detailedAddress、location.venueName、eventExperienceIntroduction 且可部分为空；提交命令只带 revisions/idempotencyKey，并从权威草稿生成完整快照。严格校验真实 `YYYY-MM-DD` 和日期顺序；拒绝地点自由文本及额外字段；
- 同机构 active 成员 + active 申请办理 grant 共同查看/编辑/提交，不按 createdBy 过滤；草稿、附件绑定/移除及提交携带 expected revision，冲突不自动覆盖并保留调用方输入；每步写实际 actor/数据库时间/revision/version 历史；
- 私有上传/确认/绑定/下载、提交 V1；NEEDS_SUPPLEMENT 下任一当前有权同机构经办人只能修改已确认字段/附件，申请机构不可写；CAS 保存草稿，重交前全量重验并在同一 applicationId 生成 V2/PENDING_REVIEW，完整保留旧版本/附件/补充意见/审核动作；驳回后拒绝保存和重交但允许新申请；
- requirementCode 固定为 BUSINESS_LICENSE/FILES、EVENT_EXPERIENCE_INTRO/TEXT、VENUE_PHOTO/FILES、OTHER_DOCUMENT/FILES；提交及重交验证营业执照/现场照片有效附件和简介非空文本，其他文档可缺省；不擅增资料。文件建议仅作能力评估，正式值确认后才进入业务校验；
- 提供同一 application 相邻 submission 差异 DTO/查询：字段逐项旧值/新值，附件按 requirementCode 返回 added/removed/replaced 安全元数据；服务端从不可变快照计算，拒绝跨申请；首版不开放客户端任选 from/to 或草稿比较；
- 申请列表和详情在查询层按 application.applicantOrganizationId、active member 和 active handler grant 过滤；跨机构、同机构无权限、停用/撤权成员及仅有 createdBy 身份均不能访问。已提交 Submission/附件关系由数据库和服务层双重不可变保护。

**B3 总部审核与原子获批**

- 状态机包含 PENDING_REVIEW、IN_REVIEW、NEEDS_SUPPLEMENT、REJECTED、APPROVED；NEEDS_SUPPLEMENT 可在原申请生成 Vn+1，REJECTED 为当前申请不可恢复终态；
- 提供独立 start-review 命令，只有明确点击触发的写操作才进入审核中，详情 GET 无副作用；开始动作不建立 owner/领取锁，其他当前有权审核员可以接续；
- 独立 request-supplement、reject、approve 命令及申请审核权限；所有审核写命令固定 submissionId/version，记录实际 actor/数据库时间，并在持锁后拒绝审核本人提交的申请；
- approve 在一个 Serializable 事务锁定当时 active member + active handler grant 集合，创建 EventScope/Event、EventOrigin、EventProfileVersion V1、EventOrganizerAppointment，并逐人创建独立 `EVENT_BASIC_INFO_VIEW` grant及动作/命令/审计；任一失败全部回滚；
- expected revision、submissionId、请求 hash、状态 CAS、同版本唯一结论约束和幂等键共同防重复/覆盖；冲突审核只能一个成功，其余返回 409 后读取权威结果；
- 批准事务不得创建宽泛角色/EventGrant、EventOrganizerAgent、MaterialTask、TaskScope 或任务办理权；总部后续另行调用现有任务创建/指派流程，不能把 appointment/basic-view grant 当任务权限。

**B4 契约与文档**

- 先 Nest DTO/控制器，再生成 OpenAPI 和客户端；不手改生成文件；
- 更新数据库/接口 runbook，记录命令、迁移、权限和失败恢复。

### 4.3 B 验收证据

- 真实隔离 PostgreSQL/HTTP 验证 DRAFT、V1、审核、补充、同申请 V2、驳回、通过；V1/V2 缺赛事名称、任一日期、省/市/区、详细地址、场馆名称、办赛经验简介、营业执照附件或现场照片附件均拒绝，其他文档缺省/为空可提交，补充/驳回均无 Event；
- DTO/日期/地点矩阵覆盖：部分空草稿可保存；2028-02-29 有效、2027-02-29 和非 `YYYY-MM-DD` 拒绝；同日/顺序/时区场景通过；location 字符串、省市区缺层级及额外地址字段拒绝；save/submit 伪造 organizationId/actor/status/version 拒绝，create 无权机构拒绝；
- 同机构经办甲创建并保存，乙能读取、继续编辑并实际提交 V1；要求补充后甲或乙可提交 V2，各动作的 actor/数据库时间/revision/version 准确且 createdBy 不被当作后续操作人；
- 甲乙从同一 draft revision 并发保存只有一个成功，另一请求 409 且数据库内容/历史不被覆盖；刷新后显式基于新 revision 才可重试。跨机构列表/深链/附件/写入全部拒绝；同机构无办理 grant、停用/撤权者及仅为创建人者拒绝；
- V1/V2、提交附件关系、submittedBy/submittedAt 的 API 修改不存在，普通 owner/runtime UPDATE/DELETE/TRUNCATE 受不可变保护；只能通过待补充草稿形成下一版本；
- NEEDS_SUPPLEMENT 下分别修改名称、日期、地点各部分、办赛经验简介，新增/移除/替换各类附件均可保存；修改 applicantOrganizationId 或非白名单字段拒绝。重交重新校验未修改的必交内容，原 applicationId 不变、V2 递增并回 PENDING_REVIEW；V1 文件/关系、补充意见和动作不可变；
- 总部读取 V1→V2 差异准确显示各字段旧/新值以及附件 added/removed/replaced；无变化项稳定，移除 V2 引用不删除 V1 文件，差异不暴露 storageKey；跨机构、跨申请拒绝，契约不存在客户端任选 from/to 或草稿比较入口；
- GET 列表/详情不改变待审核状态；明确开始进入审核中并记录实际人员/服务器时间/版本，重复及并发开始符合幂等/CAS；审核员甲开始后不产生独占，审核员乙可接续补充/驳回/通过，历史分别记录甲乙实际动作；
- 独立权限矩阵真实验证：只有 `EventGrant` 无申请审核 grant 者拒绝，只有申请审核 grant 无任何 `EventGrant` 者可共享查看/处理；撤销申请审核 grant 后立即不能接续，不影响其赛事 grant；
- 申请任一提交人为当前审核 actor 时，start-review、request-supplement、reject、approve 均由后端拒绝；不是仅隐藏按钮。两名有权非本人审核员对同一版本并发通过/驳回/补充时仅一个成功，其余 409，恰一结论且状态/历史不被覆盖；
- 相同批准重复点击和响应丢失重试返回同一 eventId 及同一组人员 basic-view grants，不重复授权；Event、origin、appointment、人员查看授权、申请状态和审计同事务回滚；
- 获批时同机构两名 active handler 均可读取新赛事基本信息；跨机构拒绝。两人只有 basic-view grant 时，赛事修改、申请/赛事审核、材料任务列表/详情/附件/写命令全部拒绝；不得借角色或前端入口扩权；
- 获批后数据库确认 MaterialTask/TaskScope 数量不变。总部随后按现有流程创建任务并只指派甲：甲按现有规则办理，乙仍只能看赛事基本信息；任务历史、截止、附件和权限反例继续通过；
- 注入 Event、origin、appointment、action 或 audit 写失败时事务全部回滚，无孤立 EventScope；
- appointment、basic-view grant、宽泛 EventGrant/角色、TaskScope 四类对象分别验证：关系不直接放行，basic-view 不产生写/审核/任务权，TaskScope 只增加明确任务能力；跨机构、无权、停用成员、过期/撤销会话和文件越权均拒绝；
- 旧赛事无来源仍正常查询；旧任务、材料、附件、V1/V2、审核历史、checksum 和文件 hash 在升级/重启后保留；
- `contract:check`、`check`、`build`、`test`、`db:test` 全部按实际结果记录，失败不得隐藏或跳过。

## 5. C：总部 Web 页面

### 5.1 准入

- B 后端、契约、真实数据库权限及事务验收完成；
- 页面文案、状态中文名称和审核权限已确认；
- 不通过前端按钮隐藏代替服务端权限。

### 5.2 交付

- 独立赛事承办申请导航、队列、状态/机构/时间筛选和空错状态；
- 详情展示赛事名称、开始/结束日期、省市区、详细地址、场馆名称、办赛经验简介快照，及资料完成情况、附件、V1/V2、提交人与全部审核动作；相邻版本提供字段和附件变化视图；
- 展示待审核与审核中；提供明确“开始审核”操作，打开详情不触发状态变化；开始不独占，审核中对任一当前有权非本人审核员提供通过、驳回、要求补充材料，固定当前 submissionId/revision，展示实际操作历史、动作后果并防误操作；
- 通过后跳转唯一赛事；赛事详情展示申请来源、机构承办关系和逐人基本信息查看授权三个分区，不把 appointment、basic-view 或宽泛 EventGrant 混为同一对象；
- 历史/总部直接创建赛事显示兼容来源，不显示虚构申请。

### 5.3 C 验收证据

- 真实 API/PostgreSQL/Chromium 验证打开详情仍待审核、甲明确开始后变审核中、乙接续形成结论，并完成原申请补充 V2 后通过、驳回终止、另建新申请、重复批准和失权场景；每一步显示实际人/时间/版本；
- Web 对待补充申请保留同一申请上下文并展示 V1/V2、补充意见及相邻版本字段/附件差异；对已驳回申请不显示编辑/重交，仅提供独立新建入口，原详情和历史持续可查；
- 两个独立审核会话对同一版本执行相反结论时 UI 收敛到服务端唯一结果，失败方显示冲突并刷新，不覆盖成功方；本人提交者即使持有申请审核权限也看不到可用审核动作，直接 API 仍拒绝；
- 刷新和详情深链有效，附件受控下载，迟到响应不覆盖新状态；全部字段及地点子字段按提交快照展示，单日赛事不被改成跨日或受浏览器时区影响；
- 键盘操作、焦点、状态非纯颜色、375/768/1440px 无页面横向溢出；
- 现有 `/events`、`/materials` 和历史页面回归；basic-view 人员只能看基本信息，不能出现赛事编辑/审核/材料办理控件，直接 API 同样拒绝；总部后建任务并指派后页面仅对被指派人增加该任务入口。

## 6. D：承办方小程序页面

### 6.1 准入

- 同机构共享办理、补充操作和获批后入口行为已确认；办理权限授予/撤销管理已明确后再开放入口；

### 6.2 交付

- 主页独立“赛事承办申请”板块，不依赖已选赛事，也不把待审申请加入赛事选择器；
- 同机构共享申请列表/详情；申请表包含赛事名称、开始/结束日期、地点三个部分和办赛经验简介，提供营业执照/现场照片必交附件及其他文档选交附件、草稿 CAS、提交确认；不按创建人过滤；
- 展示全部状态；待补充只开放已确认字段和附件，申请机构只读；在同一原申请基于上一版本形成草稿、全量重验后提交 V2，并展示旧版本/附件/补充意见/操作历史；
- 已驳回申请只读，不提供恢复编辑或重交；允许从列表独立新建申请，新申请使用新 applicationId/V1，原申请详情和审核历史保留；通过后当时有效申请经办人进入赛事基本信息只读页，不显示编辑/审核/材料办理；只有总部后建任务并明确指派后才按现有任务规则出现对应材料入口；
- 多人编辑冲突保留本地输入并提示刷新权威草稿，不自动覆盖；身份切换、前后台、断线、迟到响应、未保存输入和失权清理沿用现有安全模式；跨机构和撤权后清除受保护内容。

### 6.3 D 验收证据

- 请求逻辑和正式 weapp 构建通过；不把 Node 测试替身当平台验收；
- 微信开发者工具以同机构经办甲创建/保存，乙共享编辑并提交 V1；验证地点三个部分、办赛经验简介、日期逆序/单日、其他文档为空及无额外必填项；待补充修改每类允许内容、机构不可编辑、重交全量重验、V2/历史/补充意见完整，并验证实际人、多端冲突及状态刷新；
- 独立验证驳回不产生赛事且原申请无法编辑/重交，可另建新申请并继续查看原历史；重复提交不产生版本重复，已提交版本无编辑入口且接口拒绝，跨机构列表/深链/附件不可见；
- 两名获批时有效经办人均可看新赛事基本信息且不能修改/审核/访问未指派任务；总部后续只给其中一人创建并指派任务后，另一人仍无任务入口和文件权限。
- 真机在正式 AppID、合法 HTTPS 和测试身份具备时另行验证文件选择、上传下载、前后台和网络恢复；缺资源时明确阻塞。

## 7. 发布与回退原则

- 数据库先向后兼容追加，API 再部署，两端最后开放入口；旧客户端仍可使用现有赛事和材料流程。
- 功能开关只能控制入口，不得绕过事务和授权；半完成阶段不生成生产可见的申请入口。
- 一旦产生申请/版本/获批赛事，只做前向修复；不删除新表、重写 migration、reset 数据库或回退到会重复批准的旧二进制。
- 监控/日志只记录 ID、动作、状态、revision 和结果，不记录表单正文、审核原因、文件名、令牌或文件字节。
