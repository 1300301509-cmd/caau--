# CAAU-046：智能体球队端微信小程序

状态：**用户主动暂缓，任务未完成。** A 阶段规格与设计保留；B～E 阶段未启动。恢复实施必须由用户重新明确授权，当前不得开发球队自助账号、建档、认领、公开赛事目录或本任务规划的报名窗口改造。

当前业务使用 CAAU-041 既有 Web【比赛管理中心 → 球队管理】手工录入和关联赛事；球队主档案与本赛事资料继续独立，不自动同步覆盖。

## 任务目标

规划独立“CAAU 智能体球队端”微信小程序。首版支持球队维护自己的基础档案，以及检索总部已发布赛事、按报名状态等条件筛选并查看详情。本任务当前只执行 A 阶段现状核对、产品规格和技术设计，不编码。

## A 阶段范围

- 核对 Team、TeamMembership、EventTeam、微信身份绑定、赛事信息和工作区边界。
- 交付产品规格、页面清单、权限矩阵、接口差距、数据兼容方案和分阶段验收计划。
- 明确独立 AppID 下与现有 `InternalUser` 的关联方式及不得自动合并的边界。
- 登记已确认的单账号单球队、即时建档、后端唯一绑定、幂等规则、总部手动赛事发布/下架、公开目录及报名窗口规则；将剩余事项按首批阻塞、可后置和技术细节分级，不将建议写成已确认规则。

不新增 `apps/team-miniapp`，不修改数据库、API、OpenAPI 或生成客户端，不安装依赖，不实现报名、支付、订单、AI 对话或球员敏感资料。

## 验收标准

1. 现状结论可追溯到当前 schema、API 和仓库规则，历史文档与代码冲突时以现场代码标明实现事实。
2. 清楚区分已存在能力、必须新增能力、建议方案和待确认业务问题。
3. 明确球队主档案与赛事参赛快照继续独立。
4. 明确一个球队账号只管理一支球队，服务端维护唯一绑定并拒绝跨球队访问。
5. 明确资料完整后立即建档、可继续编辑，但不代表总部认证或参赛资格通过。
6. 明确重复点击、重试及并发建档不得生成多支球队，失败不得留下孤立记录。
7. 明确首版不做成员、邀请、角色、负责人转移或认领，也不按名称、手机号、昵称或 UnionID 自动绑定。
8. 明确只有持有赛事发布权限的总部人员可手动发布/下架，申请获批、批准办赛和赛程发布不自动公开。
9. 明确球队端列表、检索和详情只读取已发布公开版本；下架后所有公开接口停止提供内容，不能只在前端隐藏。
10. 明确公开详情字段为名称、确认的日期/城市/场馆、承办机构、当前生效报名窗口与状态、确认的介绍/组别/要求和独立公开咨询方式。
11. 明确目录支持名称、地区、比赛日期、报名状态筛选，全部由服务端在已发布投影上执行。
12. 明确公开联系人不从内部手机号自动复制，组别/要求不推导资格，建档或 OPEN 不等于报名成功，且没有伪报名动作。
13. 明确公开 DTO 使用字段白名单，不暴露内部申请附件、银行账户、审核记录或非公开联系方式。
14. 明确发布/下架保留实际操作人、服务器时间、动作和不可变版本记录，并纳入并发/幂等验收。
15. 明确承办方只复用七项办赛材料填写报名时间，不增加独立窗口表单；草稿、待审、审核中和退回补充均不影响当前值。
16. 明确整套材料通过与该 submission 窗口生效同事务，任一失败不得形成材料已通过但窗口未生效。
17. 明确总部赛事管理人员可直接修改并保留前后值、实际操作人和服务器时间；材料提交保存窗口基准 revision，两类操作竞争同一 CAS。
18. 明确发生并发冲突时返回409并展示当前值与材料值，不自动 rebase、静默覆盖或部分提交；冲突后的正式处置仍待确认，不把退回重交写成唯一方案。
19. 明确历史获批材料初始化策略仍待确认；决定前只建空锚点和只读核对清单，不自动生效，后续仍只能写同一个聚合。
20. 明确球队端仅按服务器时间和生效窗口显示报名未开始、报名中、报名结束；窗口生效与赛事公开独立，资格首版固定为未评估。
21. 新应用只依赖 `@caau/api-client`，并列出边界检查、构建、测试和正式微信验收要求。
22. 剩余事项按第一批阻塞、可后置和技术实现细节分级，不重复询问已确认规则。
23. 文档链接、格式和 Git diff 检查通过。
