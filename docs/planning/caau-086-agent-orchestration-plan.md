## 第一阶段实际接入（2026-09-26）

- 新增服务端 Skill 版本库。总部超级管理员可创建不可变草稿版本、查看历史并启用一个版本；启用新版时旧版转为已退役。首轮仅 `INTENT_ROUTING` 和 `TOOL_SELECTION` 两个固定键，未配置时沿用现有内置提示词。Skill 内容是给模型的指令，不是可执行 JavaScript/SQL，也不能注册工具或修改授权。
- 新增固定赛程工具目录，记录名称、版本、风险、实际权限和确认策略。只读查询、需求收集、候选预览、单场调整预览及绑定票据的 DRAFT 写入分别检查；服务端继续使用原有 `schedule.read`、`event.operations` 和 `schedule.draft.adjust` 判定。编辑 Skill 不会增加可调用工具。
- 新增当前会话待答对象，首轮接入排程需求中的日期和单循环歧义。问题关联规划 ID、赛事、revision 与 24 小时有效期，刷新可恢复；在有效的“是否每两支参赛球队各交手一次”问题后回复“是的/确定”等简短肯定，会按该问题补齐单循环条件，保留用户原话和来源关联。没有对应待答时短回复仍是普通对话。修改赛事、开始新任务、需求 revision 变化或到期后不采用旧问题。
- 前向迁移 `202609280001_agent_skill_runtime`；Nest DTO/控制器生成客户端。后端接口在 `/api/v1/observability/agent/skills` 下，尚无治理页面编辑 UI。完整复合目标拆分、通用待答类型、跨模块工具和受控资料检索仍属后续阶段，不以当前单一路由宣称已实现。

## 1. 产品目标

CAAU 智能助手是 Web 与小程序共用的对话入口。它应能自然聊天，理解单项或复合请求，在必要时查询有权业务数据或资料，协助形成方案，并通过受控工具完成用户明确确认的业务动作。用户留在同一个对话中；后台可以按任务选择不同流程，但不要求每句话都经过多个独立模型。

首轮编排只覆盖**现有助手已接入的赛程能力**：自由聊天、授权赛程只读查询、排程需求收集、整套单循环候选预览、单场改期预览与本人确认后保存 DRAFT。新增赛事、材料、球队等模块能力，要先有可独立验收的业务接口、权限和工具契约。Agent 不直接执行 SQL、修改数据库、审批或发布赛程。

## 3. 名词与职责

| 组件                 | 负责                                              | 不负责                                       |
| -------------------- | ------------------------------------------------- | -------------------------------------------- |
| 千问等 LLM           | 理解表达、提出目标与参数候选、组织自然语言回答    | 授权、确认、直接写库、判定算法合规           |
| 意图理解 Skill       | 向模型提供业务语义、歧义处理方法和结构化提案格式  | 发放工具权限或绕过后端规则                   |
| LangGraph 编排器     | 管理步骤、分支、任务状态、追问、恢复和结果汇总    | 自动生成 CAAU 的业务权限或工具实现           |
| 能力目录与工具适配层 | 声明工具契约并调用已有领域服务                    | 提供任意 SQL、任意 HTTP 或管理员身份         |
| 原业务服务           | 当前数据、权限、状态、确定性校验、CAS、事务与审计 | 信任模型提出的 actor、资源关系或“已确认”文本 |

Skill 是**做事方法**，工具是**可执行动作**。意图理解 Skill 输出建议，不能直接调用写工具。技术框架可继续使用现有 NestJS、LangGraph.js、PostgreSQL 和 `@caau/api-client` 边界；终端 pi-agent 只用于开发。LangGraph 支持把模型、数据、动作及人工输入拆成节点，见[官方工作流指南](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph)。

## 4. 每条消息的工作流程

```text
用户消息
  → 当前会话认证、历史资源重新鉴权、构造最小上下文
  → 意图理解 Skill + 模型提出一个或多个目标、指代与缺口
  → 编排器核对能力目录，按依赖顺序处理每个目标
  → 必要时先用有权的只读工具取当前事实
  → 仍有关键歧义：保存待答问题，向用户只问当前必需的一项
  → 聊天、查询或独立候选：返回结果与来源
  → 可写动作：确定性预览、风险说明、签发确认票据
  → 用户在结构化卡片确认：重新鉴权、核验票据与 revision
  → 原业务服务执行、返回权威回执并更新任务状态
```

意图提案建议包含：目标列表、目标之间的依赖、候选资源指代、已知参数及来源、关键歧义、建议使用的能力、无法支持的部分。它是**未经信任的提案**；服务端校验 schema、业务资源与授权后才能推进。模型无需为每句问候强制创建任务，也不能从一句“好的”推导出业务写入许可。

### 4.1 澄清与复合请求

- “澄清”是某个目标的**等待状态**。待答对象应保存会话、目标、问题、预期答案、赛事范围、修订号、创建时间和失效条件；用户刷新后仍能继续。
- 先用有权数据补足可查事实，只问用户必须自己决定的歧义。对“所有队伍都要比过一场”，不能擅自解释为每队至少一场或单循环，应问清对阵规则。
- 简短回复“是的／确定”只匹配当前有效、语义明确的待答问题；没有待答问题时只作普通回复，不保存或发布。插话不改动待确认参数；切换任务或赛事需显式隔离旧条件。
- 复合请求逐项目标处理。例如“查 D 队下周赛程，再把那场改到周三”：先查询并定位；如果“那场”仍有歧义，再询问；生成预览后等人工确认。某一目标无权或不支持时，只停止它及其依赖步骤，已授权的独立目标可继续。

### 4.2 确认与风险等级

| 动作                   | 例子                         | 默认处理                                           |
| ---------------------- | ---------------------------- | -------------------------------------------------- |
| 自由对话               | 问候、通用问题               | 直接回答，不创建业务任务                           |
| 授权读取               | 查询赛程、单场详情           | 逐次鉴权后读取，不要求每次单独确认                 |
| 独立计算               | 生成候选并校验               | 依当前已确认需求和明确配置运行；候选不覆盖正式赛程 |
| 可恢复写入             | 单场调整并保存 DRAFT         | 先展示差异和冲突，用户点击绑定票据确认后才执行     |
| 发布、审批或高影响动作 | 发布赛程、审核材料、批量修改 | 当前不开放给 Agent；未来按独立能力和确认流程设计   |

“请直接帮我改”只表达写入意图，不跳过预览和确认。用户确认也不能提升账号权限。当前 C1 票据、固定 `commandId`、revision CAS、重启回执回放和审计边界必须保留。

### 4.3 建议的结构化契约（尚非现行 DTO）

意图理解器的输出只描述**候选目标**，不输出“已授权”“已确认”或可直接执行的命令。建议结构如下；字段和枚举待本项目的多目标 Skill、评测集与受控分发协议实现时定稿：

```text
IntentProposal
  goals[]:
    category: CHAT | BUSINESS_READ | KNOWLEDGE_READ | PLAN | CHANGE_REQUEST | UNSUPPORTED
    userGoal: 本轮诉求的短摘要
    dependsOn: 其它目标的本轮位置
    resourceHints: 用户提到的赛事、球队、场次文字线索
    proposedSlots[]: 字段、候选值、来自哪条用户消息
    ambiguities[]: 会阻碍下一步的歧义及原因
```

服务端生成真正的目标 ID，并校验类别、依赖、参数和资源。会话的待答状态至少记录 `goalId`、问题类型、展示给用户的问题、可接受答案形式、关联赛事、任务 revision 和失效时间。用户回答后先核对这条待答状态，再合并本轮提案；不能让模型仅凭历史文本猜测“是的”确认了什么。任务的结构化字段与原始消息分开保存，字段须标记来源（用户明确、已授权查询、模型推测）和是否已确认。LangGraph checkpoint 记录流程进度，业务数据库中的任务、票据和回执继续承担可恢复业务状态；两者都不保存登录凭据。

## 5. 权限与工具目录

每次工具调用按**当前登录账号 × 业务能力 × 资源范围 × 资源关系 × 当前状态 × 动作风险**判断。入口的工具可见性只是体验层；读、预览和写入的执行点都调用原业务授权。模型或客户端提供的 actorId、组织 ID、赛事 ID 不能成为授权依据。跨账号、撤权、过期会话、无权赛事和变更后的 revision 必须在服务端拒绝；返回内容不得泄露无权资源细节。

每个工具登记稳定名称与版本、参数/结果 schema、能力、资源定位、读写风险、确认策略、调用预算、超时、重试与幂等、审计与脱敏规则。首轮先映射现有赛程工具和确认端点，不复制业务算法；扩展一个新模块前先补齐它自己的工具契约与权限反例。

拒绝和失败应区分：**权限不足**说明当前账号不能访问或操作；**能力未接入**说明可讨论方案、使用原页面；**信息不明**提出具体问题；**模型或工具故障**说明未完成；**版本冲突**要求重新预览。不能统一回答“我不知道”，也不能把工具失败写成操作成功。

## 6. 三级记忆与事实来源

| 层级        | 当前载体与用途                                        | 新编排的补充规则                                                                         |
| ----------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| L1 会话     | `AgentTurn` 原文、`AgentSession` 滚动摘要             | 保留最近有效指代及来源；摘要只帮助理解，不恢复已失效权限或旧事实。新会话不继承旧会话任务 |
| L2 任务     | `AgentTask`、`AgentPlanningRequest`、候选、checkpoint | 每个目标独立记录已知条件、来源、待答问题、修订号、预览及有效期；复合目标不互相覆盖       |
| L3 长期偏好 | 本人明确确认的 `AgentMemory`                          | 按需、按 owner 读取；只影响表达或一般建议，不能成为赛事约束、业务默认值或授权            |

每轮构造模型上下文时：先认证和复核会话及相关赛事权限，再取与本轮目标有关的近期消息、摘要、有效任务、待答问题、必要偏好与有权引用；控制长度并标注来源。模型结果不能直接改写 L2 的权威字段：资源 ID 先定位，规则和参数由服务端验证，条件修订使用 revision 保护。L3 继续要求用户明确保存，不能从聊天自动“学习”业务事实或私密资料。用户删除偏好后，后续上下文立即排除。

**当前赛程、比赛结果、球队资料、权限和规程不属于聊天记忆。**业务事实由有权接口实时读取；规程类文档以后通过独立知识检索能力提供来源、版本、访问范围和撤权同步。知识检索可先用现有受控存储与全文查询评估，不因“要有记忆”就预先建设向量数据库。LangGraph 的线程状态和跨会话存储是两种不同机制，见[官方记忆文档](https://docs.langchain.com/oss/javascript/langgraph/add-memory)。

“上次那个比赛结果怎么样了”的解析顺序：本轮显式指代 → 当前有效任务 → 同会话最近有来源的查询 → 有权历史引用。若仍有多个候选，要求用户选择；唯一候选也要重新鉴权并查询当前结果，不能用摘要里的旧回答代替。

## 7. 分阶段开发计划

| 阶段                | 交付范围                                                                | 验收门槛                                                                   |
| ------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| A：Skill 与契约核验 | 自行开发意图理解 Skill，建立版本、示例和评测集；审查输出并确定结构化提案契约 | Skill 可固定版本并单独测试；不会输出授权结论或直接执行业务动作             |
| B：状态与上下文     | 待答对象、目标关联、指代来源、L1/L2/L3 选择与失效规则                   | “是的／确定”、刷新、插话、切换赛事和撤权后行为一致，不重复追问或泄露旧数据 |
| C：能力目录与授权   | 现有赛程能力映射、风险级别、参数校验、逐工具鉴权                        | 低权限、跨赛事、伪造 ID、撤权及无权历史均不能越界                          |
| D：编排迁移         | 先聊天和只读查询，再排程需求/候选，最后单场预览与原确认闭环             | 原业务结果、版本、票据、CAS、回执与审计保持正确；复合目标按依赖推进        |
| E：扩展与评估       | 资料检索设计、更多业务模块准入规范、运行轨迹与评测集                    | 新模块有真实业务 API/权限与端到端证据后才开放；阶段失败与未验项单列        |

用户已授权先自行开发 Skill 底座，后续在平台治理中编辑，因此首轮采用服务端版本化指令而非引用终端文件。当前两个 Skill 键及待答场景已接入，阶段 A 的完整评测集、阶段 B 的通用多目标待答状态、阶段 D 的复合目标编排尚未完成。此计划不预设大模型能自行学习数据库、自由创建工具或绕过现有业务服务。耗时较长的整套候选可在实施时评估后台任务；是否异步由实际耗时、恢复要求和并发压测决定，不因使用 LangGraph 就自动引入队列。

## 8. 评测与发布门槛

固定样例至少覆盖：问候与自我介绍；“刚才那场／上次那个比赛”；“是的／确定”的有效待答与无待答两种情况；复合查询加修改；单循环与“每队至少一场”的歧义；D 队仅周三可用；来源和目标时间区分；没有赛事、多个赛事及切换赛事；只读账号、跨账号、撤权、伪造资源 ID；模型超时、资料无来源、工具失败；预览后版本变化、重复确认和响应丢失。

意图识别可用人工标注样例评价语义质量；**实际调用的工具、参数、权限、赛程版本、候选完整性和命令回执必须用确定性断言**。分开记录模拟适配器、真实千问、Web、小程序、微信开发者工具、真机与远程环境的结果；健康检查、图形可视化或一轮模型成功都不等于整条业务链路验收。

## 9. 待核实材料与决策

1. 自行开发的意图理解与工具选择 Skill 的评测样例、质量阈值及发布流程；终端 pi-agent 的开发用 Skill 不自动进入产品运行时。
2. 首轮仍以已接入赛程能力为范围；扩展到材料、账号或其它模块时分别确定可读字段、可写动作与负责人。
3. 知识检索的首批文件、来源、版本、访问对象、更新与删除责任；未提供资料时不承诺赛事规则问答。
4. 新编排对旧会话及未完成任务的兼容和迁移方式；实施时不得直接改写既有业务状态或历史迁移。

本规划不能替代现行 [排程需求规则](../product/agent-schedule-planning.md)、[候选边界](../product/agent-schedule-candidates.md)、[单场确认方案](caau-049-c1-agent-confirmation.md)及 [三级记忆决策](../adr/0028-agent-three-level-memory.md)。
