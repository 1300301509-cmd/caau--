# CAAU-095：承办方小程序智能助手 Demo 执行链路

状态：**第一阶段单场改期对话链路本地实现；真实千问和微信工具仍待通过**。其余 Demo 范围尚未实施。2026-09-28 依据用户提出的短期团队内测目标制定；实施状态及分层证据以 [roadmap](roadmap.md) 为准。

## 1. 目标与首版范围

用户留在小程序统一助手的同一个对话中，可以自由聊天，也可以用文字或主动选择的资料完成自己所承办赛事的以下工作：

1. 查询赛程、口述单场改期，在对话中核对预览并保存赛程草稿。
2. 口述整套单循环排程要求，补齐配置、生成候选，在对话中核对后保存一个 `DRAFT` 赛程版本。
3. 口述球队资料，或上传微信聊天中的截图/文件、手机相册图片，提取资料并创建球队，加入当前赛事。
4. 一句话包含多个目标时，按依赖顺序执行，例如先加入新球队，再按更新后的参赛名单重新排程。

首版只接以上已具备领域服务的业务动作。“工作台内容可通过对话修改”以这些明确工具为验收范围，不提供任意字段或任意 SQL 写入。承办方在**自己承办的赛事**内使用这些工具；不为 Demo 新建细分角色矩阵。模型提出目标和参数，服务端仍从登录身份、承办关系和当前赛事解析可操作范围。当前赛程发布继续与草稿保存分开；首版验收以工作台可见的 `DRAFT` 为准。

用户已明确：微信聊天记录由本人选择截图或聊天文件上传，小程序不自动读取整段微信聊天。图片、资料只作本次任务来源；不自动变成长期记忆或知识库。

## 2. 现有基础和必须补的连接

| 能力 | 当前工程已有 | 首版需要补齐 |
| --- | --- | --- |
| 对话与记忆 | 统一会话、流式文字、会话摘要、排程任务状态 | 通用可恢复行动状态，复合目标的依赖与待确认项 |
| 语义理解 | 千问结构化路由、版本化 `INTENT_ROUTING` / `TOOL_SELECTION` / `SCHEDULE_PLANNING` Skill | 以模型结构化提案处理建队、附件及确认/修订；移除生产执行路径上的业务关键词语义捷径 |
| 单场改期 | 定位、确定性预览、票据、确认后保存 `DRAFT`、回执 | 把预览和绑定确认接入同一聊天；不再要求点击业务卡片按钮 |
| 整套排程 | 需求单、单循环候选生成和校验、票据、确认保存一个 `DRAFT` 版本 | 从现有配置取值、逐项补缺、在聊天中触发候选和确认 |
| 球队 | `createTeam` 可同时建档并加入赛事，另有更新/已有球队加入接口 | 登记 `team.create` 等工具；服务端从当前身份解析机构，不让用户填写内部 ID |
| 文件 | 材料模块已有选择、上传及私有存储机制 | 新增 Agent 专属附件、提取与消息引用；现有材料上传接口不能直接复用为 Agent 接口 |
| 小程序 | 统一助手当前是文本输入 | 两个附件入口、提取状态、行动预览、执行回执、工作台刷新 |

当前依据：[统一助手编排计划](caau-086-agent-orchestration-plan.md)、[排程需求规则](../product/agent-schedule-planning.md)、[候选规则](../product/agent-schedule-candidates.md)、[候选草稿保存](../adr/0031-agent-candidate-draft-save.md)。本计划改变的是**用户在对话中推进这些步骤的方式**；尚未把现有按钮流程描述成已支持纯对话执行。

## 3. 每条消息的执行链路

```text
小程序文本 / 已上传附件 ID
  → 登录身份与当前会话、赛事上下文
  → 读取本会话有效行动、待答问题及必要的已授权业务事实
  → 千问 + 活动 Skill 输出结构化目标提案（可多个）
  → 后端校验提案格式，定位当前赛事、球队或比赛
  → 缺少必须由用户决定的内容：保存待答状态，在原对话追问
  → 信息齐备：调用只读/候选工具，形成带版本和来源的预览
  → 用户在同一对话确认、修改或取消这份明确的预览
  → 重新读取当前业务状态，调用固定写入工具
  → 保存权威回执，回复实际结果，刷新小程序工作台
```

千问负责理解“帮我排十天”“再把 D 队加上”“就按刚才那个方案”等语义。生产链路不使用用户原文的关键词/正则来决定业务意图、球队或场次。程序仍负责 JSON/schema、ID 定位、必填字段、赛程算法、版本和结果校验；这些不是自然语言关键词识别。模拟适配器可继续服务确定性测试，但不能作为真实模型理解验收。

结构化提案的最小字段：`goalType`、`dependsOn`、`eventHint`、`resourceHints`、`slots`、`slotSources`、`missingInformation`、`proposedTool`、`replyToPendingActionId`。模型输出只是提案；服务端生成行动 ID，不能相信模型给出的账号、机构、赛事 ID 或“已确认”结论。

一个会话可有多个目标，但**同一时间只要求用户确认一份明确的写入预览**。待答、预览和确认绑定 `sessionId + actorId + eventId + actionId + revision`；刷新、重新登录后可恢复。用户对预览补充条件时增加 revision，旧确认作废；切换赛事时旧行动不进入新赛事。针对待确认行动的文字回复交由模型判断为确认、修改、取消或普通插话，再由后端检查其唯一目标与当前版本；没有有效待确认行动时，“好的”只是一句普通消息。

### 持久行动与返回结果

| 状态 | 服务端含义 | 对话表现 |
| --- | --- | --- |
| `NEEDS_INPUT` | 目标已识别，但缺少用户必须决定的字段 | 只问当前最关键的一项，后续回答合并到同一行动 |
| `PREVIEW_READY` | 已得到确定性预览或球队建档草稿 | 显示对象、字段来源、预计变化和最新版本 |
| `AWAITING_CONFIRMATION` | 一份预览绑定行动 ID、revision 和有效票据 | 等待对该预览的文字确认、修改或取消 |
| `EXECUTED` | 原业务服务返回权威写入结果 | 显示赛事、球队或赛程版本，以及可回放回执 |
| `STALE` / `CANCELLED` / `FAILED` | 基础数据变化、本人取消或实际执行失败 | 不展示成功文案；提供重新预览或补充资料入口 |

建议保持现有 `POST /agent/sessions/:sessionId/messages[/stream]` 为唯一对话输入，只给 DTO 增加 `attachmentIds` 与可选的行动引用；返回增加结构化 `actions[]`、预览摘要、待答及回执引用。附件采用独立的 `/agent/attachments` 上传和状态接口。赛程仍调用当前 planning/candidate/confirmation 服务，球队仍调用当前 TeamsService；新行动表只保存编排状态与引用，不复制权威业务数据。流式 `delta` 仅是临时文字，客户端只有收到最终 `result` 才展示“已执行”。

## 4. 三条首版业务路径

### A. 单场改期

“把周一第二场改到周日上午十点半” → 查当前有权赛程并定位唯一场次 → 时间/场地缺项时追问 → 调现有单场预览 → 在聊天中说明原时间、新时间、冲突和版本 → 用户文字确认 → 复用现有票据、`DRAFT` 写入与命令回执 → 工作台重新读取当前赛程。用户更改条件后必须产生新预览，不继续旧票据。

### B. 整套编排

“十天内让所有队伍两两交手一次” → 查赛事日期、全部有效参赛球队及已有配置 → 把缺少的场地、每日时段、每场时长、缓冲和最短休息逐项问清；已有配置可以注明来源后采用 → 在聊天中展示完整条件并确认生成候选 → 复用现有单循环候选算法及独立校验 → 按日展示对阵、场地、时间、冲突和基础版本 → 用户文字确认保存 → 复用现有候选票据与 `DRAFT` 保存服务，只产生一个新版本及一个可恢复回执。候选不存在或不满足硬条件时继续修订条件，不宣称已完成排程。

若一句话要求“先加 A 队，再重新排赛程”，建队成功后重新读取参赛名单，随后才生成候选；不沿用建队前的球队快照。

### C. 球队口述或资料建档

口述资料直接进入结构化提取；附件先上传并返回 `attachmentId`，提取完成后再进入同一流程。读取当前赛事与机构、检索可能重复的球队 → 展示提取出的球队名、负责人、联系电话、省、市及每项来源 → 只追问真正缺失的必填信息 → 用户在聊天中确认建队 → 调现有 `createTeam(eventId)` 领域服务，一次建档并加入赛事 → 返回球队和赛事参赛记录，并刷新“我的比赛／球队管理”。若资料中还包含球员名单，另形成名单更新目标，不把名单塞入球队简介。

一份资料含多支球队时，每支球队有独立草稿与结果。重试同一已完成行动展示原结果，不重复创建球队；某支失败时明确列出它，已成功的球队不被描述为失败。

## 5. 附件链路与小程序入口

小程序对话框的附件按钮分为：

- **从微信聊天选择**：由用户使用 [`Taro.chooseMessageFile`](https://docs.taro.zone/docs/apis/media/image/chooseMessageFile) 主动选择截图或 PDF、Word 等聊天文件。
- **从本地选择**：首版使用 [`Taro.chooseImage`](https://docs.taro.zone/docs/apis/media/image/chooseImage) 从手机相册选择图片/截图；手机本地文档可先分享至微信文件传输助手，再从“微信聊天选择”。不要把“从本地选择”误写成可任意浏览手机文件系统。

服务端增加独立于办赛申请的 Agent 附件登记、上传、确认、状态及提取接口。消息只传附件 ID，不把二进制或整份文件编码进聊天文字。上传记录绑定当前账号、会话和赛事，保留文件名、类型、大小、提取状态与来源；实际文件复用私有存储。首轮目标格式为 JPG/PNG、PDF、TXT、DOCX：文本类在服务端提取，图片由 OCR 或已配置的视觉模型解析。现有千问聊天适配只传文本，不能把截图直接送给它当文字。提取结果保留页码或图片来源，允许用户在聊天中纠正；模型只接收与当前目标相关的节选。

文件选择与上传失败时保留输入和已选文件状态，说明失败发生在选择、上传、提取还是建队步骤。未提取成功不触发建队。

## 6. 最小工程改动顺序

| 顺序 | 开发包 | 完成标志 |
| --- | --- | --- |
| 1 | 扩展对话提案与持久行动状态；生产路由移除业务关键词语义捷径；固定工具目录增加球队动作 | 普通聊天、复合目标、追问、插话、刷新和切换赛事能正确恢复/隔离 |
| 2 | 将单场与整套排程的现有预览、票据、`DRAFT` 保存接到文字对话 | 不使用候选表单或确认按钮，能从一句话和必要补问完成真实草稿写入 |
| 3 | 接入球队口述创建、重复候选核对和赛事工作台刷新 | 用户在聊天中补齐必填资料并创建、加入当前赛事；重试无重复 |
| 4 | Agent 附件接口、文本提取与图片识别；小程序两个选择入口 | 微信聊天截图/文件和本地相册图片均能形成可追溯的球队草稿 |
| 5 | 真实千问、微信开发者工具、真机及团队内测环境联调 | 按第 7 节完整用例留存证据；测试环境使用实际 AppID 和手机可达 API |

接口变更先修改 Nest DTO/控制器，再生成 `@caau/api-client`；小程序只通过该客户端访问 API。数据库变化使用前向迁移，不更改历史迁移或现有赛事数据。最小新增持久对象是附件元数据和可恢复的跨模块行动/待确认状态；赛程版本、需求单、票据和命令回执继续使用现有权威数据，不复制一份“Agent 赛程”。

## 7. Demo 验收脚本

1. 普通对话：“你好，介绍一下你自己”；助手正常回答，不创建业务行动。
2. 口述新球队的完整资料；聊天确认后，球队管理出现一支新队并加入当前赛事。再发相同确认只回放原结果。
3. 上传微信聊天截图或文件中的球队资料，以及相册截图；助手展示识别内容、补问缺项，再完成建队。另一份包含多支球队的资料逐支显示结果。
4. 在五队赛事说“十天内每两支队伍交手一次”；助手沿用有来源的配置、追问缺项，生成十场各不重复的候选；确认前正式赛程版本不变，确认后只新增一个 `DRAFT` 版本，工作台逐场一致。
5. 口述单场改期、在预览后改口、再次确认；最终只执行最新版预览并展示原命令回执。
6. 复合请求“加一支球队，然后重排”：先看到新球队，再用更新后的球队集合排程。切换到另一赛事时，旧行动不继续执行。
7. 模型超时、附件提取失败、候选无解、赛程版本变化分别给出对应状态；任何未执行的步骤都不报告成功。

自动化需分别覆盖结构化语义契约、真实领域服务/隔离 PostgreSQL、重复确认、客户端契约及小程序界面；真实千问与微信开发者工具、真机、团队环境结果分开记录。`check`、三端构建和原有回归是代码门槛，不能代替第 4 项的真实赛程写入与第 3 项的微信文件选择验收。

## 8. Demo 环境准备

团队通过微信实际试用前，需要可用的小程序 AppID、手机可访问的测试 API、现有千问文本配置和图片识别服务。当前 `touristappid` 与回环地址仅可用于本机开发者工具体验。以上资源不阻塞前四个开发包在本地实施；环境到位后执行第 5 包验收。

## 9. 第一阶段：单场改期对话闭环（本地实现）

本阶段仅落实第 4 节 A：小程序保持普通聊天；千问结构化路由决定启动/继续/确认的提案，原增量字段提取负责星期、来源当天序号与目标时刻；缺字段使用既有持久任务追问。业务服务定位唯一比赛并生成确定性前后、冲突和基线的预览，当前会话可刷新恢复。针对该预览的明确文字“确认执行”由后端取**当前最新任务**的未过期票据，不接受模型提供票据或写入参数；条件改动或开始另一任务即取消旧票据。沿用原票据和单场赛程服务在事务中保存一个 DRAFT 版本、回执及确认消息，刷新后仍可读取原 commandId。小程序在当前对话提示文字确认并重新读取赛程；返回工作台依既有页面显示生命周期重新拉取业务状态。Web 既有按钮保留，文字执行后的赛程读取也同步更新。详细绑定见 [ADR-0032](../adr/0032-agent-single-match-text-confirmation.md)。

不包含整套候选的文字保存、球队、附件、复合目标或 Agent 发布。前述 1—8 节仍是整个 Demo 的后续计划，不能将这些项描述为第一阶段已完成。验收结论及环境缺口见 [roadmap](roadmap.md)。
