# 业务板块与代码目录映射

来源：2026-09-08 用户提供的导航截图。12 个板块名称已确认；表内英文目录与后端职责是工程规划，具体功能、数据范围和两端上线范围仍需逐模块梳理。本文不代表已有业务源码。

## 三层组织

1. 应用层：`apps/miniapp`、`apps/admin`、`apps/api` 分开，分别负责小程序、管理后台和服务端。
2. 业务层：前端按功能组织页面和交互；后端按业务数据与规则归属组织模块。
3. 模块内部：前端分页面、组件和数据请求；后端分接口入口、参数校验、业务处理和数据访问。

业务目录应在开始写对应功能前确定。现在先明确映射和边界；工程初始化时建立实际使用的目录、入口和依赖检查，模块实现时补齐源码及测试。空文件夹本身不构成工程实现。

## 12 个板块的规划映射

前端路径均以 `apps/admin/src/features/` 为前缀；小程序选定对应功能后，在 `apps/miniapp/src/features/` 下采用相同业务词汇，并通过平台页面入口承载。截图不自动决定小程序的导航方式或首版范围。

后端路径均以 `apps/api/src/modules/` 为前缀。

| 导航板块 | 前端功能目录 | 主要后端模块（规划） | 边界说明 |
| --- | --- | --- | --- |
| 经营总览 | overview/ | reporting/ | 按当前用户权限聚合数据；不另建一套财务或赛事事实数据 |
| 财务中心 | finance/ | finance/ | 预算、预测与实际收支规则；具体核算口径待确认 |
| 运营中心 | operations/ | events/、registrations/ | 暂按赛事与报名编排页面，实际子功能梳理后细分 |
| 协同中心 | collaboration/ | tasks/ | 任务、交付、审核及协作记录 |
| 承办方门户 | organizer/ | events/、tasks/、organizations/ | 面向承办方的入口，复用赛事与任务能力，不复制业务表 |
| 增长中心 | growth/ | growth/ | 具体增长业务待确认；暂不预设营销、线索或 CRM 模型 |
| 俱乐部球队 | clubs/ | organizations/、teams/ | 机构归组织模块，球队及成员业务归 teams；参赛名单归报名模块 |
| 赞助权益 | sponsorship/ | sponsorship/ | 赞助与权益业务；若需要交付任务，引用 tasks 的能力 |
| 裁判管理 | referees/ | referees/ | 裁判业务档案及可能的赛事分配；登录身份仍归 auth |
| 资料中心 | resources/ | resources/、files/ | resources 管资料目录、版本及业务可见性，files 管文件对象和受控传输 |
| 智能助手 | assistant/ | ai/ | 通过已授权业务接口查询或执行动作，不建立第二套业务规则 |
| 数据管理 | data-management/ | 待确认后映射至各数据所属模块 | 尚不确定指字典、导入导出还是系统设置，不预设万能改表接口 |

`auth/`、`organizations/`、`permissions/`、`files/` 等基础能力服务多个板块，不必各有一个导航菜单。通知能力在需求明确时引入。

## 一个贯穿示例：承办方提交材料

承办方门户展示待办，调用 tasks 提交交付；files 负责文件对象与上传验证，tasks 保存材料与任务的关联；权限检查结合当前用户、组织关系和赛事授权。总部在协同中心查看同一任务，执行审核并保留历史。

两个页面入口复用同一套任务记录和状态规则。不能因为菜单不同，就各建一套提交、审核和附件授权逻辑。

## 模块内部示例

以下是 tasks 实现时的目标示例，尚未创建这些源码文件：

```text
apps/api/src/modules/tasks/
├── tasks.module.ts          模块入口与导出能力
├── tasks.controller.ts      接口入口
├── tasks.service.ts         任务用例、状态规则和事务编排
├── tasks.repository.ts      数据访问
├── dto/                     输入校验与接口契约
└── tasks.service.spec.ts    关键业务规则测试

apps/admin/src/features/collaboration/
├── pages/                   页面
├── components/              此功能专用组件
└── hooks/                   请求与交互状态，通过 api-client 调接口
```

只在有实际内容时创建子目录。共享 UI 留在本应用的 components，跨模块复用优先经过公开接口，禁止用一个不断膨胀的 common/utils 目录存放所有业务。

## 每个模块开始实现前的准入条件

- 写明使用角色、子功能、主要数据及归属。
- 明确状态流程、权限范围、依赖模块和接口。
- 定义正常流程、失败流程及越权反例的验收标准。
- 将任务挂到开发计划，实现相关源码、数据迁移和必要测试。

模块映射是起点，数据库字段和 API 不能只根据菜单名称直接生成。
