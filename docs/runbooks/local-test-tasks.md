# 本地单份材料体验任务

本操作在 [本地测试赛事与授权](local-test-events.md) 的 A/B 赛事上，通过现有业务 API 幂等准备两个可由用户亲自办理的单份材料任务：

- 测试赛 A 办赛资料 → 承办方 A 经办人
- 测试赛 B 办赛资料 → 承办方 B 经办人

不预建材料，不代替用户保存、提交或审核，不创建附件。任务使用单份材料通道和空要求清单，承办方可自由新增材料。

## 准备与幂等规则

保持 dev 数据库、local 模式 API 与 Web 运行：

```sh
CAAU_IDENTITY_MODE=local corepack pnpm db:api
corepack pnpm dev:admin
corepack pnpm tasks:local
```

`tasks:local` 先运行第二步赛事脚本，补齐并验证两个赛事和五身份范围，再执行：

1. 固定总部赛事管理员调用 `POST /api/v1/individual-material-tasks`，分别按现有 `organizationId + handlerMemberId` 指派 A/B 经办人。
2. 调用 `PATCH /api/v1/material-tasks/:id/requirements` 配置空 `materials: []`，不设置固定五项清单。任务截止为 **2099-12-31T15:59:59.000Z**（中国标准时间 2099-12-31 23:59:59），这是明确的远期本地演示值，用于保证当前可提交，不是正式业务默认值或生产规则。
3. 调用 `POST /api/v1/material-tasks/:id/publish` 发布。发布后要求快照不可变，脚本不会延期或覆盖。
4. 再次运行时优先使用忽略索引 `.local/db/local-test-tasks.json`，否则按 eventId + 完整任务名查找。已有任务必须严格匹配赛事、机构、经办人、单份通道、空清单、截止和发布状态；任何不一致都失败，不自动修改。缺失或上次仅创建了空草案时才完成必要配置/发布。
5. 五个真实会话分别调用任务列表与 `GET /material-tasks/:id`：管理员、审核员甲/乙可读 A/B；承办A只读A且B为403；承办B只读B且A为403。最后分别读取 A/B snapshot，必须均为0份材料。

索引只含任务/赛事ID、身份别名、演示截止和Web链接，不含token。准备脚本注销验收会话，不直接写 MaterialTask、TaskScope、要求快照或授权表。

## 亲自体验

打开对应链接后选择身份：

- A任务：选择 **承办方 A 经办人**，任务下拉自动定位“测试赛 A 办赛资料”。可点击“自由新增材料”。
- B任务：选择 **承办方 B 经办人**，任务下拉自动定位“测试赛 B 办赛资料”。可点击“自由新增材料”。
- 审核：另开标签页选择 **总部审核员甲** 或 **总部审核员乙**。两者任务下拉均包含 A/B；承办方提交材料后会进入共享审核队列，甲开始后乙可接续，实际动作人由后端记录。

任务链接格式为 `/materials?event=<赛事ID>&task=<任务ID>`。身份保存在当前标签页，刷新后会重新验证并恢复；不同标签页可分别保持承办方与审核员。刚准备完成时列表应显示“0份材料”，这是预期起点。

不要用承办方 A 打开 B 深链或反向操作；后端会返回403并清理无权内容。页面隐藏或下拉过滤不是权限依据，脚本已通过真实接口反例验证。
